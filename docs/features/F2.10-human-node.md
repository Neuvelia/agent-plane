# F2.10 - Human node and local approval (minimal)

**Status:** partial (ADR-0017 implemented; ADR-0043 proposed). Not delivered: the blast-radius model (F3.9, owner decision D14) and a diff body in the panel.
**Priority:** P0
**Target phase:** Phase 2 - Local IDE (vertical slice)
**Depends on:** F0.4, F0.6, F1.5
**ADR:** ADR-0017 (accepted), ADR-0043 (proposed)

## Problem

The graph can only fail or succeed on deterministic evidence. A consequential
step (for example applying an accepted change) has no way to stop the run and
wait for an explicit human decision, and no auditable record of that decision.

## Goal

A `human` node pauses its branch until a local approve or reject decision
arrives, emits both facts as events, and lets the rest of the graph continue or
stop deterministically. "Waiting for a human" is derived from the event stream
(`approval_requested` without a matching `approval_decided`); it is not a
scheduler node state.

## Non-goals

- Blast-radius scoring (moved to F3.9, owner decision D14), reviewer roles, multiple approvers, approval expiry.
- Web/hosted approval (F4.8), push notifications, identity of the approver.
- Conditional branches: schema 0 has no conditional edges, so every dependent of a human node runs on either outcome (ADR-0043).
- Approval timeouts (the wait ends only by decision or run cancellation).
- Resume of a waiting run after process death (F3.3).

## Functional requirements

1. Node `type: human` is valid in graph schema 0. Optional `config.prompt`
   (string, max 1024 bytes, shown to the approver). Optional declared string
   inputs are carried into the approval request as bounded context.
2. A `human` node declares output port `decision` (string). On approve it
   publishes `decision: "approved"` as its accepted output; downstream nodes
   depend on it through an ordinary data binding. No ordering-only edge is added.
3. When all dependencies are accepted the node starts like any node (it holds
   one concurrency slot), emits `approval_requested` and blocks in the decision
   provider. Nodes that share its scheduler batch keep running while it waits.
   The existing batch barrier (ADR-0014) is unchanged: nodes that become ready
   only after the batch completes start after the decision. The node remains
   `running` for the scheduler.
4. A decision `{approve|reject, comment?}` (comment truncated to 2048 bytes
   after redaction) is delivered through a runtime `DecisionProvider` seam
   that the scheduler calls exactly once per human node run, so exactly one
   `approval_decided` is emitted. A provider that serves several channels (the
   local API, F2.5) owns first-decision-wins: later decisions for the same node
   run are refused without effect and return the original decision.
5. Approve: emit `approval_decided`, node `succeeded`. Reject: emit
   `approval_decided`, node `failed` with failure kind `rejected` and safe code
   `human_rejected` on `node_finished`; dependents are skipped; run fails; CLI exit 4.
6. Cancellation while waiting ends the node `cancelled`, emits no decision
   event, and does not hang the run. If the provider had already accepted a
   decision when cancellation arrived, `approval_decided` is still emitted and
   the node then ends `cancelled`. A provider error other than cancellation
   fails the node with safe code `human_decision_invalid`; provider error text
   never enters an event.
7. CLI provider: explicit `--approve NODE` / `--reject NODE` flags (repeatable;
   must name a human node, one flag per node) and an interactive prompt on
   stderr when stdin is a real terminal (checked with `golang.org/x/term`;
   `/dev/null` and `/dev/zero` are not). Concurrent human nodes are prompted one
   at a time. If any human node has
   neither a flag nor a terminal, the run fails preflight (`E_HUMAN_NO_PROVIDER`,
   exit 3) naming the node, before any node executes.
8. Reject routing (ADR-0043). Optional `config.on_reject`: `fail` (default,
   requirement 5) or `continue`. With `continue` a rejection still emits
   `approval_decided` (`rejected`), but the node ends `succeeded` with
   `decision: "rejected"`; the run is not failed by it and the verdict is
   published through a graph output bound to `decision`. Validation: any other value
   is `E_HUMAN_INVALID`. `continue` is `E_HUMAN_REJECT_UNROUTED` unless
   `decision` reaches graph outputs only, and at least one. A Shell, Agent or
   loop node bound to it runs on rejection (a loop's producer runs before its
   Gate), and no standalone Gate kind can compare the verdict string (`command`
   compares files), so any edge from `decision` to a node input is reported.
9. Approval context in the desktop panel (pure view of existing events and the
   graph summary): the prompt as the reason for approval; for each upstream node
   the latest check verdict and reason, the Git-observed changed files (bounded;
   unknown is shown as not observed, never as zero), and a link that opens that
   node. It adds no event and no decision logic. Blast radius is F3.9 and a diff
   body needs the attempt diff panel (ADR-0026), so neither is shown.

## Data / API contracts affected

Graph node type `human` (validated: one `decision` string output, config limited to `prompt`, `context_inputs` and `on_reject`, no loop); new event types
`approval_requested` and `approval_decided` (event schema 9, additive; decode
of schemas 1-8 unchanged); runtime `DecisionProvider` interface; CLI flags.

## Failure behavior

- `human` node without a path to a decision provider: preflight error naming
  the node.
- Comment over limit: truncated after redaction (the provider/API may refuse
  earlier). Unknown decision value or unknown/already-decided node run: refused
  by the provider layer with no state change.

## Acceptance criteria

- [x] A graph with `human` is valid; a missing provider fails preflight, exit 3, naming the node.
- [x] An `approval_requested` event is observable by a live consumer before any decision exists.
- [x] A node in the same scheduler batch completes while the human node waits (deterministic barrier test). Later-batch nodes wait for the barrier.
- [x] Approve publishes `decision: "approved"` and downstream runs exactly once.
- [x] Reject fails the node with code `human_rejected`, skips dependents, exit 4.
- [x] The scheduler asks the provider once per node run, so no second `approval_decided` exists. Cross-channel first-wins is verified with the local API (F2.5).
- [x] Cancellation while waiting terminates the run without leaked goroutines.
- [x] Events carry run/node-run IDs, bounded prompt/comment, and no secrets.
- [x] Schema 1-8 event streams still decode.
- [x] `make check` passes.
- [x] `on_reject: continue` makes a rejection succeed the node with `decision: "rejected"`, validated by `E_HUMAN_REJECT_UNROUTED` unless the decision reaches graph outputs only; the default still fails the run (ADR-0043).
- [x] The panel shows the reason, upstream check verdicts, changed files and an open-node link (EN and PL).
- [ ] Blast radius in the panel (F3.9) and a diff body in the panel (attempt diff panel, ADR-0026): not delivered, so this feature stays `partial`.

## Required tests

- Unit: decision validation, idempotency, state transitions.
- Integration: parallel branch completes during wait (explicit barrier, no sleeps), approve, reject, cancel.
- CLI/e2e: `--approve` and `--reject` flags, preflight failure without provider.

## Security / trust considerations

Prompt, inputs and comment are untrusted text: bound, redact configured
secrets, never interpret. A decision does not widen filesystem or process
permissions. The local API (ADR-0019) must authenticate decisions.

## Observability

`approval_requested` (prompt, bounded context, node run ID) and
`approval_decided` (decision, comment, node run ID, timestamp) are append-only
facts with sequence numbers.

## Open questions

- Conditional branches (run only the approve or the reject path) need scheduler support and are deferred; see ADR-0043 alternatives.

## Out of scope for this iteration

Roles, expiry, blast radius (F3.9), web approval, resume, notification.
