# F3.1 - Workspace Isolation / Git Worktrees

**Status:** draft (open questions resolved by the product owner on 2026-11-16 as
recorded in ADR-0024; ADR-0024 accepted 2026-11-16 after the real-Codex spike
passed; ready for an implementation plan)
**Priority:** P0
**Target phase:** Phase 3 - Local Production Ready
**Depends on:** F1.7 (static units, accept-once), F1.8 (Git-observed scope baseline)
**ADR:** ADR-0024 (accepted; isolation model, event semantics, integration
contract)

## Problem

F1.7 makes accepted runtime *values* immutable, but every Agent still writes to
one shared checkout. ADR-0015 documents the consequences:

- a correction attempt of unit C may overwrite files that accepted unit B
  produced, even though B's accepted values are frozen;
- unit-mode serializes every Agent cycle that shares a checkout, so a graph with
  two parallel workers gets no real parallelism;
- an attempt that is later rejected has already written into the user's working
  tree, and nothing rolls it back;
- F1.8 only *detects* out-of-scope changes after the fact.

The MVP scenario (`docs/reference/full-architecture-plan.md` §22, points 3-7:
two parallel workers, one fails a test, only that unit is corrected, siblings are
not re-run) is only trustworthy at file level if the units cannot see each
other's files.

## Goal

An Agent node can opt in to running in its own Git worktree created from an
explicit base commit. After the feature:

- two parallel isolated nodes can change the same file with no filesystem race;
- files written by an attempt that was not accepted never reach the integrated
  result, and never touch the user's source workspace;
- an accepted unit's changes are integrated deterministically, and a conflict is
  reported as evidence instead of being resolved silently;
- worktrees are cleaned up automatically, with an explicit retain-on-failure
  policy.

## Non-goals

- Process, network or filesystem **sandboxing**. A worktree is a different
  directory, not a permission boundary: an agent that writes to an absolute path
  can still modify the source checkout. Confinement belongs to F3.9.
- Semantic merge, rebase or automatic conflict resolution (manual by roadmap).
- Isolation of Shell nodes, standalone Gate nodes and Human nodes (see Q4).
- Making upstream file changes visible to downstream isolated nodes (see Q1).
- Modifying the user's branch, index or working tree (see Q3).
- Resume of interrupted runs and orphan recovery (F3.3, F3.11).
- Containers, VMs, remote or managed runners.
- Windows. Linux and macOS only, like the current Git helpers.
- Any UI change. The desktop must tolerate new events; showing them is later work.

## Functional requirements

### Opt-in and validation

1. Agent `config` accepts an optional `isolation: "none" | "worktree"`. Absent
   means `none` and preserves F1.7 behavior exactly, including the existing
   same-checkout serialization and every existing semantic hash. Unknown values
   fail at the Agent executor boundary.
2. `isolation: worktree` is valid only on a loop-enabled Agent node that is
   enrolled in top-level `units` (the acceptance registry exists only there).
   Any other use fails preflight, before `run_started`, naming the node.
3. `graph.workspace` semantics are unchanged: it stays the **source** repository
   and is the only workspace path in the graph. The runtime derives the
   effective workspace; the graph never contains a worktree path. The Gate's
   `workspace` must still equal the Agent's declaration (F1.8); the runtime maps
   both to the effective workspace.
4. `isolation` is semantic content: it is included in the semantic version.
   Graph `schema_version` stays 0 (additive optional field).

### Base commit

5. At run start the runtime resolves the source workspace HEAD to a full commit
   SHA exactly once. All isolated nodes of that source use this SHA. The SHA is
   recorded in the trace. A source without a committed HEAD, a bare repository,
   submodules or unresolved index stages fail preflight (same rules as
   `internal/gitstate`).
6. Preflight fails with an actionable error when the source has staged or
   unstaged changes to **tracked** files, because they would be silently absent
   from the worktree. Untracked and ignored files are not carried into worktrees
   and this is documented (see Q2, Q8).

### Worktree lifecycle

7. One worktree per isolated node run, created before its first attempt with a
   detached HEAD at the base SHA. It persists across the node's correction
   attempts, so a correction builds on the rejected attempt's files exactly as
   F1.6 does today. A fresh worktree is **not** created per attempt.
8. Worktrees live in a runtime-owned directory outside the source tree, created
   with mode `0700`. The directory name is derived from run and node-run IDs,
   never from the raw node ID or any other graph-controlled string. Paths are
   confined; symlinked or pre-existing targets are refused.
9. Agent invocation, the embedded Gate and the F1.8 scope baseline all use the
   worktree as workspace. Because the worktree is clean at the base SHA, the
   F1.8 baseline starts clean for each unit.
10. Scheduling uses the effective workspace identity. Two isolated nodes have
    distinct physical roots and a shared Git directory; per ADR-0015 distinct
    linked worktrees remain concurrent. Isolated nodes do not conflict with a
    non-isolated Agent in the source checkout. Declared-scope conflict
    diagnostics (schema 7) are not reported between isolated nodes.

### Acceptance and integration

11. Only a green, accepted attempt (F1.7 accept-once) is integrated. At
    acceptance the coordinator snapshots the worktree as a commit whose parent is
    the base SHA, stored under `refs/agentplane/<run_id>/units/<node_id>`
    (node ID encoded safely for ref names). The snapshot uses the worktree's
    contents; the commit is created with controlled identity and no hooks.
12. Integration is performed by the coordinator, serially, in the existing
    deterministic acceptance order (sorted node ID within a batch). Each unit
    commit is three-way merged onto the run's integration ref
    `refs/agentplane/<run_id>/integrated`, which starts at the base SHA. The
    result for a given set of accepted units and order is deterministic.
13. A merge conflict does not change accepted values and does not rerun any
    sibling. The runtime records a conflict fact with the conflicting paths
    (bounded, with an omitted count), leaves the integration ref at the last
    clean state, retains the conflicting unit's worktree, and the run ends
    `needs_intervention` (CLI exit 4). No conflict is auto-resolved.
14. A rejected or exhausted unit is never integrated. Its worktree contents
    exist only in its worktree.
15. The source workspace's branch, index and working tree are not modified by
    the runtime. The CLI result reports the base SHA, the integration ref and
    its commit SHA, and the per-unit commit SHAs, so the user can merge manually
    (see Q3).

### Cleanup

16. `--retain-worktrees never|failed|always`, default `failed`:
    - `never`: remove every isolated worktree when its node run ends;
    - `failed`: remove worktrees of accepted-and-integrated units; retain those
      of rejected, exhausted, conflicting, errored or cancelled units;
    - `always`: retain all.
    The run-scoped refs are always kept (they are the deliverable). Cleanup
    failure never changes run status; it is reported as a trace fact and as a
    CLI warning with the path to remove manually.
17. Cancellation terminates the node's process first, then applies the retention
    policy. Retained worktrees are reported with their absolute path.
18. Worktree root is configurable with `--worktree-root PATH` (absolute; same
    confinement and mode rules). The default location is decided in ADR-0024
    (see Q5).

### Source-workspace guard

19. Because a worktree is not a sandbox, the runtime captures an F1.8-style
    snapshot of the source workspace at run start and compares it at run end
    when at least one isolated node ran. A difference is recorded as an
    observed (not attributed) fact `source_workspace_changed`, with bounded
    sorted paths. It is a diagnostic: it does not fail the run, because the user
    or another process may legitimately have edited the checkout.

## Data / API contracts affected

- **Graph:** optional Agent `config.isolation` (additive; schema 0; semantic hash
  includes it only when present). `docs/graph-spec.md` updated.
- **Events:** additive schema 10 (assigned by merge order, see ADR-0024;
  ADR-0023 also proposes a schema for recorded run values and takes the next
  free number if it lands second). New typed facts: `workspace_prepared`, `workspace_integrated`,
  `workspace_conflict`, `workspace_released` (removed or retained, with reason),
  `source_workspace_changed`. Older schemas stay readable; no existing payload
  changes.
- **CLI:** `--retain-worktrees`, `--worktree-root`; JSON result gains an
  optional `workspace_isolation` object (base SHA, refs, per-unit SHAs,
  retained paths). CLI envelope version stays 1 unless ADR-0024 decides
  otherwise.
- **API/desktop:** no new endpoint. Existing replay must tolerate and ignore
  unknown event types.
- **Git state of the source repository:** worktree metadata is written under the
  source's common Git directory, and refs under `refs/agentplane/`. This is the
  only write into the source repository and is documented.

## Failure behavior

- Preflight (before `run_started`, no run identity): invalid `isolation` value,
  isolation on a non-loop or non-enrolled node, dirty tracked source, bare repo,
  submodules, missing HEAD, unusable or unsafe worktree root.
- `git worktree add` fails (disk full, permissions, Git missing): the node run
  is an operational error with a safe actionable message; no verdict is invented
  and no envelope is produced. Siblings that already ran are unaffected.
- Snapshot commit fails at acceptance: operational error, node is not integrated,
  run ends non-green; accepted values remain as recorded.
- Merge conflict: requirement 13.
- Cleanup failure: requirement 16.
- Process crash mid-run leaves worktrees and possibly refs behind. v1 does not
  clean them automatically; names are prefixed so they are identifiable
  (Q5). Recovery is F3.3/F3.11.
- Raw Git stderr is never placed in events; messages are classified and bounded.

## Acceptance criteria

- [ ] A graph with two isolated Agent units, both instructed (by a deterministic
  fake adapter) to rewrite the same tracked file `shared.txt` with different
  content, runs the two attempts **concurrently** (proven by a barrier both
  reach before either returns), and each unit's worktree contains only its own
  content.
- [ ] After that run the source workspace's `git status` and working-tree file
  hashes are identical to before the run, and its HEAD is unchanged.
- [ ] A unit rejected on attempts 1 and 2 and accepted on attempt 3 leaves
  nothing from attempts 1-2 in its unit commit that attempt 3 removed, while
  attempt 2 does see attempt 1's files (worktree persists across attempts).
- [ ] A unit that exhausts its budget produces no unit ref and no integration
  commit; its files exist only in its retained worktree.
- [ ] Scoped-retry scenario with real files: A, B, D accepted, C red then green.
  C's retry writes to B's file path; B's unit commit and the final integrated
  tree contain B's content, and A/B/D agent invocation counts remain 1/1/1
  with C at 2. (This closes the ADR-0015 "shared files may change" limitation
  for isolated units.)
- [ ] Two accepted units editing disjoint files integrate into one commit
  whose tree contains both; the result is byte-identical across 20 repeated
  runs of the same inputs and order.
- [ ] Two accepted units editing the same lines produce `workspace_conflict`
  naming the paths, leave the integration ref at the previous clean commit,
  exit code 4, and do not rerun or alter the already accepted unit.
- [ ] `isolation: worktree` on a non-enrolled node, on a non-loop node, with a
  dirty tracked source, or with an invalid value fails preflight with exit
  non-zero and no `run_started` event.
- [ ] Graphs without `isolation` have unchanged semantic hashes, event
  sequences and scheduling (existing F1.7 tests pass unmodified).
- [ ] `--retain-worktrees` `never`, `failed` and `always` each leave exactly the
  documented set of directories on disk after a mixed accepted/rejected run.
- [ ] Worktree directory names contain no graph-controlled text; a node ID with
  `../`, spaces, `.lock` suffix or non-ASCII characters neither escapes the root
  nor produces an invalid ref name.
- [ ] Cancelling mid-run terminates agent processes, applies the retention
  policy, and emits `workspace_released` for each worktree.
- [ ] `source_workspace_changed` is emitted when a fake agent writes to the
  source path by absolute path, and is absent otherwise.
- [ ] F1.8 `changed_files_scope` in `deny` mode evaluated inside a worktree
  flags an out-of-scope file in that worktree and ignores the other unit's
  files.
- [ ] `go test -race ./...` and `make check` pass; new events round-trip through
  serialization and old-schema fixtures still load.

## Required tests

- Unit: effective-workspace resolution and identity; safe naming of
  worktree/ref names from hostile node IDs; retention policy table; conflict
  detail bounds; semantic-hash stability with and without `isolation`; event
  payload strictness and round-trip.
- Integration (temporary Git repositories, fake adapter, explicit barriers, no
  sleeps): the parallel same-file case, scoped retry with real files,
  integration order and determinism, conflict, exhausted unit, cancellation,
  cleanup failure, dirty-source preflight, source-unchanged guard.
- Adapter compatibility: `gitstate.Capture` and the Codex adapter's workspace
  checks accept a linked-worktree root (where `.git` is a file) and reject
  nothing that a normal checkout accepts.
- CLI/e2e: built binary with a fake installed Codex, JSON result contains base
  SHA, refs and retained paths; exit codes 0, 4 and preflight failure.
- After merge (authorized, not part of CI): a real installed-Codex run in a
  disposable repository recorded under `docs/validation/`, specifically to
  verify that Codex's workspace-write sandbox can operate in a linked worktree
  whose Git metadata lives in the source's `.git` (Q7).

## Security / trust considerations

- Untrusted: graph content (node IDs, workspace, `isolation`), repository
  content and `.gitattributes`/Git config, agent output, environment values.
- All Git calls reuse the controlled invocation of `internal/gitstate`:
  `/usr/bin/git`, structured argv, minimal environment, no system/global config,
  `core.hooksPath=/dev/null`, `core.fsmonitor=false`, bounded time and output.
  `git worktree add` and the snapshot commit must not run repository hooks.
- Checkout can execute repository-configured filter/smudge drivers (for example
  LFS). ADR-0024 must choose between disabling filters for runtime-created
  checkouts and rejecting repositories that configure them (Q7).
- Never follow symlinks when creating or removing worktrees; remove only paths
  the runtime created in this run (tracked by ID), never a path derived from
  graph text. Never delete the source workspace.
- Paths in events are local absolute paths and are not secrets; they must not be
  sent anywhere implicitly. Secrets are never written to worktree names, refs,
  commit messages or events.
- A worktree is not a sandbox. Documentation and CLI output must say so wherever
  isolation is described; the source guard (req. 19) only detects, it does not
  prevent.
- Disk: each isolated node materializes a full checkout. Concurrency is already
  bounded by `--max-concurrency`; no additional quota in v1, documented.

## Observability

Events (typed, bounded, deeply copied, outside progress limits): base SHA and
effective workspace at `workspace_prepared`; unit commit SHA, integration commit
SHA and changed-path count at `workspace_integrated`; conflicting paths with an
omitted count at `workspace_conflict`; retained/removed with reason and any
cleanup error class at `workspace_released`; bounded paths at
`source_workspace_changed`. Correlated by run ID, node ID, node run ID and,
where relevant, attempt ID. The order for an isolated accepted unit is:
`gate_check` -> `return_envelope` -> `attempt_finished` (unchanged) ->
`workspace_integrated`. Operational failures emit no verdict and no envelope.

Exact payloads, bounds and the closed `reason` vocabulary are in ADR-0024
section 10 and `internal/events/workspace.go`. In short: paths are repository
relative, sorted, unique, at most 64 per payload and 1024 bytes each, with
anything unrepresentable counted in `omitted`; `source_workspace_changed` with
`indeterminate: true` records a failed inspection and carries no paths (spec
amendment accepted in the plan, decision 4).

## Open questions

**Resolved:** the product owner accepted the recommended default of every
question below (2026-11-16); the decisions are recorded in ADR-0024. Where the
ADR is more specific than the text here (Q5 default root, Q7 filter drivers are
rejected rather than disabled, Q9 schema number assigned by merge order), the
ADR prevails. The Q7 Codex-sandbox spike passed (`docs/validation/F3.1-codex-worktree-spike.md`); the agent can run read-only Git but cannot stage or commit in its worktree.
Original text kept for traceability; recommended default in bold.

1. **Do downstream isolated nodes see upstream file changes?** v1 as written:
   no, every isolated node starts from the run's base SHA and data flows only
   through ports. **Alternative:** base = run base merged with accepted upstream
   units (transitive edges). This is the right long-term semantics for
   plan -> implement -> fix pipelines but adds merge-before-start and more
   conflict paths. Recommend **defer to a follow-up (F3.1b)** and keep this spec
   to parallel siblings.
2. **Dirty source workspace.** **Fail preflight (as written).** Alternative:
   an explicit opt-out that warns and proceeds from HEAD.
3. **How does the result reach the user's branch?** **Integration ref only; the
   user merges manually (as written).** Alternative: an explicit
   `--apply-to-source` that fast-forwards or merges into the checked-out branch;
   this touches the user's tree and needs its own consequence analysis.
4. **Shell, Gate and Human nodes.** Standalone Shell/Gate nodes run in the
   source cwd and therefore do not see the integrated result, so the full
   "workers -> test gate" pipeline only works when the gate is embedded in each
   worker's loop. **Recommend deferring `isolation` for Shell nodes** (including
   F1.6a loops) to a follow-up unless the thesis demo needs it.
5. **Default worktree root and orphan handling.** Align with the F2.9 run-store
   location and the OS state/cache directory. Is a minimal
   `agentplane workspaces list|prune` in scope for v1 or left to F3.11?
   **Recommend list only if cheap; prune with F3.11.**
6. **Setting granularity.** Per Agent node (as written) versus a graph-level
   default. **Per node**; revisit when templates (F2.12) need a default.
7. **Checkout side effects and the Codex sandbox.** Filter/smudge drivers (see
   Security), and whether Codex's workspace-write sandbox can use a linked
   worktree whose gitdir is outside the writable root. Needs a short spike
   before ADR-0024 is accepted; if it fails, fall back to an isolated
   `git clone --local` style checkout (same lifecycle and integration contract).
8. **Untracked/ignored build inputs** (for example `node_modules`) are absent
   in a fresh worktree, so tests inside the worktree may fail. v1 documents the
   limitation; a per-node setup step is a possible follow-up.
9. **Event schema number** coordination with ADR-0023 (recorded run values).

## Out of scope for this iteration

Downstream visibility of upstream files, Shell/Gate/Human isolation, applying
results to the user's branch, semantic merge, orphan auto-cleanup, resume,
process/filesystem sandboxing, quotas, Windows, desktop presentation of the
new events, and any remote or managed execution.
