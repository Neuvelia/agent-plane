# F2.2 - Node Inspector

**Status:** draft
**Priority:** P0
**Target phase:** Phase 2 - Local IDE
**Depends on:** F2.1 (document API, operations, canvas), F2.4 (diagnostics in the editor)
**ADR:** ADR-0020 (operations), ADR-0021 (field descriptors, single validation path), proposed
**Plan:** `docs/superpowers/plans/2026-11-14-graph-editor.md` (slice E4)

## Problem

A node's contract (ports, configuration, loop and embedded gate) can be changed only by editing YAML by
hand, and each node type has its own strict rules that today surface only at run start. The Tarmind
inspector design shows fields that schema v0 does not have; building it literally would add settings the
engine rejects.

## Goal

Selecting a node shows one inspector with sections for inputs, execution, loop and gate, and outputs. Its
fields are generated by the sidecar from the same Go definitions the executors validate against. Every
change is an operation on the file, and validation messages appear next to the field they concern.

## Non-goals

- Fields the engine does not define: `foreach`, `depends_on`, timeouts, permission models, adapter settings
  beyond the v0 agent keys, "version" counters. Anything the descriptors do not list is preserved and shown
  under "Advanced", never invented.
- New node types or schema changes; templates (F2.12); a form builder for plugins.
- Previewing runtime values (F2.3, run values). Here "resolved input preview" means the declared source of
  each input, not a value.
- Editing graph-level inputs, outputs and edges (F2.3) or creating nodes (F2.1).
- Hand-written, per-type TypeScript validation.

## Functional requirements

### A. Descriptors and operations (Go)

1. **Field descriptors** are returned by `POST /graphs/open` and `/graphs/edit` for the node types present in
   the graph (and for all four types on request, so the toolbar can show starters). They are generated from
   the Go code that the executors use, not written by hand in the renderer. A descriptor is:
   `{id, key, kind, required, default?, enum?, min?, max?, max_bytes?, item?, fields?, requires?, excludes?,
   locked?}` where `id` is a stable identifier used for help text and tests (for example
   `shell.config.command`), `key` is the YAML key, and `kind` is one of `string`, `text`, `bool`, `int`,
   `enum`, `list` (of `item`), `map` (string to string), `input_name` (a declared input of this node),
   `path_list`, or `group` (nested `fields`). `requires`/`excludes` express cross-field rules such as the
   agent's "exactly one task source".

   Shape details fixed by slice E4.1 (`internal/fields`):
   - Additional members: `kind: scalar` (a string, boolean, integer or null, never a float; the gate's
     `expected`), `max_items`, `format`, `input_types` and `input_required`. `format` is one of `nonempty`
     (not the empty string), `not_blank` (a non-space character), `absolute_path`, `clean_absolute_path`,
     `env_name` (not empty, no `=` or NUL, not the reserved `AGENTPLANE_ATTEMPT` in any case),
     `relative_path` (portable, inside the workspace, no `..`) or `json_scalar` (the text of one JSON scalar
     or null). For `input_name` (and for an `item` of that kind), `input_types` lists the allowed port types
     and `input_required` says the port must be required. For a `map`, `input_types` means its keys are
     declared inputs of those types, and `item` describes its values.
   - A rule is `{key, equals?}` (a key of the same config mapping, with that string value or `"true"`/
     `"false"`; no `equals` means "present") or `{input}` (a declared input port). `requires` lists rules
     that must all hold; `excludes` lists rules of which none may hold. A `required` field with `excludes`
     is satisfied by exactly one of itself and its excluded alternatives.
   - A `group` without a `key` holds keys of the parent mapping; it carries the keys of one Gate kind, with
     `requires: [{key: kind, equals: KIND}]`.
   - `locked` is `{value, reason}`.
   - Allowed outputs are separate port descriptors `{name, type, required?, requires?}`.
   - Each validator owns its descriptors and derives its accepted keys from them: `shell.ConfigFields`,
     `agent.ConfigFields`, `gate.ConfigFields` and, in `graph`, `HumanConfigFields`, `LoopFields`,
     `LoopProducer` and `LoopGateKinds`, with `OutputPorts`/`HumanOutputPorts` for outputs. The Gate
     executor accepts all four kinds; which kinds a standalone Gate or a loop offers is decided where the
     node types are composed (shell loop: three; agent loop: four; standalone: see Open questions).

   Response shape fixed by slice E4.3 (`internal/api/inspector*.go`, catalogue in
   `cmd/agentplane/catalogue.go`):
   - `open` and `edit` accept `all_node_types: true` to receive every type; otherwise only the types used
     in the graph. The response always has `node_types`, an object keyed by type (empty when the sidecar
     has no catalogue): `{config: [descriptor], outputs: [port descriptor], outputs_locked, loop?}` where
     `loop` is `{fields, gate, gate_kinds}` (`fields` holds `max_attempts`, `gate` the embedded Gate's
     descriptors narrowed to `gate_kinds`). A standalone Gate's `kind` enum and groups are narrowed to
     the three standalone kinds the same way. Types that cannot loop have no `loop`.
   - When the text parses, `node_info` is keyed by node id: `{known_type, advanced, loop_advanced?,
     independent_of}`. An `advanced` entry is `{key, yaml, reason}` with `reason` `unknown` (the
     descriptors do not accept the key for this config, which includes a key of another Gate kind) or
     `shape` (the value does not fit the field's control, for example a list where a string is
     expected). `yaml` is the value encoded from the parsed tree with its own style, nesting and
     comments; the file is not re-encoded. `loop_advanced` is the same for the loop's Gate config. A
     node of an unknown type has `known_type: false` and every config key in `advanced`.
   - The API package composes nothing itself: `api.Server.NodeTypes` is built in the composition root
     from the validators' exports, and the DTOs copy descriptors field by field.
2. **Field sets for schema v0** (the descriptors must equal this; the tests pin it):
   - **shell** (`config`): `command` (string, required), `args` (list of strings), `cwd` (string),
     `env_allowlist` (list of environment names), `env` (map of name to string), `input_env` (map of declared
     string input to environment name), `stdout_json` (bool). Allowed outputs: `stdout`, `stderr` (string),
     `exit_code` (number), and `json` (json) only when `stdout_json` is true.
   - **agent** (`config`): `adapter` (string, required; the sidecar advertises known adapter ids and free text
     is accepted, validated at run preflight), `workspace` (absolute path, required), `task` (text) or a
     declared string input named `task` (exactly one source), `allowed_paths`, `context_refs`,
     `environment_refs` (lists of non-empty strings). Allowed outputs: `summary` (string); `changed_files`,
     `artifacts`, `raw_metadata`, `usage` (json).
   - **gate** (`config`): `check_id` (non-empty, at most 256 bytes), `kind` (enum `command`, `json_predicate`,
     `reported_file_scope`) and the fields of the chosen kind exactly as in `docs/graph-spec.md` (Gate node):
     `command` (`command`, `cwd`, `left_input`, `right_input`), `json_predicate` (`input`, `field` list,
     `operator` `eq`|`ne`, exactly one of `expected` or `expected_json`), `reported_file_scope` (`input`,
     `allowed_paths`). Allowed output: `verdict` (string) only.
   - **human** (`config`): `prompt` (text, at most 1024 bytes), `context_inputs` (at most 8 declared string
     inputs). Outputs are locked to `decision` (string, required). A human node has no loop section.
   - **loop** (shell and agent only): `max_attempts` (int 1-10, default 3) and an embedded gate whose kinds are
     `command`, `json_predicate`, `reported_file_scope` and, for agent producers only, `changed_files_scope`
     (`mode` `warn`|`deny`, `workspace`, `allowed_paths`, `input`); the gate's declared inputs; and
     `bindings` from `candidate.outputs.PORT` or `node.inputs.PORT` to `gate.inputs.PORT` of equal type with
     unique targets. An agent loop requires explicit `allowed_paths`.
   - **ports** (all types): input and output ports with `type` (`string`, `number`, `boolean`, `json`,
     `artifact_ref`) and `required`; port names follow the identifier grammar.
3. **Operations added by this spec** (`ops_version: 1`):

   | `op` | Fields | Effect |
   | --- | --- | --- |
   | `set_config` | `node`, `path` (list of keys), `value` | Sets a config value at the path, creating intermediate maps; the value is a JSON scalar, list or object; a set value that equals the current one changes nothing |
   | `unset_config` | `node`, `path` | Removes the key and the parent maps the removal empties (never `config` itself); a path that holds nothing changes nothing |
   | `add_port` / `update_port` / `remove_port` | `node`, `direction` (`input`/`output`), `port`, `type`, `required`; `update_port` also `new_port` | Edits a port; `remove_port` also removes edges, graph input bindings, graph outputs, loop bindings and `context_inputs`/`input_env`/gate references to that port; a rename (`new_port`) updates all of them; `update_port` refuses a type change that would create a binding type mismatch |
   | `set_loop` | `node`, `max_attempts` (absent: the default), `gate` (`inputs`, `config` object), `bindings` | Sets the whole `loop` block; refused for a node that cannot loop and for bindings the validator would refuse |
   | `clear_loop` | `node` | Removes the `loop` block; no loop changes nothing |
   | `set_units` | `units` (list of node ids; empty clears) | Sets or clears the top-level `units`; a missing or repeated id is refused |

   The port name travels in `port` because `name` is `set_name`'s field in the same operation object.
   Refusals use the F2.1 error shape with the codes `E_EDIT_CONFIG_PATH`, `E_EDIT_VALUE_INVALID`,
   `E_EDIT_PORT_INVALID`, `E_EDIT_PORT_EXISTS`, `E_EDIT_PORT_NOT_FOUND`, `E_EDIT_PORT_TYPE_CONFLICT`,
   `E_EDIT_LOOP_INVALID` and `E_EDIT_UNITS_INVALID` (slice E4.2).

4. **Unknown keys are preserved.** Config keys the descriptors do not list are returned as `advanced`
   entries (key and the YAML snippet of their value) and survive every operation unchanged.
5. **Validation** for the inspector is the single validation path (F2.4, requirement 1). Diagnostics are
   matched to fields by the diagnostic's `path` when it has one (`nodes.ID.config.command`), otherwise they
   show at node level.

### B. Inspector (renderer)

6. **Layout.** A card for the selected node with the node id (renamable), its type, a status pill for its
   diagnostics, and sections **Inputs**, **Execution**, **Loop and gate** (shell and agent only),
   **Outputs**, and **Advanced**. Sections are generated from the descriptors; a type's section list is not
   hard-coded.
7. **Fields.** Each descriptor renders the matching control (text, text area, switch, number, select, list
   editor, key/value editor, input picker). Required fields are marked; `locked` fields are shown read-only
   with the reason; `requires`/`excludes` show the cross-field rule as inline help. Labels and help texts come
   from PL/EN catalogues keyed by the descriptor `id`.
8. **Editing model.** A committed change (blur, Enter, or a toggle) sends one `edit` batch; typing alone does
   not. The returned text replaces the draft, so the YAML view and the canvas update, and the same undo
   stack applies. An invalid value is **saved as typed** (the file is the truth) and shown with its
   diagnostic next to the field; it is never silently dropped or "fixed".
9. **Input sources.** Under Inputs, each input shows where it comes from: `NODE.outputs.PORT` of an edge, a
   graph input binding, a literal (`config.task`), or "unbound" with the required/optional mark. This is a
   declaration, not a value.
10. **Ports.** Add, rename, retype, toggle required and remove ports. Removing or retyping a port that has
    edges or references shows what will change before it applies. Output names offered are limited to the
    type's allowed outputs.
11. **Loop and gate.** Enabling the loop adds a starter block (`max_attempts` 3, a `json_predicate` gate with
    one declared input and one binding from a candidate output when the producer has a `json` output;
    otherwise the person is asked to pick the producer's candidate output first). The binding rows enforce
    equal types and unique targets by offering only compatible choices.
12. **Advanced.** Lists unknown config keys with their value text; each can be edited as a YAML scalar or flow
    value (parsed by the server) or removed.
13. **Parallelism note.** Next to the node, "runs independently of: ..." lists the nodes with no data
    dependency path to or from it, computed by the engine from the edges (deterministic, no ordering edges
    exist in v0).
14. **Keyboard and screen readers.** Sections are headings; every control is native and labelled; list and map
    editors have add and remove buttons with names; validation messages are associated with their field
    (`aria-describedby`); the inspector is reachable without a pointer from the node list.
15. **States and stories.** Loading, error, read-only (anchor file or YAML error) and empty (nothing
    selected) states. Stories (EN and PL, axe clean) for each node type, a loop with a gate of each kind, a
    field with a diagnostic, the Advanced section, the read-only state.

## Data / API contracts affected

Descriptors and the operations above join the `open`/`edit` responses and the operation vocabulary
(ADR-0020, ADR-0021). Graph schema v0, events and the run store are unchanged. No new diagnostic codes.

## Failure behavior

- An operation that cannot apply (unknown node, invalid port name, a binding that cannot be made type-correct)
  is refused as a whole with the same structured error as F2.1; the inspector shows it at the field.
- A descriptor id with no help text in a language falls back to English, then to the key; a test makes the
  gap visible.
- A node whose type the sidecar does not know (a newer graph) shows type and Advanced only, with a notice.
- A config value the descriptors cannot represent (for example a list where a string is expected) is shown
  as raw YAML in Advanced and is not overwritten.

## Acceptance criteria

- [x] **Descriptors equal the executors:** a Go test builds a valid and an invalid config for every descriptor
      field and shows `ValidateNodeConfig` accepts exactly what the descriptors allow (required, enum, bounds,
      cross-field rules), for shell, gate, agent, and the human and loop rules in `graph.Validate`.
      (E4.1: `internal/fields/fieldstest` derives both directions from the descriptors; each package's
      `fields_test.go` runs it.)
- [x] **No drift:** adding a config key to an executor without a descriptor fails a test (every key the
      executors accept appears in a descriptor). (E4.1: executors derive accepted keys from their
      descriptors, so an undescribed key is refused, and each key set is pinned to requirement 2.)
- [ ] **File is the truth:** every inspector change is an operation; after a series of edits the YAML text
      equals what the operations produced, comments and order are preserved, and the semantic version equals
      the typed prediction (Go).
- [ ] An invalid configuration can be saved but is never silent: the field shows its diagnostic and Run is
      disabled (e2e).
- [x] Port edits: `remove_port` removes every reference to the port in one batch and `graph.Validate` reports
      no dangling reference; `update_port` refuses a type change that would create `E_BINDING_TYPE_MISMATCH`
      (Go). (E4.2: `internal/graph/edit/inspector_test.go`.)
- [ ] Loop and gate: each gate kind can be configured from the inspector to a graph that `agentplane graph
      validate` accepts; invalid bindings (unequal types, duplicate target, no candidate output) are not
      offered and are refused if sent (Go and e2e). (E4.2 covers the Go part: each kind configured by
      operations passes `validateGraph`, `cmd/agentplane/inspector_ops_test.go`; invalid bindings are refused.)
- [x] Unknown config keys, including nested ones, survive 20 random operations unchanged (property test).
      (E4.2: 50 seeds of 20 applied operations each, `inspector_property_test.go`.)
- [ ] Human node: the inspector offers no loop and no output editing; `context_inputs` lists only declared
      string inputs and at most 8 (Go and renderer).
- [x] The independence list equals a reference computed from the edges in the test for the corpus graphs.
      (E4.3: `graph.IndependentNodes` against a Warshall closure for `.agents/graphs/*.yaml` and small
      shapes, `internal/graph/independence_test.go`; served as `node_info.*.independent_of`.)
- [x] Every descriptor `id` has a help text in EN and PL (catalogue test). (E4.4:
      `desktop/test/inspector-text.test.ts` against `test/fixtures/node-types.json`, which
      `cmd/agentplane/catalogue_test.go` pins to the served catalogue.)
- [ ] Keyboard only: change a shell command, add an argument and an output port, enable a loop and save, with
      no pointer use (e2e).
- [ ] No per-type validation is written in TypeScript (grep test as in F2.1); stories exist for every state in
      requirement 15; `npm run check`, `make check`, `make desktop-e2e` pass; axe is clean in both languages.

## Required tests

- **Go:** descriptor generation and the executor-equality test, the no-drift test, each operation (success and
  failures), preservation of unknown keys (property test), loop and gate rules, independence computation.
- **Renderer unit:** field-to-operation mapping, diagnostic-to-field matching, port-edit previews.
- **e2e:** shell, agent, gate, human and loop editing against real graphs; keyboard path; invalid config.
- **Stories:** as above.

## Security / trust considerations

Config values are untrusted text (commands, paths, environment names). They are shown and edited as text and
never executed, expanded or resolved by the editor. Raw secrets must not be typed into config: the Advanced
section and the environment fields show a fixed warning that environment values belong in `env_allowlist` and
`environment_refs`, not in the graph. The agent `workspace` and shell `cwd` are strings the editor does not
open or read.

## Observability

Editing emits no run events. Validation results are the engine's.

## Open questions

- The list of adapter ids the sidecar advertises (the sidecar may not select an adapter at all in `serve`);
  until decided, the field accepts free text and shows known ids as suggestions when available.
- Whether `changed_files_scope` mode defaults to `warn` or `deny` in the starter (this spec proposes `warn`,
  the non-blocking mode).
- Found in E4.1: the Gate executor's static check accepts `kind: changed_files_scope` on a standalone Gate
  node, and no graph rule refuses it there; this spec offers only three kinds for a standalone Gate. Decide
  whether the engine should refuse it (a separate engine change) or the inspector simply not offer it.
  E4.3 takes the conservative option: the catalogue does not offer it (the standalone `kind` enum has three
  kinds); a graph that already uses it is still read and validated as before. The engine question stays
  open.
- Found in E4.1: a Shell node's declared outputs (`json` requiring `stdout_json`, no other names) are checked
  when the node runs, not by `ValidateNodeConfig`, so such a mistake reaches no diagnostic before Run. The
  descriptors state the rule; whether static validation should report it is an engine decision outside F2.2.
- Found in E4.4: no engine diagnostic carries a field path today. Executor errors use `nodes.ID.config` (or
  `nodes.ID.loop.gate`) and loop rules `nodes.ID.loop`, so the inspector shows them at the top of the
  Execution or Loop section, and port diagnostics (`nodes.ID.inputs.P`) at the port. Field-level placement
  works by path as soon as a diagnostic names a key; adding such paths is an engine change outside F2.2.
- Decided in E4.4 (conservative): Advanced values are replaced by typing JSON (a flow value YAML also reads)
  or plain text, parsed in the renderer (`JSON.parse`, else the text as a string) and sent with `set_config`.
  No operation takes YAML text, and adding one would widen the vocabulary; a server-side YAML parse can be
  added later as an operation of its own.
- Decided in E4.4: `POST /graphs/validate {text|grant}` also returns `node_types` and `node_info`, because
  the editor validates typed text through that route and the inspector must follow the YAML view.
- Decided in E4.4: loop binding choices are the engine's answers to previewed `set_loop` batches (as
  `can_connect` is for edges), so the renderer compares no port types; refused choices are not offered.

## Out of scope for this iteration

Permissions, timeouts, retries beyond `max_attempts`, additional gate kinds, plugin forms, templates, value
previews.
