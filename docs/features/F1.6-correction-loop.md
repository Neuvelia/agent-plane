# F1.6 - Correction Loop + maxAttempts

**Status:** implemented (ADR-0014)
**Priority:** P0
**Target phase:** Phase 1 - Agent Loop
**Depends on:** F1.1, F1.4, F1.5

## Problem

A red deterministic check currently ends the path. A coding agent needs a
bounded opportunity to correct only its own failed result using the actual
Check Result as feedback.

## Goal

Execute `produce -> check -> correct` inside one logical unit with a finite
attempt budget, trace each attempt, and release only a green accepted output
to downstream nodes.

## Non-goals

- Batch or sibling-unit retry (F1.7), adaptive budgets, cross-unit replanning,
  workspace isolation or persistence/recovery.

## Functional requirements

1. Author a finite positive `max_attempts`; omission defaults to 3. Reject
   zero, negative and unreasonable values before execution. A bounded upper
   limit must be fixed in the loop ADR.
2. The first produce call is attempt 1. Each correction creates a new unique
   `AttemptID` under one `NodeRunID`; the run ID and graph version remain
   stable. Prior attempt trace is immutable.
3. A red Check Result is passed verbatim as typed feedback to the next agent
   attempt with the original task and explicit intended scope. No retry
   occurs for an execution error category that the loop policy excludes.
4. If a Gate is green, accept that attempt's declared outputs once and make
   them available to downstream bindings. Red attempt outputs remain
   unavailable to downstream nodes.
5. At budget exhaustion, end in `failed_needs_intervention` (or a documented
   compatible terminal state), preserve every Check Result and skip dependent
   nodes. Cancellation stops further attempts immediately.
6. Define the loop-to-Gate graph contract and attempt event/state semantics
   in an ADR before implementation. A loop is inside a node/unit; it must not
   create a cycle in schema-v0 DAG edges.

## Data / API contracts affected

Loop configuration, Agent correction input, attempt identity and state,
accepted-output publication and event schema. The ADR must describe how the
Gate selected by a loop consumes candidate output without weakening explicit
data dependencies.

## Failure behavior

Invalid budget, missing Gate, ambiguous check binding and unsupported agent
capability fail preflight. A red final attempt yields intervention state, not
an unbounded retry. Process errors and cancellation retain their distinct
causes. Accepted data is never replaced by a red candidate.

## Acceptance criteria

- [x] With no configured budget, a permanently red fake agent runs exactly
      three attempts and terminates needing intervention.
- [x] Explicit budgets of 1 and 2 produce exactly that many attempts; invalid
      budgets fail before a provider starts.
- [x] A red then green sequence yields two distinct attempt IDs under one
      node-run ID; downstream executes once with only green output.
- [x] Each attempt's input, Check Result and terminal verdict can be found in
      trace without overwriting prior attempts.
- [x] Cancellation between attempts prevents a later attempt; cancellation
      during execution propagates to the adapter.
- [x] `make check` and `go test -race ./...` pass.

## Required tests

- Unit: budget validation, attempt state transitions, eligible error
  categories and feedback construction.
- Integration: red/red/red, red/green, single-attempt green, cancellation and
  downstream visibility using deterministic fake adapters and gates.
- CLI/e2e: serialized trace shows each attempt and terminal intervention.

## Security / trust considerations

Feedback contains untrusted check evidence. Bound and redact it before
passing it to a provider. Attempts reuse an explicit workspace but F1.6 does
not isolate or roll back filesystem edits; do not claim an accepted repository
state until F3.1 defines workspace isolation.

## Observability

Emit attempt started/finished facts with run/node/attempt IDs, linked Check
Results and the final accepted or intervention state. No private reasoning.

## Resolved implementation decisions

ADR-0014 defines optional node-level loop with one embedded Gate and explicit
candidate.outputs/node.inputs to gate.inputs bindings, including a required
candidate dependency. Default3 attempts, integer1–10; explicit null invalid.
Only valid red retries. Exhaustion uses failed state with needs_intervention
failure kind/CLI4. Runtime owns attempts/publication; feedback is the same
sanitized CheckResult with original task/intended scope. Trace input is a
bounded fingerprint/redacted metadata representation, not raw replay input.
Schema6 preserves schema5 CheckResult lookup. No rollback/isolation/envelope.

## Out of scope for this iteration

F1.7 sibling-unit return envelope, F1.8 changed-files enforcement, F3.1
worktrees and F3.3 recovery.
