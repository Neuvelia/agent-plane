# F3.9c - Requested permissions in the desktop (inspector section and pre-run view)

**Status:** draft (ADR-0039 proposed; not implemented; blocked on F3.9)
**Priority:** P0 (completes roadmap F2.2 "permissions" section and F3.9 acceptance 2)
**Target phase:** Phase 3 - Local Production Ready
**Depends on:** F3.9 (permissions report type and `graph permissions` implementation, ADR-0029), F2.2 (inspector), F3.8 (secret names only)
**ADR:** ADR-0039 (proposed)
**Closes:** issue #184; replaces the unnamed follow-ups in `F2.2-node-inspector.md` and `F3.9-execution-policy-v0.md`

## Problem

F3.9 ships a CLI permissions report but the desktop shows nothing about what a run will be allowed to do. The
roadmap promises a permissions inspector section and a view of requested permissions before a run.

## Goal

A person opening a graph sees, per node and for the whole graph before pressing Run, which permissions are
requested, where each comes from, which secrets are assigned (names only) and whether the current platform can
enforce, only detect, or not observe each one. In the first slice the view is read-only.

## Non-goals

- Editing `policy` in the UI (slice S3, below, and only after the owner accepts ADR-0039).
- Any enforcement, probe or policy logic in TypeScript.
- Changing the F3.9 report schema, graph schema or event schema.
- Blast-radius approval, organization policy (F5.9, F6.4).
- Showing secret values, ever.

## Functional requirements

### Slice S1 - read-only route (Go)

1. A loopback route returns the F3.9 permissions report for submitted graph text. It calls the same Go function as
   `agentplane graph permissions --json`; there is one implementation.
2. Request carries the graph text and an optional policy mode `audit|enforce`. Response is the report plus the
   platform probe result used. The route is read-only and needs no write trust.
3. Invalid graph: the route returns the validation diagnostics, not a partial report.

### Slice S2 - inspector section and pre-run panel (desktop)

4. The node inspector shows a **Permissions** section for Shell and Agent nodes: each requested permission, its
   source (graph default or node override), assigned secret names and enforcement state from the ADR-0029
   closed vocabulary. Gate and Human nodes show "no configurable permissions".
5. The run-start flow shows a pre-run panel listing every node's permissions and states and any preflight
   blocker the report predicts. The panel does not block Run by itself.
6. The text states audit versus enforce and never labels an audit-mode permission as applied.
7. If the sidecar does not offer the route, the section and panel are hidden.

### Slice S3 - editing (separate decision gate)

8. Editing uses descriptor-driven graph edit operations (ADR-0020), validated by the engine. Start only after
   S1 and S2 are accepted; if it needs an operation outside the versioned vocabulary, open a new ADR.

## Data / API contracts affected

One additive read-only loopback route. No graph, event or schema change. Report type owned by F3.9.

## Failure behavior

Report unavailable or graph invalid: show diagnostics or hide the panel; never show a guessed state. A probe
failure is shown as `unenforceable`.

## Acceptance criteria

- [ ] Route output for a fixture graph is byte-equal to `agentplane graph permissions --json` for the same graph and mode (Go test).
- [ ] The route response and every UI string contain no secret value (byte scan with a sentinel secret).
- [ ] A graph without `policy` shows every permission as `unrestricted (not declared)` (the F3.9 report wording) with platform states; semantic hash, events and CLI output are unchanged.
- [ ] Selecting a Shell node with `paths.write` shows source, permission and state; on a platform where the probe reports unavailable, the state reads `unenforceable` (renderer test over a recorded report, no renderer-computed states).
- [ ] An audit-mode report never renders as applied (renderer test; mirrors `TestAuditPermissionsAreNeverApplied`).
- [ ] The pre-run panel lists a predicted `policy_unenforceable` blocker for `enforce` on a platform where it applies, before any process starts.
- [ ] A sidecar without the route hides the section (no error, no empty section).
- [ ] An architecture test shows the renderer imports no policy evaluation code.

## Required tests

- Unit: route handler, report equality with the CLI, secret scan.
- Renderer: section states, audit label, hidden when unsupported.
- Integration: open fixture graph, call route, assert pre-run panel contents.

## Security / trust considerations

Secret names are shown, values never. The report is derived from graph text the user supplied; the route does not
read the filesystem beyond the platform probe.

## Observability

No events. The route is read-only; no run is created.

## Open questions

- Whether S3 editing ships with Phase 3 or later (owner decision).
- Whether the pre-run panel should require acknowledgement in enforce mode (product decision; ADR-0039 recommends no).

## Out of scope for this iteration

Editing, policy language, blast radius, Windows AppContainer (F3.9b).
