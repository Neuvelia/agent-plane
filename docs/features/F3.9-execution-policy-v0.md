# F3.9 - Permissions / Execution Policy v0

**Status:** draft (ADR-0029 proposed, shared with F3.8). Split on 2026-11-26 (product owner): **F3.9a** (tasks T1-T7,
verifiable locally on Linux) is implemented first; **F3.9b** (T8-T11: Landlock, network namespaces, Codex sandbox
pinning, Windows) follows once its spikes and a working CI job exist. See "Implementation plan and acceptance map".
**Priority:** P0
**Target phase:** Phase 3 - Local Production Ready
**Depends on:** F1.2 (Codex adapter), F3.1 (workspace isolation, ADR-0024), F3.8 (secret references)
**Closes:** the confinement that F1.8 (scope check) and F3.1 (worktrees) explicitly defer: both state they are
not sandboxes and name F3.9 as the place for confinement.

## Problem

Tarmind (in code today: agentplane) runs shell commands and coding agents with the full authority of the user.
What exists today limits intent or detects after the fact, but nothing prevents:

- F1.8 `changed_files_scope` compares Git-observed changes with `allowed_paths` after the node ran. It cannot
  prevent a write and cannot see a write outside the repository.
- F3.1 gives an Agent its own worktree. An absolute path still reaches the source checkout; ADR-0024 says so.
- `shell` nodes run any command, with any `cwd`, with network. `env_allowlist` and `environment_refs` copy
  ambient variables. There is no way to say "this node may not use the network" or "this node may only run
  `go`".
- Agent `allowed_paths` is intent only (graph-spec: "identify intent and references only"); the Codex adapter
  runs `--sandbox workspace-write` but AgentPlane neither configures nor verifies what that permits.

## Goal

A graph can state the permissions each node needs (write paths, network, shell, commands, secrets). Preflight
shows exactly what the graph requests and, for the machine it will run on, which requests can be prevented,
contained, delegated, detected or only recorded. In enforce mode a request that cannot be enforced stops the run
before it starts, and a violation that occurs blocks the node with evidence. In audit mode nothing is blocked,
but every observable violation is recorded. The policy and secret assignment are evaluated by one pipeline, so a
secret can never reach a node the policy does not admit.

## Non-goals

- A policy language, organization policies, approval chains (F5.9, F6.4). v0 has four fixed permissions.
- Read confinement. An enforced node can still read any file the user can read, including other credentials.
- Confining descendants of the node's own command. `commands` constrains the process the runner starts; what that
  process spawns is not constrained in v0 on any platform.
- Network filtering by host or port; only on/off.
- Blast-radius levels and human approval by consequence (separate feature).
- Sandboxing the model traffic of an agent adapter. The adapter's own calls to its provider are not restricted;
  `network: off` for an Agent means the commands the agent runs.
- New Go dependencies. All mechanisms are standard library (`syscall`, `os/exec`), the Linux kernel, the
  Windows API reached through `syscall.NewLazyDLL`, or tools the adapters already rely on.
- Implementing macOS enforcement. macOS is reported as unenforced except where Codex enforces it itself.

F1.8 semantics reused: patterns are workspace-relative (`FormatRelativePath`), `**` globs, a similar prefix
(`internal/runtime2/`) never matches `internal/runtime/**`, untracked, deleted and renamed paths all count,
results are sorted, and an undeterminable Git state fails `deny` closed. F3.1 semantics reused: the graph never
contains a worktree path; the runtime derives the effective workspace and points the Agent and its embedded Gate
at it; paths are confined and symlinked or pre-existing targets are refused.

## Functional requirements

### A. Policy surface

1. A graph may declare an optional top-level `policy` mapping and an optional per-node `config.policy` mapping:

   ```yaml
   policy:
     mode: audit            # audit | enforce, default audit
     defaults:
       network: off
   nodes:
     build:
       type: shell
       config:
         command: go
         args: [build, ./...]
         policy:
           paths: {write: ["bin/**"]}
           commands: [go]
           shell: on
   ```

   Keys (all optional):
   - `paths.write`: list of workspace-relative patterns in F1.8 syntax. The empty list means no writes.
   - `network`: `on` or `off`.
   - `shell`: `on` or `off`. `off` means the node may not run an external process through the runner.
   - `commands`: list of command names or absolute paths the node's own process may be.
   Unknown keys, wrong types and absolute or escaping patterns (`..`, drive letters, UNC, alternate data streams,
   NUL) fail validation naming the node and key.
2. An absent key requests no restriction and is shown as `unrestricted (not declared)` in the permissions report.
   A graph without any `policy` behaves and hashes exactly as on `main`; no policy event is emitted.
3. Graph `defaults` apply to every node that does not set the key. A node may set a key to a stricter value
   (narrower path set by subset, `network: on` to `off`, `shell: on` to `off`, smaller command set); a node value
   that widens a default fails validation naming the node. Defaults cannot grant secrets (F3.8-4).
4. `mode` is `audit` or `enforce`. The runner may set a mode stronger than the graph (`agentplane run --policy-mode
   enforce`); a graph can never lower the mode the runner chose. Effective mode is the stronger of the two.
5. `paths.write` patterns are relative to the node's effective workspace: the F3.1 worktree when the node is
   isolated, otherwise the node's `workspace` (Agent) or `cwd` (Shell, resolved once at preflight against the
   runner cwd and recorded as absolute in `policy_evaluated`). Roots are resolved with `filepath.EvalSymlinks`
   at preflight and must stay inside the workspace after resolution; a root that escapes through a symlink or
   junction fails preflight.

### B. Evaluation, preflight and consent

6. A pure function computes, for each node, the effective policy: defaults merged with node values by the
   narrowing rules. No I/O.
7. A platform capability probe (side-effect free, bounded, reusable by F2.11's capability report) reports which
   mechanisms exist on this machine: Landlock ABI for filesystem writes, unprivileged user and network
   namespaces for `network: off`, Windows Job Object support, Git evidence availability, Codex sandbox
   availability. It never installs or changes anything.
8. The permissions report lists, per node: type, requested permissions, assigned secret names (F3.8), and for each
   permission its enforcement state on this machine:
   - `prevented`: the operating system or the launcher refuses the action.
   - `contained`: the action can happen but only in a disposable worktree whose integration is refused; the source
     checkout and integrated ref are unchanged (F3.1 mechanism).
   - `delegated`: enforced by the agent's own sandbox, not by Tarmind. The trust boundary is the vendor's.
   - `detected`: the violation is found after the fact (F1.8 Git evidence) and recorded; not prevented.
   - `unobserved`: neither prevented nor detectable on this machine; nothing is recorded.
   - `unenforceable`: the request cannot be honored here at all.
   Each permission records two fields: `state` (what this machine can do, from the vocabulary above) and
   `applied` (whether the mode enforces it). Under `audit`, `applied` is false, so an audit run never reports a
   permission as `prevented` when nothing was prevented. On `policy_evaluated`, a permission with `applied: true`
   requires the event's own `applied: true` (the converse is legal: enforce with no applied permission). Decided 2026-11-17 (lead, delegated by the product owner); the team may revisit.
   The report is a Go type with a JSON form; `agentplane graph permissions PATH [--json]` prints it, and
   `agentplane run` prints it before `run_started`. `graph validate` is unchanged. The loopback API and desktop
   presentation of "requested permissions before the run" is a follow-up that consumes the same type
   (Out of scope).
9. One pipeline, in this order, all before `run_started`: parse and validate graph, evaluate policy (6), probe
   platform (7), decide per-permission enforcement, deliver-or-deny each secret grant (F3.8), resolve only the
   admitted secrets, build the redaction set, print the report. A secret is delivered only if the node's effective
   policy admits it and the secret's backing variable is not reachable through any other channel (F3.8-11). A node
   granted a secret in enforce mode must have `network` declared (`on` or `off`); an undeclared network next to a
   secret is `policy_secret_network_undeclared`.
10. Enforce mode, fail closed: any requested permission whose enforcement state is `unenforceable`, `unobserved`
    or `detected` for a path/network/shell/commands request is a preflight error `policy_unenforceable` naming the
    node, the permission and what would make it enforceable (for example `isolation: worktree` or a newer kernel).
    Enforce mode never silently degrades to audit. `delegated` and `contained` are accepted in enforce mode and
    printed as such.
11. Audit mode: nothing is blocked. Each permission records its state in `policy_evaluated`; observable violations
    become `policy_violation` events with `outcome: recorded`.

### C. Enforcement

12. `shell: off` on a Shell node, and a `commands` allowlist that does not match the node's resolved command, are
    enforced by the launcher: the process is not started, the node is blocked with a `policy_violation`. The
    command is resolved once to an absolute path; that path is checked and that path is launched, so a `PATH`
    entry added by the node's own `env` cannot change the outcome. On Windows the resolved path is compared
    case-insensitively after `EvalSymlinks`; UNC, `\\?\` and alternate-data-stream forms are rejected.
13. `paths.write` for a Shell node on Linux is enforced by the kernel: the runner re-executes itself as a minimal
    helper that applies a Landlock ruleset (write access granted to the resolved allowed directories, to a node
    scratch directory and to nothing else), then replaces itself with the node's command. Landlock rules are
    directory-hierarchy based, so enforcement granularity is the directory; a file-level pattern such as
    `src/**` is enforced at its directory (`src/`) and a pattern naming one file (`src/main.go`) is enforced at
    its parent directory, with the file-level part staying detective via F1.8. Decided 2026-11-17 (lead, delegated by the product owner); the team may revisit: path globs
    follow the F1.8 grammar (a trailing `/**` only); this spec does not widen it.
    The helper is the same binary and takes no input from the graph other than the argv the runner built. It
    sets `PR_SET_NO_NEW_PRIVS`, applies and verifies the full ruleset before `exec`, and exits without exec if
    any step fails. It rejects any unexpected, missing or tampered argv, unknown flag, or invocation not made by
    the runner (test `TestLandlockHelperRejectsTamperedArgv`; plus a test that the child cannot regain
    privileges). If Landlock is unavailable the state is `unenforceable` (13a spike gates this).
14. `network: off` for a Shell node on Linux is enforced by starting the child in new user and network namespaces
    (`SysProcAttr.Cloneflags`, UID/GID mappings), which leaves no usable interface. Where unprivileged user
    namespaces are disabled or restricted (some distributions) the state is `unenforceable`. Landlock network
    rules (kernel 6.7+) are an alternative that covers TCP only and are not used in v0.
15. For an Agent node the mechanisms are different:
    - `network`: `delegated` to the Codex sandbox. The adapter already passes `--sandbox workspace-write` and
      `--ignore-user-config`; this feature requires it to also pin the sandbox's network setting explicitly
      instead of inheriting a default (spike 15a). `network: on` is `unrestricted`.
    - `paths.write`: Codex confines tool commands to the workspace root it was given (`--cd`), which is the
      worktree when isolated. Within that root Tarmind cannot prevent a write outside `paths.write`. With
      `isolation: worktree` the state is `contained` (an out-of-scope change is rejected at integration and never
      reaches the source checkout) plus `detected` (F1.8). Without isolation the state is `detected` only, so
      enforce mode requires `isolation: worktree` for any Agent node that declares `paths.write`.
    - `shell` and `commands`: `unenforceable` for Agent nodes in v0. An agent's purpose is running commands.
16. A violation (a refused launch, an out-of-scope write found by the F1.8 check on a node with `paths.write`, a
    Landlock/namespace refusal that the node reports as a failure, a `secret_in_workspace` hit) in enforce mode
    blocks the node: it ends with failure kind `policy_blocked`, a typed `policy_violation` fact and a red Check
    Result of kind `execution_policy` carrying bounded sorted evidence. A blocked node is not retried by a
    correction loop (the budget is not consumed again for the same violation) and its accepted outputs are not
    recorded. Sibling accepted units are untouched (AGENTS.md rule 6). The run ends in the existing
    needs-intervention class unless Open question 4 decides otherwise.
17. A write the kernel prevents inside a Shell node surfaces to the node as an ordinary I/O error; the runtime
    cannot attribute every `EACCES` to policy. The node's own failure stands, and `policy_evaluated` already
    records the permission as `state: prevented` with `applied: true`, so the trace explains it. Attributed `policy_violation` facts
    come only from checks the runtime performs itself (launch refusal, post-run scope check, workspace scan).
18. `policy_violation` evidence never contains a secret value and is passed through the run's redactor.

### D. Platform matrix (what Tarmind can say honestly, no new dependencies)

| Permission | Linux Shell | Linux Agent (Codex) | Windows Shell | Windows Agent |
| --- | --- | --- | --- | --- |
| `shell` | prevented (launcher) | unenforceable | prevented (launcher) | n/a: adapter unsupported (process ownership needs Darwin/Linux) |
| `commands` (own process) | prevented (launcher); descendants unconstrained | unenforceable | prevented (launcher); descendants unconstrained | n/a |
| `paths.write` | prevented at directory granularity if Landlock available; else unenforceable (F1.8 detects when Git evidence works) | contained with `isolation: worktree`, detected otherwise; Codex confines to workspace root (delegated, verify in spike) | unenforceable; unobserved (Git evidence is `/usr/bin/git`-based and does not run on Windows today) | n/a |
| `network: off` | prevented via user+net namespaces if permitted; else unenforceable | delegated to Codex sandbox (tool commands only) | unenforceable (no stdlib mechanism without admin-level firewall or AppContainer) | n/a |
| secrets (F3.8) | env delivery, redaction, workspace scan | env delivery, redaction, workspace scan; Codex env filtering unverified | env delivery and redaction; scan `unobserved` | n/a |

Consequences on Windows, supported in the first release: Shell nodes get `shell` and `commands` enforcement and
the full F3.8 secret model (injection, redaction, preflight). `paths.write` and `network: off` in enforce mode
fail preflight with `policy_unenforceable`; in audit mode they run and are reported `unobserved`. A Job Object
created through `syscall.NewLazyDLL("kernel32.dll")` is already usable for kill-on-close cleanup, but filesystem
and network confinement need AppContainer or restricted tokens, a large amount of `unsafe` Windows API code that
this spec defers (Open question 3). macOS is reported `unenforceable` for Shell and `delegated` for Agent network
and workspace confinement as far as Codex enforces them.

## Data / API contracts affected

- Graph: additive optional top-level `policy` and per-node `config.policy` (`shell` and `agent` field registries;
  `policy` accepted in `config` of Gate/Human is a validation error because those nodes have no permissions to
  restrict beyond what the runtime already fixes). No `schema_version` bump proposed (Open question 5).
- Events: new typed facts `policy_evaluated` (one per node run before its first attempt; effective policy, mode,
  enforcement states, secret assignments from F3.8, resolved scope root) and `policy_violation` (node run,
  permission, evidence list, `outcome: blocked|recorded`). New Check Result kind `execution_policy`. One event
  schema bump covers F3.8 and F3.9: event schema 14 (proposed; next free number confirmed at merge; F2.8b = 12 and
  F3.4 = 13, Decided 2026-11-17 (lead, delegated by the product owner); the team may revisit). Readers of older schemas see none of it.
- CLI: `agentplane run --policy-mode audit|enforce` (stronger only), `agentplane graph permissions PATH [--json]`.
- Runtime: consumer-owned port `runtime.PolicyEnforcer` composed by the CLI, like `WorkspaceManager`; the
  platform mechanisms (Landlock helper, namespaces, Job Object) live in a platform package behind it, with
  per-OS build tags and an `other` implementation that reports `unenforceable`. The pure policy evaluation and
  the pattern matcher are domain code shared with the F1.8 scope Gate (no second matcher).
- Process: the hidden helper subcommand used for Landlock is not user-facing, rejects any argument not produced by
  the runner, and is disabled when the binary is not the runner itself.

## Failure behavior

- Invalid policy: validation error naming node and key; nothing runs.
- Enforce mode with an unenforceable request: preflight error, no events, non-zero exit, names the missing
  mechanism and the way to satisfy it.
- Probe failure (cannot determine Landlock/userns): treated as unavailable; the state is `unenforceable`, never
  assumed enforced.
- Helper or namespace setup fails after preflight said `prevented` (race, changed kernel setting): the node does
  not start unconfined; it fails with `policy_blocked` and `reason: enforcement_unavailable`. Never run
  unconfined in enforce mode.
- Cancellation: the confined child is terminated through the same cancellation path as today.
- A violation in audit mode never changes node outcome or run result.

## Acceptance criteria

- [ ] A graph without `policy` or `secrets` has byte-identical semantic hash, events and CLI output to `main`.
- [ ] A node `policy` that widens a graph default fails validation naming node and key.
- [ ] A graph policy cannot lower a runner-set `--policy-mode enforce`.
- [ ] `agentplane graph permissions` on a fixture prints, for every node, requested permissions, assigned secret
  names and an enforcement state from the closed vocabulary; `--json` output is stable and secret-free.
- [ ] Enforce mode, Linux, Landlock available: a Shell node with `paths.write: ["out/**"]` that writes
  `out/a.txt` succeeds and the same node writing `../escape.txt` and an absolute path outside the workspace fails
  with a permission error and the file does not exist afterward (asserted on the filesystem, not on a log).
- [ ] Enforce mode, Linux, Landlock unavailable (simulated by the probe): the same graph fails preflight with
  `policy_unenforceable` and no process starts.
- [ ] Enforce mode, `network: off`, Linux with user namespaces: a Shell node that connects to a loopback listener
  opened by the test cannot connect; with `network: on` it can.
- [ ] Enforce mode, Shell node, `shell: off` or a non-matching `commands` entry: the process is never started
  (asserted by a marker file the command would create) and the node ends `policy_blocked` with a red
  `execution_policy` Check Result.
- [ ] A command resolved from a `PATH` entry supplied by the node's own `env` is checked and launched as the same
  absolute path.
- [ ] Enforce mode, Agent with `paths.write` and no `isolation: worktree`: preflight error requiring isolation.
- [ ] Enforce mode, isolated Agent (fake adapter) that writes outside `paths.write` inside its worktree: the unit
  is not integrated, the source checkout and `refs/agentplane/<run>/integrated` hold no out-of-scope change, the
  node is `policy_blocked` with evidence listing the sorted paths.
- [ ] A blocked node is not retried by a correction loop and accepted siblings are not rerun.
- [ ] Audit mode never reports `applied: true`: every permission carries `state` and `applied`, and a violating
  write under `audit` is `state: prevented|unobserved|detected` with `applied: false` (test
  `TestAuditPermissionsAreNeverApplied`).
- [ ] Audit mode: the same violations produce `policy_violation` with `outcome: recorded`, the node outcome and
  run result are unchanged, and unobservable permissions are marked `unobserved`.
- [ ] A secret assigned to a node whose policy does not admit it never appears in that node's environment (fake
  executor asserts the environment), and the run fails preflight with `secret_policy_denied`.
- [ ] A secret value never appears in `graph.yaml`, `events.jsonl`, `policy_evaluated`, `policy_violation`
  evidence, the permissions report, API responses or the store directory (byte scan, shared with F3.8).
- [ ] Windows: `shell` and `commands` enforcement tests pass; a graph with `paths.write` or `network: off` fails
  preflight in enforce mode with `policy_unenforceable`; audit mode reports `unobserved`.
- [ ] Architecture test: platform enforcement and secret providers are imported only by the composition root;
  `internal/runtime` imports neither.
- [ ] `go test -race` passes for every package touched; helper process and namespace tests leave no child process
  behind (asserted by waiting on the process, not by sleeping).

### F3.9a consequences

Without the Landlock helper and namespaces (F3.9b), F3.9a reports the platform honestly:

- Shell `paths.write` and Shell `network: off` are `unenforceable` on every platform: enforce mode fails preflight
  with `policy_unenforceable`; audit mode runs and records the state (`unobserved`, since no Git-based detection
  exists for Shell nodes).
- Shell `shell` and `commands` are `prevented` by the launcher on every platform (requirement 12), including Windows,
  where the tests cannot run until a Windows machine or CI job is available.
- Agent `paths.write` is `contained` + `detected` with `isolation: worktree`, `detected` without; Agent `network`
  stays `unenforceable` until spike 15a pins the Codex setting (F3.9b); Agent `shell`/`commands` are `unenforceable`.

Open question 5 (schema versioning) must be confirmed by the owner before T1 starts; T1 assumes the recommended
additive, unversioned form. Open questions 1, 2 and 3 are decided inside F3.9b by their spikes.

### Risks noted at T0

- **Attribution in a shared workspace** (T6): a `secret_in_workspace` hit is attributed to every node with a grant
  that ran in that workspace (F3.8 behaviour). Under enforce this can block a node that did not write the value.
  T6 must either narrow attribution (per-node baselines) or document the over-blocking and test it.
- **Exit code** (T6): needs-intervention is shared with human gates; scripts cannot tell a policy block from a pending
  approval by exit code alone. The `--json` failure kind distinguishes them.
- **F3.9a shows little `prevented`**: until F3.9b, enforce mode refuses most Shell `paths.write`/`network` requests.
  The report and docs must say so plainly rather than suggest a sandbox.
- **CI**: GitHub Actions do not start (billing). F3.9b cannot tick a platform criterion without a named CI job whose
  skips count as failures.

## Required tests

- Unit: policy parse and validation; narrowing/merge rules; mode strengthening; pattern matcher shared with F1.8
  (similar prefix, `**`, deletes, renames, Windows case and separator forms, `..`, UNC, ADS); command resolution
  and same-path launch; enforcement-state decision table for every cell of the platform matrix with fake probes;
  `policy_unenforceable` diagnostics; report JSON stability.
- Integration (temp repos/directories, fake probes and fake adapters): the single-pipeline ordering (policy before
  secret delivery before `run_started`); contained-by-integration-refusal with real Git worktrees; blocked node
  not retried; sibling units untouched; event stream reconstruction of `policy_evaluated` -> `policy_violation`
  -> failure; audit-mode parity.
- Platform (guarded by `internal/testenv` helpers; skip with a reason where the mechanism is absent): Landlock
  write confinement and namespace network isolation on Linux; launcher enforcement and path-form rejection on
  Windows. Ubuntu 23.10+/24.04 restricts unprivileged user namespaces through AppArmor (likely on GitHub-hosted
  runners) and WSL2 kernels may lack Landlock. At least one named CI job (a Linux runner or container with
  userns allowed and Landlock present, configured explicitly) must run these enforce tests with skips treated
  as failures. A run where all platform tests skipped is not verification: the progress log must record
  "enforcement unverified on <platform>", and that mechanism cannot be marked implemented.
- CLI/e2e: `graph permissions`, `run --policy-mode enforce` on the three-node fixture; exit codes; `serve` run
  through the loopback API (secret-free responses).

## Security / trust considerations

- Graph files, command names, patterns, environment and paths are untrusted. Patterns are validated before use;
  roots are resolved through symlinks and junctions and must stay inside the workspace; the Landlock helper is
  reachable only through the runner-built argv.
- A permissions report is a consent surface. A graph from an unknown source must be shown with every requested
  permission and every secret assignment before it runs; hiding it in a quiet success path defeats the feature.
- Prevent/contain/delegate/detect are different promises and must never be collapsed into "sandboxed" in docs,
  CLI output or UI. A `delegated` permission is only as strong as the vendor sandbox, which can change with the
  installed version.
- Enforce mode must never run a node less confined than reported. TOCTOU between the preflight probe and launch is
  closed by re-applying the confinement at launch and failing closed.
- Reading remains unrestricted. Residual risks: an enforced node can read other credentials on disk, spawn
  unconstrained descendants, and (with `network: on`) send anything it can read. The F3.8 workspace scan and
  redaction reduce but do not remove this.
- Policy never widens permissions of the runner: it can only restrict a child, and no policy field adds
  filesystem or process authority.

## Observability

- `policy_evaluated`: node run ID, effective permissions, mode, per-permission enforcement state, resolved scope
  root, secret assignments (names only).
- `policy_violation`: node run ID, attempt ID when relevant, permission, bounded sorted evidence, outcome
  `blocked` or `recorded`, reason from a closed vocabulary (`launch_refused`, `out_of_scope_write`,
  `secret_in_workspace`, `enforcement_unavailable`).
- Red `execution_policy` Check Result so the existing Run Inspector and trace lookups can show it without new
  plumbing.
- Preflight failures are diagnostics, not events.

## Open questions

1. **Linux write confinement mechanism.** Recommended default: self re-exec helper applying Landlock (stdlib
   `syscall` only), subject to a spike (13a) proving it works for a command that needs the Go toolchain's temp and
   cache directories, and that an allowed-directories list is practical. Fallback if the spike fails: Shell
   `paths.write` is `detected` and enforce mode requires isolation-style containment, which Shell nodes do not
   have (F3.1 excludes them), so enforce would reject Shell `paths.write` on Linux.
2. **Codex sandbox pinning (15a).** Spike to confirm that `--sandbox workspace-write` with explicit
   network-off configuration denies tool-command network, confines writes to the `--cd` root in a linked worktree,
   and how it treats environment variables with secret-like names (also F3.8 question 6). If the vendor setting
   cannot be pinned, Agent `network: off` becomes `unenforceable`.
3. **Windows depth.** Recommended default: v0 ships what is above (launcher enforcement plus full secrets) and
   reports `paths`/`network` as unenforceable; F3.9b evaluates AppContainer or restricted tokens, which is a
   significant `unsafe` surface. Needs an owner decision on whether Windows may be advertised with that limit in
   the first release. Native Windows support for Git evidence is a separate owner decision already pending in
   `docs/development-workflow.md`.
4. **Run result for a blocked node.** Decided 2026-11-26 (product owner): the existing needs-intervention class and
   exit code, with failure kind `policy_blocked`. No dedicated exit code.
5. **Schema versioning.** Recommended: additive optional `policy` and `config.policy`, no graph `schema_version`
   bump (as `units`). Alternative: bump and migrate.
6. **Default mode.** Decided 2026-11-26 (product owner): `audit` when a policy is present and no mode is stated, so
   adopting a policy never breaks an existing run; documentation states plainly that audit blocks nothing.
7. **Undeclared keys under enforce.** Decided 2026-11-26 (product owner): an undeclared permission is unrestricted
   and shown as `unrestricted (not declared)` in the report. Default-deny is left for v1.
8. **Secret next to network.** Recommended: require `network` to be declared for any node holding a secret in
   enforce mode (requirement 9); consider requiring `off` for Agent nodes once 15a is proven.
9. **`shell: off` for Agent nodes.** Recommended: `unenforceable` in v0; revisit if Codex exposes a read-only mode
   that fits a "reviewer" node.

## Out of scope for this iteration

- Read confinement; descendant-process confinement; host/port network rules.
- AppContainer, restricted tokens, Windows Firewall rules (F3.9b candidate).
- macOS Shell enforcement.
- Loopback API route and desktop view for requested permissions (the Go report type is the contract; roadmap
  acceptance "UI shows requested permissions before a run" is completed by that follow-up).
- Policy language, organization policy, blast-radius approval (F5.9, F6.4).
- Rewriting `docs/graph-spec.md`, `docs/security-model.md` and `docs/architecture.md` (done together with the
  implementation, not this spec).
