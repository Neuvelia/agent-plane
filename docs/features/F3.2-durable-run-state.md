# F3.2 - Durable Run State / Append-only Event Store

**Status:** implemented on Linux (plan tasks 1-9); the Windows store and kill tests have not been run (no Windows runner in this environment). ADR-0027 accepted by the owner on 2026-11-26.
**Priority:** P0
**Target phase:** Phase 3 - Local Production Ready
**Depends on:** F0.6 (event model), F1.3 (progress), F2.9 (JSONL run store)
**ADR:** ADR-0027 (accepted; extends ADR-0019, rejects SQLite)

Tarmind (in code today: agentplane) keeps this feature local-first: no
database, no service, no new mandatory dependency.

## Inventory: what existed on `main` before F3.2 (2026-11-17)

This section is the starting point the feature changed; the requirements, amendments and acceptance criteria below describe the result.

- **Run store (F2.9, ADR-0019, `internal/store`).** `<store>/<run_id>/events.jsonl`
  (one redacted retained event per line) plus `graph.yaml`. Non-progress events
  are `fsync`ed before `Writer.Append` returns; `log_chunk` and progress are
  synced by the next non-progress event or `Close`. Directories 0700, files 0600,
  exclusive creation. The writer latches the first write/sync error. Persistence
  is a synchronous sink on the emitter (`Collector.SetPersist`).
- **Persist-before-deliver mostly holds.** `Collector.Append` retains, records and
  persists before `enqueueLive` (`collector.go`), and `serve` writes the store
  before its own persist step. F3.2 turns this into a tested contract. Gaps:
  after a persist error the failing event is still delivered (the error is
  recorded, then `enqueueLive` still runs); progress events beyond the
  retention bound are never persisted but are delivered live; unsynced log
  chunks can be shown and then lost on kill.
- **Not durable today (ADR-0019 "Durability scope").** The run directory entry
  and `graph.yaml` are not fsynced (power loss can leave a run without a graph
  or directory). No index: `List` opens and fully parses every run. No
  retention. No lock, so a live run in another process and a dead run both
  look unterminated. A hung filesystem blocks the run (no timeout).
- **Event schema.** `events.SchemaVersion = 11` (`internal/domain/events/event.go`),
  carried on every event; decoding validates it and upcasts selected legacy
  shapes (schema 1 `node_evidence`, schema 4 gate payloads). Later versions have
  been additive (10 `value_recorded`, 11 isolation facts; F2.8b's `attempt_diff` is
  schema 12).
- **Run/node states.** `docs/domain-model.md` defines no state enumeration; it
  states invariants (a run ends in exactly one terminal state; sequence is
  monotonic; "runtime state must be reconstructable from durable events once
  persistence is introduced", invariant 10). `INTERRUPTED` appears only in the
  reference plan (`docs/reference/full-architecture-plan.md`) and `CHECKING` does
  not exist as a run/node state: checks are `gate_check` facts and attempt events.
  `interrupted` exists as a **derived store status** (`store.StatusInterrupted`),
  as an API overlay (`running` while the server follows a run), and as a desktop
  `RunStatus` (`reducer.ts`: no terminal event and not live).
- **Reconstruction.** `store.Read` validates run ID, increasing sequence,
  first `run_started`, nothing after `run_finished`, schema support; a bad final
  line is `truncated`, mid-log corruption is an error. The API (`GET /runs`,
  `/runs/{id}`, `/runs/{id}/events`) replays events from the store; the desktop
  derives all state by reducing them (`desktop/src/reducer.ts`).
  Node-level interruption is not derived: a node with `node_started` and no
  terminal event keeps showing `running` until the run is marked interrupted.

## Problem

History of finished steps already survives a killed process, but the guarantees
are implicit and partial: a live run cannot be told from a dead one, the layout
has no format version, listing is O(runs x events), nothing bounds disk use, and
the Windows behaviour of the sync/rename calls is untested. F3.3 (resume) needs
a store whose "complete" boundary and "interrupted" state are exact.

## Goal

A run's durable state is exactly its event log. After `kill -9` at any point,
every transition that was observable to a subscriber or the scheduler is on
disk, an unterminated run is reliably reported `interrupted`, and state is
reconstructed from events alone. Listing stays fast with thousands of runs, and
retention is explicit and local.

## Non-goals

- Resume or recovery of interrupted runs (F3.3); F3.2 only identifies them.
- SQLite or any database (rejected, see ADR-0027).
- Artifact store (F3.5), export (F3.7), cloud sync, multi-writer per run.
- Power-loss guarantees stronger than "no acknowledged transition lost on a
  journaling filesystem with working fsync" (stated, not tested).
- New event types or an event schema bump (see requirement 6).

## Functional requirements

Each requirement records the recommended option; alternatives are in ADR-0027.

1. **Transition-complete boundary.** A transition is complete only when its
   event line has been written and `fsync`ed. The sink must complete before
   the event is delivered to any subscriber (stream, stdout, API) and before
   the scheduler acts on the transition. Consequence: anything a client saw
   is on disk. `log_chunk` and progress keep deferred sync (they are not
   transitions); explicit exception: progress events beyond the retention bound
   are delivered live but never stored, and log chunks not yet synced can be
   lost on kill. A sink error stops the run as in ADR-0019, and live delivery
   must stop after the first persist error (the failing event and all later
   ones are not delivered). A bounded
   per-write timeout is out of scope (open question 4).
2. **Creation durability.** Write `graph.yaml` with sync before creating
   `events.jsonl`, then fsync the run directory and the store directory
   (POSIX). A run directory without a valid `events.jsonl` first line is
   `corrupt`/ignored, never half-readable.
3. **Interrupted run.** Interrupted is a *derived* state, not a recorded event
   in F3.2: a log with no `run_finished` whose writer is gone. A live writer
   holds an exclusive advisory lock on `<run>/run.lock` for the run's lifetime
   (`flock` on Unix, `LockFileEx` on Windows, via `golang.org/x/sys`, already in
   `go.mod`; the lock dies with the process, including `kill -9`). Reader
   rule: terminal event -> its status; else lock held -> `running`; else
   `interrupted`. The reducer also derives node/attempt `interrupted` (started,
   never finished) once the run is interrupted. Representations: store status
   `interrupted` (unchanged string), API run summary field `status` plus
   `interrupted_at_sequence` (last durable sequence), desktop `RunStatus`
   already has it. F3.3 may later append an explicit recovery event.
4. **Reading older logs.** No rewrite or in-place migration of schema 1-11
   logs. The reader supports every schema from 1 to current through the
   existing decoder. A log with a higher schema than the binary is listed
   `unsupported` (new typed error) with its schema, not `corrupt`, and is never
   modified. A store-level `<store>/store.json` (`{"store_format":1}`) is
   created on first write; absence means format 0 (the ADR-0019 layout) and is
   fully readable. A newer `store_format` makes the store read-only with an
   actionable error.
5. **Summary snapshot and listing.** Each finished run gets `<run>/summary.json`
   (the existing `Summary` fields plus `log_bytes`), written to a temporary file in
   the run directory, synced and renamed into place, once, at the terminal event
   (amendment A3: a snapshot taken at `run_started` could never be trusted for
   listing, so it would cost a rename per run for no reader). It is an
   optimisation: `List` trusts it only when it names the same run, describes a
   finished and complete log (a terminal status, a finish time, no truncation, a
   schema this build supports) and `log_bytes` equals the current `events.jsonl` size;
   otherwise (missing, stale, damaged, unterminated) it parses the log. On any
   disagreement the log wins and the snapshot is rewritten best effort, skipped
   while the run lock is held so it cannot race the writer, and a failure is
   reported through `Store.SnapshotWarn`, never as a listing error (read-only
   stores still list). The writer reports its own snapshot failure through
   `Writer.SnapshotError()`; the run is unaffected. `List` therefore reads N small
   files instead of N full logs. Limit: a same-size edit of a finished log cannot
   be detected by `log_bytes`; a log is append-only and never edited, so this is
   accepted. No store-wide index file in F3.2: the benchmark below met the budget.
6. **No new event types.** Interrupted and snapshot state add no events and
   keep schema 11. Any future recorded `run_interrupted` fact is F3.3 with its
   own schema bump.
7. **Retention.** Local, off by default: `store.json` may hold
   `retention: {max_runs, max_age_days, max_total_bytes}` (edited by hand; there is
   no command to set it); absent or zero means keep everything. Applied only by
   `agentplane runs prune [--dry-run]` (and once at `serve` start, only when
   configured: in the background after the announcement line, so a large store
   never delays startup, stopped at shutdown, reporting to stderr; an unreadable
   `store.json` is a warning there, never silence). Never deletes an unterminated run (live or
   interrupted) regardless of age, because F3.3 resume needs it, nor a locked,
   corrupt or unsupported one; deletes whole run directories, oldest first,
   under the run's exclusive lock; prints removed run IDs. Selection: `max_age_days`
   first, counted from the run's `run_finished` timestamp (`Summary.finished_at`),
   not its start, so a run that took days is not expired the moment it ends; then `max_runs` counted over every run (kept runs use the budget), then
   `max_total_bytes` over run directory sizes. Only real directories named like a
   run ID that hold `events.jsonl` count; a symlink is never followed. A deletion
   that fails (Windows sharing violation) is reported and skipped, not retried in
   a loop, and `runs prune` exits 1. Prune does not touch Git worktrees or
   `refs/agentplane/*`, which F3.1 owns. A dry run prints exactly the plan the real
   prune executes (`Store.PlanPrune`, then `Store.Prune`); in `--json` it is listed
   under `would_remove` and `removed` stays empty. Planning rebuilds a missing
   snapshot best effort, as `List` does, so a store from before snapshots is not
   re-parsed by every later prune.
8. **Windows consistency.** Document and test: `File.Sync` maps to
   `FlushFileBuffers`; directory fsync does not exist on Windows (no-op there,
   so creation durability is best-effort, documented); `os.Rename` onto an
   existing file replaces it but is not guaranteed atomic across crashes, so
   no authoritative state relies on rename: the log is append-only and the
   snapshot is rebuildable from it. Files opened by readers or the writer can
   block delete/rename (prune skips them). Locking uses `LockFileEx`, released
   on process termination.
9. **Concurrent readers.** Reading a log while it is being appended never
   returns a torn event: only complete `\n`-terminated lines are consumed; a
   trailing partial line is `truncated` for a dead run and ignored for a live
   one.

## Data / API contracts affected

- Store layout: adds `store.json`, `<run>/summary.json`, `<run>/run.lock`.
  `events.jsonl` and `graph.yaml` unchanged. Format version introduced.
- `store.Summary`: new optional fields (`last_sequence`, `schema` range);
  new status `unsupported`; `interrupted` now means "no live writer".
- API: `GET /runs` entries and `GET /runs/{id}` gain `interrupted_at_sequence`
  and may report `unsupported`; existing fields unchanged (additive).
- CLI: new `runs prune`; `runs list` shows `unsupported`; exit codes documented.
- Events: unchanged (schema 11). `internal/store/AGENTS.md`, ADR-0019 and
  `docs/domain-model.md` (state wording) are updated by the implementation.

## Failure behavior

- fsync or write failure: run stops, error names run ID and directory
  (unchanged); the log up to the last synced line stays valid.
- Lock cannot be taken at run start (another live writer): refuse to start
  that run ID with an actionable error.
- Corrupt mid-log: listed `corrupt` with reason (unchanged); never pruned
  automatically.
- Snapshot unreadable or stale: ignored and rebuilt, never an error.
- Newer schema or `store_format`: read-only, typed error, no writes.
- Prune failure on one run does not abort the others and exits non-zero.

## Acceptance criteria

- [x] Killing a CLI process with SIGKILL (TerminateProcess on Windows) after a
      node's `node_finished` was observed leaves that event and all earlier ones
      in `events.jsonl`; a fresh process reports the run `interrupted`.
      Proven by `TestKillNineAfterNodeFinishedLeavesDurablePrefix` (Linux; the Windows run, which uses TerminateProcess, has not been executed).
- [x] No non-progress event printed or streamed by a run is missing from disk
      after a kill (persist-before-deliver; progress and log chunks excepted,
      see requirement 1).
      Proven by `TestNoStreamedNonProgressEventIsMissingFromDiskAfterKill` and `TestCollectorDeliversOnlyPersistedEvents`.
- [x] Test `TestLiveDeliveryStopsAfterPersistError`: after an injected persist
      error no further event (including the failing one) reaches subscribers.
      Proven by `TestLiveDeliveryStopsAfterPersistError`.
- [x] `runs prune` never removes an unterminated (live or interrupted) run,
      whatever its age. Proven by `TestPruneNeverRemovesAnUnterminatedRunWhateverItsAge`.
- [x] State reduced from the stored events equals state reduced from the live
      stream for finished runs (Go reducer and desktop reducer, golden log).
      Proven by `TestStoredEventsEqualLiveEventsForAFinishedRun` (the stored sequence equals the live sequence) and the desktop reducer case `reduces the stored sequence and the same sequence delivered as a stream to the same state` (`desktop/test/reducer.test.ts`). There is no Go event reducer (amendment A4).
- [x] A live run in another process reads `running`; after kill, `interrupted`
      within one `List` call (lock released).
      Proven by `TestLiveRunReadsRunningAndDeadRunReadsInterrupted` and the `running` then `interrupted` assertions of `TestKillNineAfterNodeFinishedLeavesDurablePrefix`; the API side by `TestHubOverlayDoesNotMaskARunLiveInAnotherProcess`.
- [x] Logs of every schema 1-11 fixture read back; a schema 12 fixture is
      `unsupported` and unmodified.
      Proven by `TestSchemaFixturesRoundTrip` (fixtures v1 to v11; the schema 12 case is built from the current fixture, amendment A5) and `TestUnsupportedSchemaIsTypedAndListedUnsupported`; at the API, `TestUnsupportedRunIsListedAndGetReportsIt`.
- [x] `List` over 5,000 synthetic runs completes within the budget recorded
      in the spec's benchmark (initial target: 1 s warm, Linux; Windows number
      recorded, not gated) and parses no log whose snapshot is valid. Proven by
      `TestListFiveThousandRunsMeetsTheBudget` and `TestListParsesNoLogWhenTheSnapshotIsValid`.
      The Windows number is not recorded yet (no Windows runner in this environment).
- [x] A stale or deleted `summary.json` never changes `List` output. Proven by
      `TestStaleOrDeletedSnapshotNeverChangesListOutput`.
- [x] `runs prune` honours each limit, `--dry-run` deletes nothing, and never
      removes a locked or corrupt run. Proven by `TestSelectForPruneHonoursEachLimitOldestFirst`,
      `TestPruneHonoursMaxRunsMaxAgeAndMaxTotalBytesOnDisk`, `TestPlanIsReadOnlyAndMatchesWhatPruneRemoves`,
      `TestPruneNeverRemovesALockedCorruptOrUnsupportedRun` and `TestRunsPruneCommand`.
- [x] Injected fsync failure and short write stop the run and leave a readable
      prefix.
      Proven by `TestInjectedFsyncFailureStopsTheRunAndLeavesAReadablePrefix` and `TestShortWriteStopsTheRunAndLeavesAReadablePrefix`.
- [ ] `make check` and `go test -race ./internal/store/...` pass on Linux; the
      store tests pass on Windows. Linux: `make check` and `go test -race ./...` pass
      on the integrated tree (2026-11-18). Windows: only `GOOS=windows go vet` was
      run; the tests were not, so this criterion stays open until a Windows run.

## Amendments recorded while implementing

Each differs from the text above on purpose.

- **A1 - CLI `run` does not cancel on a persist error.** Requirement 1 says a sink
  error stops the run "as in ADR-0019". `serve` does: it cancels the run and ends
  the stream with an error. CLI `run` keeps the run going, shows its result and
  exits 1 with the run ID and the partial log path (`TestPersistFailure*` in
  `cmd/agentplane/store_test.go`). Live delivery stops at the first error in both.
- **A2 - End-of-run watch replay.** `run --watch` finishes by replaying the run's
  retained in-memory events that were not delivered live. After a persist error
  that replay still prints events the store never received. It is the result
  display, not live delivery, and the command reports the run as not persisted
  and exits 1 (`TestPersistFailureInWatchModeFinishesTheWatchAndReports`).
- **A3 - The snapshot is written at the terminal event only.** See requirement 5.
- **A4 - No Go event reducer.** The repository has none, so "Go reducer and desktop
  reducer" is met by the stronger statement that the stored event sequence equals
  the live sequence, plus the desktop reducer golden case.
- **A5 - Schema fixtures.** Fixtures `v1.jsonl` to `v11.jsonl` are committed. The
  "schema 12" case is the current fixture with its schema number raised, so it
  follows `events.SchemaVersion`; a schema bump must add the next fixture or
  `TestSchemaFixturesRoundTrip` fails.
- **A6 - Retention is edited by hand.** `store.json` holds the limits; there is no
  command to set them. See requirement 7.
- **A7 - The crash test graph chains its second node.** "Two-branch graph, first
  branch finishes, second blocks" cannot observe `node_finished` of the first
  branch before the second ends, because a node's terminal event is emitted when
  its batch is accepted. The second node therefore depends on the first and
  starts in the next batch, and the test reads the child's stderr, where the
  watch renderer writes node lines.
- **A9 - Retention age counts from the finish, and runs after the announcement.**
  `Summary.finished_at` (the `run_finished` timestamp) was added so `max_age_days`
  does not expire a run that took days the moment it ends; a snapshot without it
  is rebuilt from the log. Retention at `serve` start runs in the background after
  the announcement line and is stopped at shutdown (`Store.PlanPrune` and
  `Store.Prune` take a context). Found by the review of #128.
- **A8 - `Store.SnapshotWarn` and `Writer.SnapshotError`.** Snapshot failures are
  non-fatal and reported through these two hooks (requirement 5); no event
  records them.

## Benchmark

`TestListFiveThousandRunsMeetsTheBudget` seeds 5,000 synthetic finished runs
(two-event logs, valid snapshots, no per-file fsync) and lists them warm.
It parses no log, is skipped under `-short` and `-race`, and gates only on Linux
(budget 1 s); other platforms log the number. `BenchmarkList5000` repeats it.

| Platform | Runs | Warm `List` with snapshots | Without snapshots (parse every log) |
| --- | --- | --- | --- |
| Linux, 4 CPUs, Go 1.24 (2026-11-18) | 5,000 | about 65 ms | about 230 ms |
| Windows | 5,000 | not measured | not measured |

The synthetic logs are tiny. A real log is larger, so the parse-everything cost
grows with log size while the snapshot cost does not.

## Required tests

- Unit (`internal/store`): sync ordering via the `logFile` fault seam,
  creation order and dir sync calls (seam), lock held/released, snapshot
  validity rules, schema fixtures 1-11 and 12, retention selection, partial
  trailing line, concurrent read during append (race detector).
- Integration: run in a helper process; reader in the test process; persist
  before deliver (child stdout line implies disk line).
- CLI/e2e: `kill -9` crash test. The test binary re-executes itself as a child
  running a two-branch shell graph; the first branch finishes, the second
  blocks on a file the test never creates. The test reads the child's stdout
  until the first `node_finished`, then kills it with `Process.Kill`
  (no sleeps), and asserts the stored prefix, `interrupted` status, node
  `interrupted` derivation, and that `runs list/show` agree. Runs on Linux and
  Windows.
- Desktop: reducer test for derived node interruption; `npm run check`.

## Security / trust considerations

Run IDs, paths and the store directory remain untrusted; permissions stay
0700/0600 (also for `store.json`, `summary.json`, `run.lock`). Snapshots add no
data beyond the redacted log. The lock file holds no content. Prune only
deletes directories that match the run-ID pattern and contain `events.jsonl`;
never follows symlinks out of the store. No secret is written to any new file.

## Observability

No new events. Store anomalies (stale snapshot rebuilt, unsupported schema,
prune actions) are reported through CLI/API output and structured errors, not
silent logs. Interrupted-ness is observable from the log plus the lock state.

## Open questions

Recommended defaults in parentheses; owner confirms before implementation.

1. Record interruption as an event now? (No; derived, F3.3 decides.)
2. Store-wide `index.json`? (No; per-run snapshot first, measure. Measured: not needed.)
3. Retention default? (Keep everything; explicit prune only.)
4. Timeout on a hung sink write? (Not in F3.2; document, revisit with F3.4.)
5. Directory fsync on Windows? (Best-effort no-op, documented.)
6. `store.json` required or lazily created? (Lazily on first write.)

## Out of scope for this iteration

Resume (F3.3), cancellation/timeouts (F3.4), artifacts (F3.5), export (F3.7),
usage metadata (F3.10), diagnostics (F3.11), cloud metadata sync (F4.7), any
SQLite or other embedded database.
