# F2.12 - Safe Graph Templates

**Status:** implemented (owner decisions 2026-11-15); pattern and domain template files, Go tests and the desktop picker implemented
**Priority:** P1
**Target phase:** Phase 2 - Local IDE
**Depends on:** F2.1 (New graph flow, create-on-first-save), F2.2-F2.4 (editing, issues panel, Run gating),
F1.4 (Gate kinds), F1.6/F1.6a (bounded loops), F2.10 (human node)
**Works with:** F2.11 (capability report used for requirement notices; setup's last step offers four templates as cards, ADR-0046)
**ADR:** none required for the proposed design (templates are ordinary graph files bundled with the
renderer; no API, schema or event change). An ADR is required if the owner chooses sidecar-served
templates (see Open questions).

## Problem

A new graph in the desktop starts empty. To get a working graph a person must know the schema-v0 shapes of
shell, agent, gate and human nodes, loop and embedded-gate syntax, binding rules and which commands are safe
to try. The repository's example graphs are not offered in the app, and two of them need a Go toolchain.
There is no starting point that shows the correct graph/loop/gate patterns and is safe to run as is.

## Goal

"New graph" offers four templates next to a blank graph. Each template is an ordinary schema-v0 graph file
kept in the repository. Choosing one creates an unsaved draft with that text through the existing
create-on-first-save flow; after the first save it is a normal graph file with no link back to a generator.
Three templates validate with zero diagnostics and run on Linux and macOS without edits; the agent template
has exactly one value the person must fill, which is marked in the file and is the only diagnostic it
produces. No template contains a secret, a destructive or network command, or starts a paid agent run by
default. Tests prove each of these properties for every template.

## Non-goals

- (Superseded by the Addendum: the four domain templates named in the roadmap entry were added later.)
- A template language, variables, placeholders resolved by the app, or a generator. Templates are copied
  text; the only change the app makes is the top-level `id` line (requirement 7).
- User-defined or downloaded templates, a gallery, marketplace, sharing or updates of already created graphs.
- New node types, schema fields, edit operations or API routes.
- Running agent nodes from the desktop (not possible today: `serve` has no adapter; see F2.11).
- CLI scaffolding (`agentplane graph new --template`).
- Windows equivalents of the shell commands (see Open questions).

## Functional requirements

### A. Template files

1. **Location.** Templates live in `.agents/templates/` as `<id>.yaml`, with an index
   `.agents/templates/index.json`. They are not placed in `.agents/graphs/`, whose files are globbed by
   existing golden and corpus tests (`internal/graph/edit/helpers_test.go`,
   `cmd/agentplane/validation_test.go`).
2. **Index** (version 1):

   ```json
   {
     "version": 1,
     "templates": [
       {
         "id": "agent-scoped-approval",
         "file": "agent-scoped-approval.yaml",
         "requires": ["git", "codex"],
         "platforms": ["linux", "darwin"],
         "placeholders": [{"path": "nodes.implement.config.workspace", "marker": "FILL"}],
         "expected_diagnostics": [{"code": "E_NODE_CONFIG_INVALID", "path": "nodes.implement.config"}]
       }
     ]
   }
   ```

   `requires` uses F2.11 tool ids (`git`, `codex`); shell, gate and human nodes need no entry. `platforms`
   uses Go `GOOS` names. `placeholders` lists every value the person must fill. `expected_diagnostics` lists
   exactly the diagnostics `agentplane graph validate` reports for the unedited template (code and
   location path); it is empty for every template without placeholders. Titles and descriptions are UI text
   and live in `i18n/en.ts` and `i18n/pl.ts` under `templates.<id>.title` and `templates.<id>.description`,
   not in the index.
3. **File rules** for every template: schema_version 0; UTF-8 without BOM; LF line endings; at most 8 KiB;
   no YAML anchors, aliases or merge keys (so the canvas is editable, F2.1 requirement 19); a top-level
   `name`; a header comment saying what the graph demonstrates and that its commands only print text;
   `metadata.layout` positions for every node; exactly one line `id: <template id>` at column 0.
4. **Placeholder marking.** A value the person must fill is an empty string followed on the same line by a
   comment starting `# FILL:` that says what to enter, for example
   `workspace: "" # FILL: absolute path of the Git repository the agent may edit`. A valid default the person
   should review is followed by a comment starting `# REVIEW:`. `FILL` values make validation fail with the
   declared diagnostic, so F2.4 shows them in the issues panel and Run stays disabled until they are filled.
   `REVIEW` values never cause a diagnostic. Comments survive canvas edits and saves (ADR-0020).

### B. The four templates

The YAML below is illustrative; the constraints in each row and in requirement 6 are normative. Exact text is
fixed in the implementation PR.

| Id | Shows | Nodes | Placeholders | Runs unedited |
| --- | --- | --- | --- | --- |
| `parallel-shell` | Two independent branches run concurrently; a dependent node receives both outputs through typed edges; a graph output | `left`, `right` (`/usr/bin/printf`), `join` (`/bin/sh -c` printing two `input_env` values) | none | yes (Linux, macOS) |
| `shell-check-loop` | A shell node with `loop.max_attempts: 3` and an embedded `json_predicate` gate; attempt 1 is red, attempt 2 green, using `AGENTPLANE_ATTEMPT` (F1.6a); a comment says to replace the script with a real check | `check` | none | yes (Linux, macOS) |
| `human-approval` | The smallest human gate: a shell summary, a `human` node with `prompt` and `context_inputs`, and a dependent shell node that runs only after approval | `summarize`, `approve`, `done` | none | yes (Linux, macOS), waits for a decision in the app |
| `agent-scoped-approval` | A human approval *before* the agent (the agent's `start` input is bound from it, so no model call happens without a decision); an agent node with explicit `allowed_paths`, `loop.max_attempts: 3` and an embedded `reported_file_scope` gate bound from `candidate.outputs.changed_files`; a human approval of the result that receives the summary and the changed files; the task comes from a required graph input | `confirm_start` (human), `implement` (agent), `approve` (human), `record` (shell) | `nodes.implement.config.workspace` (`FILL`); `allowed_paths` in the agent and its gate (`REVIEW`, equal values) | no: needs the workspace filled and Codex through the CLI |

`parallel-shell` sketch:

```yaml
# Template: parallel shell branches. "left" and "right" run at the same time;
# "join" starts after both and receives their text through edges.
# The commands only print text: nothing is read, written or sent.
schema_version: 0
id: parallel-shell
name: Parallel shell branches
inputs: {}
nodes:
  left:
    type: shell
    config: {command: /usr/bin/printf, args: ["left branch done"]}
    outputs: {stdout: {type: string, required: true}}
  right:
    type: shell
    config: {command: /usr/bin/printf, args: ["right branch done"]}
    outputs: {stdout: {type: string, required: true}}
  join:
    type: shell
    inputs:
      left_text: {type: string, required: true}
      right_text: {type: string, required: true}
    config:
      command: /bin/sh
      args: ["-c", 'printf "%s + %s\n" "$LEFT_TEXT" "$RIGHT_TEXT"']
      input_env: {left_text: LEFT_TEXT, right_text: RIGHT_TEXT}
    outputs: {stdout: {type: string, required: true}}
edges:
  - {from: left.outputs.stdout, to: join.inputs.left_text}
  - {from: right.outputs.stdout, to: join.inputs.right_text}
outputs:
  result: {from: join.outputs.stdout}
metadata:
  layout:
    nodes: {left: {x: 0, y: 0}, right: {x: 0, y: 160}, join: {x: 320, y: 80}}
```

`agent-scoped-approval` sketch of the agent node:

```yaml
  implement:
    type: agent
    inputs:
      task: {type: string, required: true}
      start: {type: string, required: true} # bound from confirm_start.outputs.decision
    config:
      adapter: codex
      workspace: "" # FILL: absolute path of the Git repository the agent may edit
      allowed_paths: ["src/"] # REVIEW: the paths the agent is meant to change
    outputs:
      summary: {type: string}
      changed_files: {type: json}
    loop:
      max_attempts: 3
      gate:
        inputs:
          candidate: {type: json, required: true}
        config:
          check_id: reported-scope
          kind: reported_file_scope
          input: candidate
          allowed_paths: ["src/"] # REVIEW: keep equal to config.allowed_paths
      bindings:
        - {from: candidate.outputs.changed_files, to: gate.inputs.candidate}
```

5. **No paid agent run by default.** The agent template cannot start a model call as delivered: its `FILL`
   value blocks validation and Run (F2.4); the desktop engine has no agent adapter; `agentplane run`
   uses Codex only with explicit `--adapter codex --codex-bin`; and even then the `confirm_start` human node
   must be approved before the agent runs. The template has no `environment_refs`; a
   comment explains that Codex authentication needs a deliberately added reference (F1.2). The picker states
   that this template runs agent nodes through the CLI only.

### C. Safety rules (normative, enforced by tests)

6. Every template satisfies all of:
   - S1. Shell `command` is `/usr/bin/printf` or `/bin/sh`. No other executable.
   - S2. `/bin/sh` is used only as `args: ["-c", SCRIPT]`. Every command word in SCRIPT is an unquoted shell builtin or
     keyword from the allowlist `printf`, `echo`, `test`, `[`, `]`, `if`, `then`, `else`, `fi`; any other command
     word, a quoted or variable command word, or a path such as `/usr/bin/find` is rejected. The allowlist is
     needed because an empty child environment does not prevent program lookup: `/bin/sh` (dash) falls back to a
     default `PATH`, so `env -i /bin/sh -c 'unlink f'` still runs `/usr/bin/unlink`. SCRIPT is tokenized and
     may contain only plain words, single- and double-quoted strings, `$NAME`/`${NAME}` references and the
     separators `;` and newline; it contains
     none of `` ` ``, `$(`, `>`, `<`, `|`, `&` (a `\n` inside a `printf` format is allowed); contains none of these whole words: `rm`, `mv`, `cp`, `dd`,
     `ln`, `chmod`, `chown`, `sudo`, `su`, `curl`, `wget`, `nc`, `ncat`, `ssh`, `scp`, `rsync`, `git`, `eval`,
     `exec`, `source`, `kill`, `mkfs`, `npm`, `pip`, `go`, `docker`; and references only environment names
     declared in that node's `input_env` or `AGENTPLANE_ATTEMPT`.
   - S3. No shell node sets `cwd`, `env` or `env_allowlist`; no agent node sets `environment_refs` or
     `context_refs`.
   - S4. No gate uses `kind: command` or `kind: changed_files_scope` (both need a workspace path).
   - S5. No string anywhere contains `://`, `git@` or `www.`.
   - S6. No secret-like content: no key named `token`, `secret`, `password` or `api_key` (any case), and no
     value matching `sk-`, `ghp_`, `github_pat_`, `AKIA[0-9A-Z]{16}`, `xox[abp]-` or `-----BEGIN`.
   - S7. At most one agent node; its `adapter` is `codex`; every `loop.max_attempts` is explicit and at
     most 3.

### D. Desktop "New graph"

7. **Picker.** "New graph" first shows a dialog listing "Blank graph" and the four templates in this order:
   `parallel-shell` (labelled as the suggested first graph), `shell-check-loop`, `human-approval`,
   `agent-scoped-approval`. Each entry shows its localized title and description, its node types, whether it
   has values to fill, and notices:
   - when F2.11's report gives an `engine.os` not in `platforms`: "Commands in this template need Linux or
     macOS";
   - for each `requires` id: its F2.11 status (or "not checked" when no report is available); for `codex`
     additionally "Agent nodes run only through `agentplane run` in this version".
   Notices inform; no entry is disabled. Cancel closes the dialog and creates nothing.
8. **Creation.** Choosing an entry calls the existing `window.agentplane.newGraph()` (native save dialog in
   main, grant returned). "Blank graph" keeps today's `newGraphText(label)`. A template's draft is the
   template text with its single `id: <template id>` line replaced by `id: <derived id>`, where the derived
   id uses the same derivation as `newGraphText`. Nothing else in the text changes. The draft is unsaved and
   dirty; the first Save creates the file with `base_hash: null` (F2.1 requirement 7, ADR-0021). The draft is
   validated through `/graphs/validate` like any other draft; the renderer implements no graph rule.
9. **Bundling.** The renderer imports the template files and the index as raw text at build time (the
   mechanism Storybook fixtures use for `.agents/graphs`). No network, filesystem or new bridge access is
   used at runtime.
10. **Language, accessibility, stories.** Every label in EN and PL; YAML, ids, commands and diagnostics shown
    verbatim. The picker is a modal dialog with a title, initial focus on the first entry, a focus trap that
    Escape and Cancel leave, entries as a radio group operable by arrow keys, notices in text, visible focus
    and reduced motion. Stories (EN and PL, axe clean): picker default; picker on a Windows report; picker
    without a capability report; Codex not configured; a draft from `agent-scoped-approval` showing its
    placeholder in the issues panel.

## Failure behavior

- Save dialog cancelled after choosing a template: no draft is created, the previous document is untouched.
- A dirty draft is open when "New graph" is chosen: the existing save / discard / cancel prompt runs first.
- A bundled template that does not contain exactly one `id: <template id>` line: the entry is shown as
  unavailable with a localized error; the build-time test (below) makes this unreachable in a release.
- Template run fails on Windows because `/usr/bin/printf` or `/bin/sh` is absent: the run fails as any shell
  node with a missing command does; the picker notice warned beforehand.
- Running `agent-scoped-approval` after filling the workspace in the desktop: preflight fails with the
  existing adapter-unavailable error; nothing is executed.

## Security / trust considerations

- Templates are trusted repository content, reviewed like code, yet the tests treat them as untrusted input
  and enforce S1-S7, so a later edit cannot add a destructive, network or secret-bearing template unnoticed.
- After creation the file is the person's own graph; later edits are outside these guarantees and follow the
  normal validation and Run gating.
- Creation goes through the existing grant flow; the renderer never sees a path. No template content is sent
  anywhere; no network access at build or run time.
- The agent template cannot cause a model call or spend without three deliberate steps (fill the workspace,
  add the authentication reference if needed, run from the CLI with explicit Codex flags).

## Observability

Creating a draft from a template is not an execution transition and emits no event. Runs of saved templates
emit the normal run events.

## Decisions (decided by the owner on 2026-11-15)

1. Templates live in `.agents/templates/` and are bundled into the renderer; no sidecar route.
2. Templates are POSIX-only; on Windows the picker shows a notice.
3. The agent template has a human approval before the agent node, in addition to the approval of the result.
4. `environment_refs` is left out of the agent template, with an explanatory comment.
5. The four pattern templates stand in for the roadmap's domain templates for now.
6. The renderer replaces the template's single `id:` line with a text edit (no new edit operation).

## Addendum: domain templates (implemented)

The roadmap's domain templates are now bundled after the four pattern templates (picker order:
`fix-issue`, `code-review`, `dependency-update`, `repo-audit`). They add no engine, schema, API or
edit-operation change and follow requirements 3-7 and rules S1-S7 unchanged. Each has the shape of
`agent-scoped-approval`: a `human` node approves the start (the agent's `start` input is bound from it), one
`codex` agent node has `loop.max_attempts: 3` and an embedded `reported_file_scope` gate bound from
`changed_files`, a `human` node sees the agent output, and a shell node only prints text. Each has one
`FILL` value (`workspace`) and `requires: ["git", "codex"]`; none runs unedited.

| Id | Agent node | `allowed_paths` | Human gates |
| --- | --- | --- | --- |
| `fix-issue` | `fix` (input `issue`) | `src/`, `tests/` (`REVIEW`) | `confirm_start`, `approve_fix` (summary and changed files) |
| `code-review` | `review` (input `target`) | empty: any reported change fails the gate | `confirm_start`, `read_findings` |
| `dependency-update` | `update` (input `scope`) | `package.json`, `package-lock.json` (`REVIEW`) | `confirm_start`, `approve_update` (summary and changed files) |
| `repo-audit` | `audit` (fixed `config.task`, no graph input) | empty | `confirm_start`, `read_report` |

Limits: the gate checks the files the agent reports, not the shell, network or installs Codex performs, so
the human decision after the run is the consequence gate. Commands such as an install or test run are not
templated (S1/S2 allow only printing); the prompts tell the person to run their own tests. A model review or
audit is advice, not a gate. Tests: `TestDomainTemplatesAreBoundedGatedAndReviewedByAPerson` plus the
existing corpus tests, which now cover eight templates; `desktop/test/templates.test.tsx` covers order,
index agreement, node types, EN/PL text and picker markup. The e2e entry list was updated but the e2e and
stories were not run in this change.
