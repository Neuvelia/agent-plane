# F1.6a - Correction loop for Shell nodes (addendum to F1.6)

**Status:** implemented (ADR-0018)
**Priority:** P0
**Target phase:** Phase 2 - Local IDE (vertical slice)
**Depends on:** F0.5, F1.4, F1.5, F1.6
**ADR:** ADR-0018 (accepted)

## Problem

F1.6 loops exist only for Agent producers. A deterministic demo and tests of
scoped retry without an LLM need a Shell producer that can fail a check and be
re-run alone.

## Goal

A `shell` node may declare the same bounded `loop` with one embedded Gate. A
red Gate re-executes only that node, up to `max_attempts`; green accepts once.

## Non-goals

- Correction feedback to the command (a shell command is re-run unchanged).
- Agent-only requirements (`allowed_paths`, feedback capability, scope check).
- Batch retry, replanning, workspace isolation.

## Functional requirements

1. Loop syntax, `max_attempts` bounds (1-10, default 3), embedded Gate and
   typed binding rules are exactly those of ADR-0014. Only the producer type
   rule changes: producer is `agent` or `shell`.
2. For a `shell` producer `allowed_paths` is not required and not used.
3. Each shell attempt receives `AGENTPLANE_ATTEMPT` (1-based decimal) in its
   child environment through the existing explicit environment mechanism, so
   a command can behave deterministically per attempt. No other new variable.
   The name is reserved for every shell node: it is rejected, in any letter
   case, in `env`, `env_allowlist` and as an `input_env` target. A node outside
   a loop never receives it.
4. The embedded Gate binds `candidate.outputs.PORT` from the shell node's
   declared JSON outputs, validated before binding as in ADR-0014.
5. Attempt IDs, `attempt_*` events, `gate_check` and Check Results follow
   schema 6+ unchanged; failure after exhaustion is `needs_intervention`, exit 4.
6. A non-zero shell exit is an operational failure: fatal, not retried
   (only a valid red Gate retries), exactly as for Agent.
7. Nonloop shell nodes and all existing graphs keep identical behavior and
   semantic hashes.
8. A `changed_files_scope` Gate requires an Agent producer and is rejected for a
   shell producer. Both a non-zero exit (kind `executor`) and an exhausted budget
   (kind `needs_intervention`) exit 4; they are told apart by `failure.kind`.

## Data / API contracts affected

Validation rule E_LOOP_INVALID producer type; runtime loop coordinator accepts a
shell executor; one new reserved child environment variable. Event schema is
unchanged by this addendum.

## Failure behavior

Shell producer with missing Gate or unbound required Gate input fails
validation before execution. Command exit non-zero is a fatal node failure.

## Acceptance criteria

- [x] A shell loop graph validates; a loop on a `gate` or `human` node is still rejected.
- [x] Attempt 1 red, attempt 2 green: two unique AttemptIDs, downstream runs once with the green output.
- [x] A completed sibling branch is not re-run.
- [x] `AGENTPLANE_ATTEMPT` equals 1 then 2 in the child.
- [x] Exhausting `max_attempts` yields needs_intervention and exit 4.
- [x] A non-zero shell exit is not retried.
- [x] Existing Agent loop tests and semantic hashes unchanged.
- [x] `make check` passes.

## Required tests

- Unit: validation matrix for producer types.
- Integration: red-to-green, exhaustion, non-zero exit, sibling isolation.
- CLI/e2e: `docs/examples` shell-loop graph.

## Security / trust considerations

The attempt number is the only injected value; commands stay untrusted argv.

## Observability

Same attempt/gate/check events as Agent loops.

## Open questions

- None blocking.

## Out of scope for this iteration

Feedback transport to shell, per-attempt command variants, rollback.
A test command as the loop check (exit != 0 is red) is F1.4a (ADR-0035); a
producer's own non-zero exit stays fatal.
