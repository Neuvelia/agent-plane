### Top 5 ryzyk

1. **CI od 2026-11-19 faktycznie nie wykonuje jobów.**
   - Każdy run `ci` na `main` kończy się `failure` po ok. 4 sekundach. Przykład: run 45630051909 dla `0ea4a06`, trwał 14:04:13–14:04:17.
   - Według raportu agenta audytowego GitHub nie uruchomił jobów z powodu nieudanych płatności konta. Komunikatu nie weryfikowałem bezpośrednio; widać natomiast, że run kończy się w kilka sekund.
   - Skutek: cała praca scalona po 2026-11-16 nie ma dowodu z CI, w tym F2.3 E5a/E5b, F2.6, F2.8b, F2.11, F2.12, F3.4 tasks 1–6 i F3.8. Dotyczy to w szczególności desktop e2e i Windows.
   - Status „done” dla UI opiera się dziś na lokalnych deklaracjach w specach.
2. **Gate nie może uruchomić testu, a nieudany Shell w pętli jest fatalny.**
   - Gate `command` akceptuje wyłącznie `/usr/bin/diff` (`internal/gate/config.go:58-60`; decyzja w `docs/adr/0012-gate-node-contract.md:97`).
   - Niezerowy exit Shell node'a w pętli nie jest retry'owany (`cmd/agentplane/shell_loop_test.go:130`, `TestShellLoopNonZeroExitIsFatalNotRetried`).
   - Skutek: centralny scenariusz [R] i [A], „test failuje → agent poprawia” (F1.4 AC1, exit fazy 1, Demo B, sukces MVP [A] §22), nie jest wyrażalny bezpośrednio. Demo F1.7 użyło gate'a typu diff.
3. **Zadeklarowane timeouty są cicho ignorowane.**
   - `timeout_seconds` i `limits.run_timeout_seconds` są parsowane i walidowane (`internal/domain/graph/timeout.go:8-20`).
   - Żaden plik w `internal/runtime` ich nie czyta. Eventy `cancel_requested`/`process_terminated` (`internal/domain/events/cancel.go:11-12`) ani `run.ReasonOf`/`CancelCause` nie są nigdzie emitowane ani używane poza testami (sprawdzone grepem).
   - Graph obiecuje semantykę, której runtime nie realizuje. To narusza [R] 5.1: „runtime nie powinien po cichu reinterpretować”.
4. **Walidator przepuszcza nieznany typ node'a.**
   - `type: foo` daje `graph validate` z exit 0 i komunikatem „valid”. Sonda: `Graph g: valid`, `exit=0`.
   - Przyczyna: `cmd/agentplane/validation.go:30` sprawdza konfigurację tylko dla shell/gate/agent, a `internal/domain/graph/validation.go:132` tylko pusty typ.
   - Błąd ujawnia się dopiero w runtime, z exit 4 zamiast 3. Łamie to F0.1 AC1 i F0.2 AC1.
5. **Rozjazd statusów w dokumentacji repo.** Statusy w specach i ADR nie odpowiadają kodowi, a w repo są dwa konkurencyjne źródła statusu: linie `**Status:**` w specach, `docs/roadmap.md` i szkic REL2 `docs/roadmap.json`. Przykłady:
   - F3.4 „draft, no implementation yet”, choć tasks 1–6 są scalone;
   - F3.9 „draft”, choć słownik eventów już istnieje;
   - F2.8 „F2.8b not implemented”, choć silnik jest zrobiony;
   - F1.7 „real demo pending”, choć demo wykonano 2026-11-17;
   - ADR-0027, 0028 i 0029 mają status `proposed`, a zależny od nich kod jest na `main`.

   Harness z fazy 2 ma ten problem rozwiązać. Musi przy tym rozstrzygnąć relację z REL2 (pytanie Q3).

Pozostałe istotne ryzyka:

- **brak resume (F3.3)**, przez co Demo D jest niewykonalne;
- **Shell trzyma pełny stdout/stderr w pamięci bez limitu** (`internal/shell/executor.go:277-283`);
- **`POST /runs` bez klucza idempotencji** (`internal/api/server.go:303-363`);
- **żadne e2e desktopu nie uruchamia node'a agent.**
