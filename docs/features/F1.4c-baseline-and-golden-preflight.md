# F1.4c - Baseline and golden preflight for loop checks

**Status:** draft
**Priority:** P1
**Target phase:** Phase 1 - Agent Loop (derived from F1.4, builds on F1.4b)
**Registry:** `docs/roadmap/features.yaml` entry F1.4c
**Depends on:** F1.4b, F1.6, F3.1
**ADR:** ADR-0048 (proposed)
**Issue:** #204

## Problem

A loop with a `test_command` Gate (F1.4b) spends producer attempts, and model
tokens, even when the check cannot drive a useful correction:

- **The check already passes on the untouched input.** The work is already
  done, or the check does not test the requested change. Every attempt is
  green by accident, or the agent "fixes" nothing.
- **The check is broken.** Exit 126 or 127 means the command, interpreter or
  a file it runs is missing. Every attempt is red for the same infrastructure
  reason, and the feedback misleads the agent.
- **The check cannot tell a correct change from an incorrect one.** Even a
  known-good patch does not turn it green.

The adoption analysis against `kacwojdev/agent-control-plane` showed these as
its main zero-token stop reasons (`already_satisfied`, `check_broken`,
`check_unproven`, `golden_broken`). Naming them cut its unexplained wasted
runs from 89 to 23 of 113.

## Goal

An opt-in `baseline` block on a loop classifies the check **before attempt 1**,
using no producer attempt and no model call. It stops the node with a named,
typed reason when a correction loop cannot help.

## Non-goals

- Baseline for the `command` (diff), `json_predicate` or `reported_file_scope`
  kinds. In v1 only `test_command` has a meaningful "before" state.
- Treating a green baseline as success (ADR-0048, alternative B).
- Detecting flaky checks or re-running the baseline more than once.
- Patch authoring tools. The golden patch is a file the author supplies.

## Functional requirements

1. `loop.baseline` is an optional mapping, valid only when `loop.gate` is of
   kind `test_command`. Keys:
   - `require: red` (required; the only value in v1, so the intent is
     explicit);
   - `golden_patch` (optional): a canonical absolute path to a unified diff
     file.

   Unknown keys are rejected. Without `baseline`, behavior and the graph's
   semantic hash are unchanged.
2. **Baseline run.** Before attempt 1, the runtime runs the embedded Gate once.
   It uses the producer's resolved ordinary inputs (`node.inputs.PORT`
   bindings), and every binding from `candidate.outputs.PORT` is left out.
   The Gate's `test_command` therefore runs in its configured `cwd` against the
   workspace as it is. Under `isolation: worktree` it runs in the node's fresh
   worktree.

   A Gate whose required input is bound only to a candidate output cannot
   take a baseline. That is a validation error, `E_BASELINE_NEEDS_CANDIDATE`,
   with a hint to bind a `node.inputs` port.
3. **Classification:**
   - Exit 126 or 127, or a start failure → `failed`, `failure_kind:
     check_broken`, exit 4. Producer attempts: 0. The reason holds the exit
     code, the last stderr line, and the hint "a check that runs a file the
     change adds must test for it first".
   - Any other non-zero exit → red. The loop proceeds to attempt 1 as today.
     The baseline result is recorded but is not an attempt and does not
     consume `max_attempts`.
   - Exit 0 → `failed`, `failure_kind: baseline_green`, exit 4. Producer
     attempts: 0. Reason: "check already passes before any change".
4. **Golden proof**, only when the baseline is red and `golden_patch` is set:
   1. Create a temporary linked worktree of the workspace's repository at
      `HEAD` (F3.1 machinery) and apply the patch with `git apply` (no
      `--3way`).
   2. Run the Gate there.
   3. If the patch does not apply → `failure_kind: golden_broken`.
   4. If the Gate is not green → `failure_kind: check_unproven`.
   5. If the Gate is green → proceed to attempt 1.

   The temporary worktree is always removed. The source workspace and its
   index are never modified.
5. Cancellation during the baseline or the golden run cancels the node, as in
   F1.4b FR5. Timeouts and signals are operational errors, never a
   classification.
6. Side effects of the baseline command follow the Gate's declared
   `side_effects` (ADR-0042). A `workspace_writes` check may leave files in the
   workspace before attempt 1. The spec and the event both say so.

## Data / API contracts affected

- **Graph schema:** `loop.baseline` with `require` and `golden_patch`; field
  descriptors for the inspector.
- **Events (schema bump):** a new `baseline_check` event per node run,
  carrying the version-1 Check Result of the baseline (and of the golden run
  if any) and the classification. New `failure_kind` values:
  `baseline_green`, `check_broken`, `check_unproven`, `golden_broken`.
- **CLI:** exit 4 for all four kinds. `runs show` prints the classification.
- **Desktop:** the node inspector shows the baseline result and kind as text
  (no new panel).

## Failure behavior

| Situation | Result |
| --- | --- |
| `baseline` on a non-`test_command` Gate, unknown key, relative `golden_patch` | validation error |
| `golden_patch` set but the workspace is not a Git repository | preflight error `E_BASELINE_GOLDEN_NO_GIT` |
| Patch file missing or unreadable at run time | `golden_broken` with the path, never the content |

## Roadmap criteria

F1.4c is a derived entry with no roadmap criteria of its own. It does not
change F1.4 or F1.4b criteria.

## Acceptance criteria

- [ ] F1.4c-AC1: A green baseline ends the node `failed` with `baseline_green` and exit 4.
  A counting fake producer records zero starts.
- [ ] F1.4c-AC2: A baseline check exiting 127 ends `check_broken` with zero producer
  starts and the hint in the reason.
- [ ] F1.4c-AC3: A red baseline lets attempt 1 run. The trace holds one `baseline_check`
  and `max_attempts` attempts at most (the baseline is not counted).
- [ ] F1.4c-AC4: A golden patch that turns the check green lets attempt 1 run. One that
  does not gives `check_unproven`. One that does not apply gives `golden_broken`.
  In all three cases `git status --porcelain` and the index of the source workspace
  are unchanged, and no temporary worktree remains (`git worktree list`).
- [ ] F1.4c-AC5: Without `baseline`, F1.4b tests pass unchanged and semantic hashes are
  identical.
- [ ] F1.4c-AC6: Baseline evidence is bounded and redacted as F1.4b evidence is.

## Required tests

- **Unit:** config validation; classification table (exit 0 / 1 / 2 / 126 /
  127 / start failure / signal).
- **Integration:** the loop with a counting fake producer; golden proof in a
  temporary Git repository.
- **CLI/e2e:** `agentplane run` exit code and `runs show` output for each kind.

## Security / trust considerations

- The baseline runs author code once more, with the same privileges and
  confinement as the Gate (F3.9d if declared).
- The golden patch is untrusted input. It is applied only in a throwaway
  worktree, and its content never enters events.

## Observability

- One `baseline_check` event with the classification.
- The four failure kinds are countable across runs. They are the metric for
  how many attempts the preflight saved.

## Open questions

1. Should `baseline_green` become a success ("already satisfied") that skips
   the producer? That would publish accepted outputs without a producer run,
   which ADR-0015 forbids today. Recommended: keep it a failure in v1
   (ADR-0048).
2. Should exit 126/127 inside the loop (not only at baseline) also become
   `check_broken` instead of red? Recommended: yes, as a follow-up amendment
   to ADR-0042, because a red verdict from a missing binary is never
   correctable.

## Out of scope for this iteration

Baseline for other Gate kinds, a "satisfied" success outcome, flaky-check
detection, `--3way` patch application.
