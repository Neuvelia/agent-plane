# F2.11 - Onboarding and Capability Detection

**Status:** accepted for implementation (owner decisions 2026-11-15); Go side implemented, desktop side pending
**Priority:** P1
**Target phase:** Phase 2 - Local IDE
**Depends on:** F1.1 (adapter `Detect` contract, ADR-0009), F1.2 (Codex detection, ADR-0010), F2.5 (desktop
shell and loopback API, ADR-0019), F2.5a (design system, PL/EN, Storybook), F2.1 (New graph flow)
**Works with:** F2.12 (the welcome screen's "Start from a template" action opens the F2.12 picker)
**ADR:** ADR-0025 (proposed), capability report route and DTO

## Problem

A person who installs the desktop app gets the Runs screen and no indication of what their machine can
run. Whether a graph will work depends on facts the app never shows: whether the engine sidecar started
and which version it is, whether the Git binary the engine uses exists (Agent evidence and
`changed_files_scope` need it), and whether a supported coding-agent CLI is installed and usable. Today
these facts surface only as a failed run (`codex_detection`, `codex_git`, `loop adapter is unavailable`).

## Goal

On first launch the desktop shows a welcome screen that lists, in PL or EN, what this machine can run:
the engine and its version, Git, and each coding-agent adapter the engine has, each with a status in text,
what that status means for graphs, and what still works when something is missing. The facts come from the
Go sidecar through one read-only API route forwarded by the exact allowlist; the renderer runs no process
and reads no file. Detection reuses the existing side-effect-free probes, makes no network call by
AgentPlane's action, sends nothing anywhere and stores nothing on disk. From the welcome screen the person
can start a graph from a template (F2.12), open a graph, or skip.

## Non-goals

- Running agent nodes from the desktop. `serve` has no agent adapter today (`serveExecutor` in
  `cmd/agentplane/serve.go`); enabling that is a separate feature. This spec reports Codex; it does not make
  it runnable from the app.
- Installing, updating or configuring any tool; downloading anything; opening external web pages.
- Detecting tools for which no adapter exists. **Claude Code is not detected because no Claude Code adapter
  exists in `internal/agent`**; it is neither probed nor listed (see Open questions for an optional static
  "not supported yet" row). No other CLI is probed.
- Searching `PATH` or the disk for binaries. The engine itself uses fixed paths (Git) or an explicitly
  configured absolute path (Codex, ADR-0010); detection checks exactly those, nothing more.
- Docker detection, a repository list or folder scan, a "runner self-check" that executes a graph, and
  account sign-in (all listed in the roadmap entry; deferred, see Out of scope).
- Telemetry, crash reporting, analytics or update checks of any kind.
- A settings screen. The only persisted state is the "welcome completed" flag (requirement 10).

## Functional requirements

### A. Capability report (Go sidecar)

1. **Route.** The loopback API (ADR-0019 rules: bearer token, Host check, no CORS, loopback only, unknown
   fields rejected, bodies capped at 64 KiB) adds:
   - `GET /capabilities` returns the most recent report; if none exists in this sidecar process, it runs
     detection first and returns its result.
   - `POST /capabilities/check` (empty body or `{}`; anything else is 400) runs detection again and returns
     the new report.
   Concurrent calls while detection is running join the same detection (single flight); no request starts a
   second set of probes. The report is kept in memory only and is discarded when the sidecar exits.
2. **DTO** (JSON, separate from runtime types, `version: 1`):

   ```json
   {
     "version": 1,
     "checked_at": "2026-11-15T10:00:00Z",
     "engine": {"version": "0.0.0-dev", "os": "linux", "arch": "amd64"},
     "tools": [
       {"id": "git", "kind": "tool", "status": "available", "version": "2.43.0", "reason": ""},
       {"id": "codex", "kind": "agent_adapter", "status": "not_configured", "version": "", "reason": "no_binary_configured"}
     ]
   }
   ```

   - `engine.version` is `internal/version.String()`; `os`/`arch` are `runtime.GOOS`/`runtime.GOARCH`.
   - `tools` is ordered `git` first, then registered agent adapters by id. In this iteration that is exactly
     `git` and `codex`.
   - `status` is one of `available`, `missing`, `not_configured`, `unsupported_platform`,
     `unsupported_version`, `error`.
   - `version` is set only when `status` is `available` and is the version string parsed by a strict
     pattern (at most 64 bytes, `[0-9A-Za-z.+-]`), otherwise empty.
   - `reason` is a code from a fixed set (requirement 5), never free text, raw tool output, stderr, a path or
     an environment value.
3. **Git.** The engine runs Git at the fixed path `/usr/bin/git` (`internal/gitstate`,
   `internal/runtime/workspace.go`), so detection checks that path, not `PATH`:
   - On an OS other than Linux or Darwin: `unsupported_platform`, no process is started.
   - Path absent: `missing`. Present but not a regular executable file: `error` with `reason: not_executable`.
   - Otherwise one probe `/usr/bin/git --version` with: an environment containing only
     `GIT_CONFIG_NOSYSTEM=1`, `GIT_CONFIG_GLOBAL=/dev/null`, `LC_ALL=C`; working directory the sidecar's
     temporary directory, not a repository; stdin closed; output capped at 4 KiB; a 10 second timeout with
     process termination. Output matching `^git version ([0-9][0-9A-Za-z.+-]*)` gives `available`; any other
     output, non-zero exit, timeout or overflow gives `error` with the matching reason.
   The probe takes the binary path as a parameter so tests use a fake binary; production passes
   `/usr/bin/git` only.
4. **Agent adapters.** For each adapter the sidecar is composed with, detection calls the adapter's existing
   `Detect(ctx)` (ADR-0009) and maps the `CapabilityReport` and error:
   - Codex requires an absolute binary (ADR-0010). `serve` gains an optional `--codex-bin ABSOLUTE_PATH` flag
     used **only** for detection in this iteration (agent execution in `serve` is unchanged). Electron main
     passes it only when the environment variable `AGENTPLANE_CODEX_BIN` is set to an absolute path;
     otherwise the flag is absent and Codex reports `not_configured` / `no_binary_configured` without
     calling `Detect`.
   - Mapping: `Detect` returns `Available: true` -> `available` with the reported version (a version not
     matching the strict pattern -> `error`/`unrecognized_version`); returns no error and `Available: false`
     (binary absent) -> `missing`; error kind `codex_unsupported_platform` -> `unsupported_platform`;
     `codex_unsupported_capability` -> `unsupported_version`/`missing_required_flags`; any other detection
     error, including an unrecognised `--version` response (the adapter reports it as `codex_detection`) ->
     `error`/`probe_failed`. Error text is never copied.
   - On an OS other than Linux or Darwin every adapter row is `unsupported_platform` and `Detect` is not
     called (every adapter today needs Darwin/Linux process ownership, ADR-0010).
   - The Codex probes are those of ADR-0010 (`--version`, `--help`, `exec --help`), empty environment,
     10 seconds each. No model call, no authentication, no workspace access.
   Git and adapter detection run concurrently; one full detection is bounded by the longest chain of
   probes (Codex: three sequential 10 second probes) plus process shutdown.
5. **Reason codes** (fixed set, extended only by a spec change): `""`, `no_binary_configured`,
   `not_executable`, `probe_failed`, `probe_timeout`, `output_too_large`, `unrecognized_version`,
   `missing_required_flags`, `platform_not_supported`.
6. **No side channel.** Detection emits no run event (it is not an execution transition), writes nothing to
   the run store or any file, and logs nothing about tool output. A detection failure never fails sidecar
   startup; it only shapes the report.

### B. Transport to the renderer (Electron)

7. `desktop/electron/allowlist.cjs` adds exactly `['GET', /^\/capabilities$/]` and
   `['POST', /^\/capabilities\/check$/]`. No prefix match; no other route becomes reachable. The renderer
   calls them through the existing `window.agentplane.request`; no new preload method is added for
   detection. The renderer never spawns a process, reads a path or receives a binary path. The only preload
   addition is a read-only `appVersion` string (Electron `app.getVersion()`), shown on the Engine row next to
   the engine version (owner decision 6); no compatibility check is made between the two.
8. Electron main adds `--codex-bin` to the `serve` argv only as stated in requirement 4 and never logs it.

### C. Welcome screen (renderer)

9. **Content.** A welcome screen with:
   - a heading and two sentences on what AgentPlane does (local, graphs of shell/agent/gate/human nodes,
     nothing leaves the machine);
   - a **capability list**: one row per report entry plus an "Engine" row. Each row shows the name, a status
     word and glyph (never colour alone), the version when known, a one-sentence meaning, and for any status
     other than `available` what still works and what to do (requirement 11);
   - a "Check again" button that calls `POST /capabilities/check`;
   - actions: "Start from a template" (opens the F2.12 picker; until F2.12 ships it opens the plain New graph
     flow), "Open a graph" (existing `openGraph()`), and "Skip".
10. **First run.** The screen opens on launch when the renderer has no record that it was completed. Choosing
    any action marks it completed. The flag is stored in renderer `localStorage` under
    `agentplane.welcome.v1` (same mechanism as the F2.5a language preference). If storage is unavailable
    the screen opens on every launch and can still be dismissed for the session; no error is shown. The
    screen is always reachable later from a "Welcome and setup" entry in navigation.
11. **Missing-tool guidance** (static localized text, no links, no commands are run):

    | Row / status | Meaning shown | What still works |
    | --- | --- | --- |
    | Engine not connected (existing connection state) | The engine did not start or stopped; nothing can be validated or run | Nothing; the existing connection-lost state and its guidance apply |
    | Git `missing` / `error` | Agent nodes and `changed_files_scope` checks cannot record Git evidence | Shell, gate and human graphs |
    | Git `unsupported_platform` | Git evidence is supported only on Linux and macOS | Shell, gate and human graphs |
    | Codex `not_configured` | No Codex binary was given to the desktop engine; agent nodes run from the CLI with `--adapter codex --codex-bin` | Everything except agent nodes in the desktop |
    | Codex `missing` | The configured Codex binary does not exist | As above |
    | Codex `unsupported_version` | This Codex lacks a flag or version AgentPlane needs (ADR-0010) | As above |
    | Codex `unsupported_platform` | The Codex adapter needs Linux or macOS | As above |
    | Codex `available` | Codex was found. Running agent nodes from the desktop is not available in this version; use `agentplane run` | Everything; agent nodes through the CLI |
    | any `error` | Detection could not finish; the reason code is shown as received | As for `missing` |

    Commands, flags, ids, versions and reason codes are shown verbatim, not translated.
12. **States.** Loading (first detection running: rows show "Checking..." and the list is `aria-busy`),
    loaded, request failed (an error with Retry; never an empty or guessed list), engine disconnected
    (rows not shown; the connection state explains), and re-checking (previous report stays visible and is
    marked as being refreshed).

### D. Language, accessibility, stories

13. Every label, meaning and guidance sentence exists in `i18n/en.ts` and `i18n/pl.ts` with identical keys
    and parameters. Initial language follows F2.5a.
14. The screen has one `h1`, the capability list is a list with each row's status in text, focus moves to
    the heading when the screen opens, completion of a check is announced through a polite live region,
    every action is a native button reachable by keyboard, focus is visible, reduced motion is honoured, and
    nothing is conveyed by colour alone.
15. Stories (EN and PL, axe clean, recorded fixtures through the in-memory bridge): all available; Git
    missing; Codex not configured; Codex unsupported version; Windows (`unsupported_platform` for both);
    detection error; checking; re-checking; request failed; engine disconnected.

## Data / API contracts affected

- New loopback routes `GET /capabilities` and `POST /capabilities/check` and the version-1 capability DTO
  (requires the ADR named in the header; ADR-0019 is referenced, not changed).
- New optional `agentplane serve --codex-bin ABSOLUTE_PATH` flag (detection only).
- Electron: two allowlist rules; main reads `AGENTPLANE_CODEX_BIN`; preload gains the read-only `appVersion`
  value, no new method.
- Renderer: new welcome screen, i18n keys, `localStorage` key `agentplane.welcome.v1`.
- Unchanged: graph schema, event schema, run store, `agentplane run`, adapter interfaces, `codex.Adapter`.
- Docs: `desktop/README.md`, `desktop/electron/AGENTS.md` and `internal/api/AGENTS.md` updated for the new
  routes and flag.

## Failure behavior

- A probe that times out, exits non-zero, overflows or prints an unrecognized version yields a row with
  `status: error` and a reason code; the other rows are unaffected and the route still returns 200.
- A panic or unexpected error inside detection is recovered into `error` rows; the sidecar keeps serving.
- `--codex-bin` given but relative: `serve` exits with a usage error before announcing its port (consistent
  with `run`); main does not pass a relative value.
- Sidecar unavailable: the renderer shows the existing connection-lost state; the welcome screen shows no
  capability rows rather than stale ones.
- `POST /capabilities/check` while a check runs joins it and returns its result.
- `localStorage` unavailable: see requirement 10.
- An unknown `status` or `reason` from a newer engine is shown verbatim with a neutral glyph, never mapped to
  `available`.

## Acceptance criteria

- [ ] `GET /capabilities` returns a version-1 report whose `tools` ids are exactly `["git", "codex"]` in that
      order, with `engine.version` equal to `agentplane version` output (Go API test).
- [ ] With a fake Git binary printing `git version 2.43.0`, the Git row is `available` / `2.43.0`; with no
      binary `missing`; with a non-executable file `error`/`not_executable`; with a fake that sleeps past the
      timeout `error`/`probe_timeout` and the process is gone afterwards; with 8 KiB of output
      `error`/`output_too_large`; with `hello` `error`/`unrecognized_version` (Go unit, Linux CI).
- [ ] The fake Git binary records its argv and environment: argv is exactly `--version`, the environment is
      exactly the three variables of requirement 3, and its working directory is not inside the repository
      (Go unit).
- [ ] Without `--codex-bin`, Codex is `not_configured`/`no_binary_configured` and `Detect` is not called
      (counting fake adapter); with the existing Codex fake CLIs, each `Detect` outcome maps to the status of
      requirement 4 (Go unit, reusing `internal/agent/codex` fakes).
- [ ] Ten concurrent `POST /capabilities/check` calls start exactly one set of probes (counting fake, explicit
      synchronization, no sleeps) and all return the same `checked_at` (Go unit).
- [ ] No report field contains an absolute path, an environment value or raw probe output: a test runs
      detection with fakes whose output and path contain a marker string and asserts the serialized report
      does not contain it (Go unit).
- [ ] Detection writes nothing: the store directory and the sidecar's temp directory have the same listing
      before and after a check, and no run event is emitted (Go API test).
- [ ] The capability package imports no `net` or `net/http` package (Go test over `go list -deps`), and the
      renderer welcome code contains no `fetch`, `XMLHttpRequest`, `WebSocket` or `EventSource` (static test).
- [ ] `allowlist.test.ts`: the two routes are allowed with the exact methods; `GET /capabilities/check`,
      `POST /capabilities`, `/capabilities/`, `/capabilities/../runs` and `/capabilitiesx` are refused.
- [ ] With empty `localStorage` the welcome screen opens on launch; after "Skip" a relaunch opens the Runs
      screen; with `localStorage` throwing, the screen opens and "Skip" closes it without an error (renderer
      unit and e2e).
- [ ] e2e on Linux CI (real Electron and sidecar under xvfb, no `AGENTPLANE_CODEX_BIN`): the welcome screen
      shows the Engine row with the sidecar version, Git with a status from the fixed set, Codex
      `not_configured`; "Check again" completes and the live region announces it; the whole flow is done
      with the keyboard only.
- [ ] Every status and reason in requirements 2 and 5 has EN and PL text; catalogue test passes; the stories
      of requirement 15 exist, EN and PL, zero axe violations, no external requests.
- [ ] Native verification recorded in the PR for Linux and macOS with a real Git (and, where installed, a
      real Codex given through `AGENTPLANE_CODEX_BIN`), and for Windows showing `unsupported_platform` for
      Git and Codex without any probe process started.
- [ ] `make check`, `npm run check` in `desktop/`, `make desktop-e2e` and the story run pass.

## Security / trust considerations

- Tool output is untrusted: only a version string matching a strict pattern leaves the probe; everything else
  is reduced to a reason code. Nothing from a probe is logged.
- Probes use a fixed path or an explicitly configured absolute path, structured argv, a minimal explicit
  environment, closed stdin, bounded output and time, and terminate their process (AGENTS.md process rules).
  No `PATH` lookup and no ambient environment.
- Detection does not contact the network and sends nothing anywhere. AgentPlane cannot guarantee what a
  third-party binary does when asked for `--version` or `--help`; the probes are the minimal ones the engine
  already runs before an agent node (ADR-0010) and run with no credentials or `HOME` in their environment.
- The renderer receives no path, token or environment value. The new routes are read-only and reachable only
  through the exact allowlist; they cannot start a run or a model call.
- No telemetry, no persisted report, no identifiers. The only persisted value is the welcome flag in renderer
  storage.

## Observability

Detection is not an execution transition and emits no run event. The report carries `checked_at` and reason
codes so the state the person saw is explainable. API errors are structured as in ADR-0019.

## Decisions (decided by the owner on 2026-11-15)

1. The capability route has its own ADR: ADR-0025.
2. Codex is configured for the desktop only through `AGENTPLANE_CODEX_BIN` (an absolute path); no file dialog
   and no `PATH` lookup.
3. Claude Code is left out: no row and no probe, because no adapter exists.
4. Windows shows `unsupported_platform` for Git and Codex, and no probe process is started.
5. The first-run flag lives in renderer `localStorage` (`agentplane.welcome.v1`).
6. The welcome screen shows the desktop app version beside the engine version. A desktop/engine mismatch
   warning is later work.
7. Docker detection, a repository list and a runner self-check move to a later spec.
