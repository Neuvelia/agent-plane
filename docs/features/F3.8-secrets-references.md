# F3.8 - Secrets References

**Status:** implemented for the `env` provider and Shell nodes (event schema 14). Not done: Agent `secret_env`,
the `local`/keychain provider, policy-driven denial and enforcement (F3.9), and the two acceptance criteria
that are only partly covered (7 and 15; 16 of 18 are ticked), and the `...Enforce` variant of criterion 10, which
waits for F3.9. ADR-0029 accepted on 2026-11-26 (shared with F3.9).
**Priority:** P0
**Target phase:** Phase 3 - Local Production Ready
**Depends on:** F1.1 (adapter contract), F1.2 (Codex adapter), F3.1 (workspace isolation, ADR-0024)
**Designed with:** F3.9 (execution policy). The two specs share one ADR and one preflight pipeline; read
`F3.9-execution-policy-v0.md` before implementing either.

## Problem

Tarmind (in code today: agentplane) runs commands and coding agents that need credentials (a Git token, an API
key). Today there is no supported way to give a node one. The only paths are ones that bypass every control:

- `env: {TOKEN: "..."}` in a Shell node puts the raw value in the graph file, which the store copies to
  `graph.yaml` (ADR-0019).
- `env_allowlist` (Shell) and `environment_refs` (Agent) copy an ambient runner variable into the child. They
  work, but nothing marks that variable as secret, so it appears in events unless the user also remembered
  `--redact-env NAME` (F0.6, F0.7, `serve --redact-env`).
- `--input key=value` and `--record-values` carry values into events; ADR-0023 redacts configured values before
  truncation, but only values the user listed by hand.

Redaction is therefore opt-in per variable and unrelated to which node may use the value. A node can receive a
credential it was never assigned, and a credential can reach an event, `graph.yaml` or a recorded value without
being known to the redactor.

## Goal

A graph names secrets by reference only. The runner resolves them at run time, hands each value only to the
node runs that were explicitly assigned it, redacts every resolved value (exact bytes plus the encoded forms of requirement 10) from events, progress,
evidence, recorded values, CLI results and node output, and refuses to start the run when a reference cannot be
resolved. Redaction is best effort, not a guarantee. The design intent is that the preflight that checks the
execution policy (F3.9) also decides whether a secret may be delivered, so that secret resolution cannot bypass
policy; the policy stage does not exist until F3.9.

## Non-goals

- A central or cloud secrets vault, sharing secrets between users, rotation, expiry, audit export (Team tier).
- Resolving secrets from the OS keychain in this iteration (see Decision 1; the provider port makes it a
  drop-in).
- Secrets for Gate, Human or embedded-loop Gate processes. Only Shell and Agent nodes may hold a grant.
- Delivering secrets by argv, file or prompt text. Environment variable only.
- Protecting a secret from the process it was granted to. A granted child can read, transform, store or send
  its own secret; the controls are limiting who gets it (assignment), where it can go (F3.9 network and path
  policy), and detecting leaks into recorded output (redaction and the workspace scan).
- Preventing an Agent from reading other secrets on the machine (files under the user's home, other
  environment). Read confinement is out of scope for F3.9 v0 as well.
- Renaming code identifiers, flags or file formats from `agentplane` to Tarmind.

## Functional requirements

### A. Graph surface

> Requirement numbers run 1-15 across sections A-E, but section B repeats number 5 (kept so that existing citations
> stay valid). Cite them as A.5 (flows to Agent) and B.5 (resolution) where the number alone is ambiguous.

1. A graph may declare an optional top-level `secrets` mapping from a secret name to `{secret_ref: <ref>}`:

   ```yaml
   secrets:
     gh_token:
       secret_ref: env/GITHUB_TOKEN
   ```

   Names match `[a-z][a-z0-9_]{0,63}`. A secret entry has exactly one field, `secret_ref`; any other field,
   including a value, fails validation naming the secret. `secrets` is semantic content: a graph without it keeps
   its semantic hash byte for byte.
2. A `secret_ref` is `<provider>/<name>`: provider `[a-z][a-z0-9-]{0,31}`, name 1-128 printable ASCII characters
   with no `/` and no whitespace. `env` is the only provider implemented. `local` is reserved for the OS keychain
   and is reported as "provider not available" until implemented. Unknown providers fail validation.
3. A Shell or Agent node (Agent deferred, see the Deferral note under Acceptance criteria) assigns secrets with `config.secret_env`, a mapping from a child environment variable
   name to a declared secret name:

   ```yaml
   config:
     secret_env: {GH_TOKEN: gh_token}
   ```

   A node receives exactly the secrets named there and no others. A secret name that is not declared, a
   duplicate or invalid environment name, a name that collides case-insensitively with `env`, `env_allowlist`,
   `input_env` or `environment_refs`, or `secret_env` on a Gate, Human or other node type fails validation naming
   the node. The graph never contains a value.
4. Graph defaults cannot assign secrets. Only a node's own `config.secret_env` grants.
5. Any Agent node reachable over data edges from a node with a non-empty `secret_env` fails validation with
   `E_SECRET_FLOWS_TO_AGENT`, whether the edge is direct or runs through other nodes. No node type is a barrier:
   shell, gate, human and agent nodes all propagate, because any of them can pass a value on. Reason: accepted
   output is immutable and reaches downstream nodes raw (result redaction applies only to the presented copy), and an
   Agent's inputs are rendered into a prompt sent to a remote model. One error is reported per (source, Agent)
   pair, on the shortest path (ties by edge order), in source, Agent, first-edge order. A direct edge names both
   nodes and the edge; a longer path names the node ids along the path (`a -> b -> agent`) and the first edge,
   never a value or an out-of-grammar variable name. The remedy is to remove the edge, route the data through no
   secret-holding node, or remove `secret_env`. An empty `secret_env: {}` assigns nothing and does not trigger
   the rule. Decided by the product owner after the review of PR #167 (direct) and PR #169 (transitive).

   **Remaining gaps, not covered because they are not data edges.** (a) Shared workspace: a Shell node with a
   secret can write a file that an Agent in the same workspace then reads. Detecting that after the fact is the
   job of the workspace scan (requirement 13); it is detection, not prevention. (b) The approval context a
   `human` node shows is redacted but not rejected by this rule. Measured on the 18 graphs in the
   repository (`.agents/graphs` 3, `.agents/templates` 8, `docs/examples` 4, `desktop/test/fixtures` 3): none uses
   `secrets` or `secret_env`, so the rule rejects none. Graph input bindings and graph outputs do not carry node
   output into another node's input, Gate bindings and loop feedback stay inside one node, and units add no data
   path beyond edges.

### B. Resolution and preflight

5. Resolution happens once per run, in the runner process, after graph validation and after the execution policy
   has been evaluated (F3.9 requirement 9; until F3.9 there is no policy stage, so resolution follows validation
   directly), and before `run_started`. A reference is resolved only if at least one
   node's effective policy admits receiving it. A declared but unassigned secret is not resolved.
6. Every static failure is a preflight error with the existing `PreflightError` diagnostics shape, emits no
   events, and names the secret, the node and a correction:
   `secret_unresolved` (provider returned not found), `secret_empty` (resolved to an empty string),
   `secret_provider_unavailable` (no provider in the runner, or the provider failed; its error text is never
   shown), `secret_invalid_value` (contains NUL; or is not valid UTF-8 when the run rewrites redacted text as
   JSON: an observed executor, `--record-values` or attempt diffs), `secret_delivery_unsupported` (the
   executor does not declare the `SecretReceiver` capability for the node type, so the value would be dropped;
   fail closed, see below), `secret_policy_denied` (F3.9 denies delivery; not emitted by the F3.8 code), `E_SECRET_AMBIENT_BYPASS`
   (requirement 11; the validator's existing code, reported by graph validation before the secret stage).
   Messages name the secret and the node, never the environment variable behind the reference, a value, its
   length or provider error text. Static findings (delivery, missing provider) are reported together before
   any secret is read; value findings are reported for every failing secret in name order.
7. Resolved values live only in process memory. They are never written to `Options` structures that are
   serialized, to events, to the store, to the loopback API, to error strings or to logs. Resume (F3.2) must
   re-resolve; the store never holds them.
8. The `env` provider reads `os.LookupEnv(name)` from the runner at preflight. Environment names are compared
   case-insensitively for collision checks on every OS (as `input_env` already does) and looked up exactly as
   given.

### C. Redaction

9. Every resolved value is added to the run's redaction set automatically, in addition to `--redact-env` values,
   before any executor starts. The existing redactor semantics hold: streaming, undecided-tail, secret-absent
   marker. Redaction applies to events, progress, evidence, recorded values, error strings that reach events,
   Check Result evidence and CLI/API output.
    The run result is redacted at its single presentation point (`runMachine.snapshot`): string and
    artifact-reference outputs have secret bytes replaced by the marker; number, boolean and JSON outputs are
    never rewritten and are withheld (`redacted: true`, `value: null`, declared type kept) when masking would
    change their text or a decoded JSON string spells a secret (the `value_recorded` rule); a mask that is not
    valid UTF-8 also withholds. `Failure.Err` text is masked; `errors.Is` still reaches the cause and `errors.As` reaches only a masked copy
    of `shell.ExecutionError`/`agent.ExecutionError` (stdout, stderr and cause text masked), and only the first such type in the chain, not types it wraps;
    `Diagnostics` carry no values and are not rewritten. Accepted outputs used by downstream nodes stay raw. The
    same set includes `--redact-env` values, so `--redact-env` now also masks graph outputs; `cli_schema_version`
    stays 1 because `redacted` is additive. With no secrets and no `--redact-env` the result and JSON are
    byte-identical to before.
10. Besides the raw bytes, the set includes, for each secret of at least 8 bytes, the hex (lower and upper case)
    and percent-encoded forms and the standard and URL-safe Base64 forms. A secret inside a larger Base64 blob
    encodes differently for each of three byte offsets modulo 3, so Base64 is covered for all three alignments
    (the stable characters of each, excluding padding and boundary characters that depend on neighbouring
    bytes). These are defense in depth, not a guarantee: other encodings, hashes, truncations and splits are
    not recognized (see Security).
    The set is bounded to 64 secrets of at most 16 KiB each (up to 16 forms per secret). Decided 2026-11-17 (lead, delegated by the product owner); the team may revisit.
    Exceeding either bound fails at preflight with a structured error naming the secret name and the bound
    (`secret_redaction_bound_exceeded`), never a silent skip (test `TestPreflightRedactionBoundFailsLoudly`).
11. `E_SECRET_AMBIENT_BYPASS`: if a variable named by an `env`-provider reference is also named in any other
    channel of a node that is not assigned that secret (`env_allowlist`, `environment_refs`, `env` key,
    `input_env` target), preflight fails in every mode, audit included. This is a correctness rule, not an
    enforcement level: audit is the default and must not let an unassigned node receive the value. It closes
    the route of copying a secret's backing variable around the assignment.
12. The graph bytes, the parsed graph definition, the `--input` values and any recorded graph input must not
    contain a resolved value; the run fails in preflight, after the secrets are resolved and before
    `run_started`, so the store never copies the graph (`graph.yaml` is written with the first event). The check
    compares raw bytes only (encoded forms are the redactor's concern), also finds a value hidden by YAML
    escapes, folding or a map key, and runs with or without `--store-dir`, in `run` and `serve`. Findings are
    preflight diagnostics `secret_value_in_graph` (location `graph`) and `secret_value_in_input` (location
    `inputs.<key>`, or `inputs` when an input name holds the value), ordered by secret name and then location;
    they name the secret and the location, never the value, a fragment or its length. `--input` is not compared
    with `--redact-env` values, and the existing `--redact-env` graph check keeps its message, exit code, timing and
    its condition on `--store-dir`. Known gap: a secret that is declared but assigned to no node is not resolved
    (requirement B.5), so its value embedded in a graph is not detected. A short secret value matches any text that
    contains it and may refuse an unrelated graph; the refusal is deliberate (fail loud).

### D. Detection in the workspace

13. After an Agent or Shell node that has a grant ends, the runtime scans the files the node changed (the F1.8
    Git-observed set, or the isolated worktree diff of F3.1) for the raw granted values, bounded to 256 files and
    8 MiB per file, 32 MiB total. A hit produces a red Check Result of kind `secret_in_workspace` naming the path
    and the secret name, never the value, and the node outcome follows the node's policy mode (F3.9). Where Git
    evidence is unavailable (Windows today) the scan reports `unobserved`. This is detection, not prevention. The scan
    never follows the final path component (a symlink's own target text is scanned; files are opened with
    `O_NOFOLLOW` and checked with `SameFile`). Ancestor directories are checked before the open, so it is best
    effort against a concurrent hostile writer in the same workspace: swapping a directory in between can expose
    only a path and a secret name. The 32 MiB budget is counted per file, so a smaller file after a refused larger
    one is still scanned.

    Runtime wiring. The runtime opens one scan window per node run through the `WorkspaceScanner` port
    before the first attempt and scans once after the last one, in the worker goroutine, so the scan reads the
    final state of the workspace: a value written in attempt 1 and removed in attempt 2 is not reported (detection
    of state, not of history). The changed set is Git-observed (F1.8) and includes ignored files, because a leaked
    token usually lands in an ignored `.env`. Only the raw granted values are searched, with no length threshold.
    The result is one node-run scoped Check Result (no `attempt_id`, so it never replaces an attempt's Gate check or
    `attempt_finished.check_id`) emitted before `workspace_integrated` and `node_finished`:
    red `secret_found_in_workspace` (one evidence entry per path and secret, `path` and `secret_name`, at most 31
    plus an `omitted` marker), green `no_secret_in_changed_files`, green `secret_scan_incomplete` (a limit or an
    unreadable path left gaps) or green `secret_scan_unobserved` (no Git evidence, a failed scan, or no scanner
    configured). Every path is passed through the run's redaction set before it is recorded, because a path is
    untrusted text and can spell the value. A node without a grant causes no scanner call and no event; a cancelled
    run is not scanned. Until F3.9 adds a policy mode the red result is an audit fact only: it does not change the
    node or run outcome, so a leaked value in a changed file can still be integrated from an isolated worktree.
    Known limits: a Shell `cwd` below the repository root is `unobserved` in v0; two nodes sharing a workspace see
    each other's changes; encoded forms (hex, Base64) are not searched. A file that is not a regular file (FIFO, device, directory) is always reported as `not_regular_file`, never read.

    Remaining gaps for F3.9. (1) Attribution in a shared workspace: the changed set is the whole workspace delta
    between `Begin` and `Scan`, so two granted nodes running in one repository can each see the other's files and
    both receive a red result for a secret only one of them wrote. F3.9 in enforce mode must resolve attribution
    before it blocks a node on this check. (2) The `reason` of a red result is `secret_found_in_workspace`, while the
    schema 14 fixture uses `secret_in_workspace_violation`; unify them when F3.9 defines the policy reasons. (3) If a
    window is still open when the coordinator finishes a node (the worker expected a retry that was not scheduled),
    the result is green `secret_scan_unobserved` with reference reason `scan_not_completed`.

### E. Observability

14. (Not implemented; depends on F3.9, which emits the event.) The `policy_evaluated` event (F3.9) carries a `secrets` section per node run: assigned secret names, provider,
    env variable name and `resolved: true`. It carries no value, length, hash, prefix or suffix.
15. Redaction-set size is reported as a count only.

## Data / API contracts affected

- Graph schema: additive optional top-level `secrets`; additive `config.secret_env` for `shell` (and `agent`, deferred: `E_SECRET_ENV_AGENT_UNSUPPORTED`)
  (registered in each executor's `ConfigFields`, so the desktop editor shows them). No `schema_version` bump
  proposed (Decision 4).
- Events: one new section inside the F3.9 `policy_evaluated` fact. The event schema bump is shared with F3.9:
  event schema 14 (`events.SchemaVersion`, constant `SchemaPolicy`; F2.8b = 12 and F3.4 = 13,
  Decided 2026-11-17 (lead, delegated by the product owner); the team may revisit). Older readers see none of it.
  As implemented by F3.8, schema 14 defines the `policy_evaluated`/`policy_violation` shapes and validators but
  nothing emits them yet; the facts F3.8 actually emits are the node-run `secret_in_workspace` Check Results.
- CLI: no new flag for resolution. `--redact-env` is unchanged and still additive.
- Runtime: consumer-owned port `runtime.SecretResolver` composed by the CLI, like `WorkspaceManager` (ADR-0024);
  the architecture test must prove providers are imported only by the composition root.
  `Options.SecretResolver` is nil in a runner without providers. An executor declares it can deliver secrets
  with the optional `runtime.SecretReceiver` (`ReceivesSecrets(nodeType) bool`); a graph that assigns a secret
  to a node type the executor does not receive fails preflight with `secret_delivery_unsupported`, so a value
  is never silently dropped. The preflight keeps resolved values only in memory: in the run's redaction template
  and in the per-node secret environment (`secrets.Env`) that the scheduler hands to the node process.
- Persistence: none. Nothing about a secret value is stored.

## Failure behavior

- Missing, empty or unavailable secret: preflight error, no events, non-zero exit; message names the secret name
  and the node (not the value, and not the variable behind the reference).
- A secret value that cannot be redacted safely (no safe marker byte, invalid UTF-8 with an observed executor):
  preflight error, never a silent skip.
- Provider returns different values on a second read in the same run: not possible, values are resolved once.
- A secret appears in a node's output: replaced by the marker in events, progress, evidence and results (the exact
  bytes, plus the hex, percent-encoded and Base64 std/URL forms in all three alignments for secrets of at least 8
  bytes; shorter secrets are matched raw only); the run is not failed for that alone. The workspace scan
  (requirement 13) records a red Check Result and, until F3.9, changes no node or run outcome; a node fails on it
  only in F3.9 enforce mode.
- Cancellation or crash: the in-memory values are discarded with the process; no cleanup of persisted state.

## Security / trust considerations

- Graph definitions, environment values and provider output are untrusted. A hostile graph can name any
  `env/...` variable of the runner; the preflight permissions report (F3.9) must list every assigned secret so
  the user consents before running, and enforce mode can deny delivery (requirement F3.9-9).
- Delivered by environment only: argv is visible to other local users on many systems and is more likely to be
  echoed by tools.
- Redaction is exact-byte matching plus listed encodings. A child that hashes, truncates, reorders or encrypts
  its secret defeats it. Say so in the CLI help and docs; do not call redaction a guarantee.
- A secret granted to an Agent is visible to the model-driven process. The model can print it or send it over the
  network unless F3.9 network policy forbids it; the Codex sandbox's treatment of secret-looking variable names
  is unverified and is a spike item (Decision 6).
- Secret values must never appear in worktree names, refs, event paths, error strings, evidence or panics. Wrap
  provider errors without including values.
- No network is used by the `env` provider. A future keychain provider launches a fixed OS tool with structured
  argv, a bounded timeout and bounded output, and never a shell string.

## Decisions on the open questions

Decided by the product owner for the F3.8 closure. The code matches each decision unless stated.

1. **Keychain provider.** `env` only. `local` stays reserved and reports as unavailable
   (`E_SECRET_PROVIDER_UNAVAILABLE` at validation, `secret_provider_unavailable` at preflight). The OS keychain is
   F3.8b.
2. **Encoded forms.** Included (requirement 10), as defense in depth only. Searching the workspace for encoded
   forms is not done (the scan looks for raw values).
3. **Minimum length.** Any non-empty value is accepted. v0 emits no warning below 8 bytes; such a value gets its
   raw form only (`TestFormsShortValueRawOnly`). A very short secret (1-3 characters) is redacted wherever those
   characters occur in unrelated text and makes the resolved-value guard refuse unrelated graphs (fail loud); this is a
   deliberate v0 trade-off.
4. **Schema versioning.** Additive, no graph `schema_version` bump.
5. **`serve`.** Reads its own process environment when a run starts; it is read-only for secret declarations and
   bindings, and no route creates, edits or returns them. Operations that would change a binding are refused with
   `secrets_read_only`. Known limitation: `PUT /graphs/save` writes text, so a client holding a write grant can
   still save any YAML (ADR-0021 annotation); the file holds references only, never values.
6. **Codex spike.** Not run. `secret_env` on an Agent node is rejected with `E_SECRET_ENV_AGENT_UNSUPPORTED`.

Further decisions recorded during implementation:

- A value must be valid UTF-8 when the run rewrites redacted text as JSON (an observed executor, `--record-values`
  or `--record-diffs`); otherwise preflight fails with `secret_invalid_value`.
- The validator's code `E_SECRET_AMBIENT_BYPASS` stays as the name of the ambient-bypass rule.
- `SecretReceiver` and `secret_delivery_unsupported` need no new ADR; ADR-0029 decision 11 records them.
- `E_SECRET_FLOWS_TO_AGENT` is transitive and has no barrier node type (requirement A.5).
- The workspace scan budget (32 MiB) is counted per file that is read, so a smaller file after a refused larger one is
  still scanned.
