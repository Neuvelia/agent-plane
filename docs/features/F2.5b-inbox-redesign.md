# F2.5b - Inbox: triage queue (desktop redesign, step 1)

**Status:** implemented
**Priority:** P1
**Target phase:** Phase 2 - Local IDE
**Registry:** `docs/roadmap/features.yaml` entry F2.5b (derived from F2.5)
**Depends on:** F2.5, F2.5a, F2.9, F2.10
**ADR:** ADR-0046 (replaces F2.5a requirement 11; presentation only, no event, API, persistence or trust-boundary change)
**Design source:** Tarmind Dashboard UX canvas, artboard "Inbox: triage queue" (dark). The
light variant of the canvas is not implemented (light theme stays a non-goal of F2.5a).

## Problem

The F2.5a Dashboard spreads what needs a person over four cards (Needs attention, Active runs,
Outcomes, Quick actions). Every row only links to the run inspector, so deciding an approval or
understanding why a run stopped always means leaving the screen. The revised design turns the
landing screen into a triage queue: the queue on the left, the selected item with its evidence and
its action on the right.

## Goal

The landing screen is the **Inbox**. It lists everything that needs a person or is still running,
grouped and filterable, and shows the selected item with the facts its events recorded. A pending
approval is decided in place. This is the first screen of the desktop redesign; the other screens
of the canvas follow as separate steps.

## Non-goals

- Any change to the Go sidecar, HTTP API, event schema, run store or Electron preload surface.
- The global search entry of the page header (there is no command palette), resume of an interrupted run, and the light theme.
- An account name in the profile row (there are no accounts; the row says "Local profile").
- Per-file `+/-` line counts and diffs in "What changed" (no backing contract in the inbox; F2.8b
  diffs are opt-in and shown elsewhere).
- Any execution, retry or state rule in the renderer.

## Functional requirements

1. The Sidebar entry "Dashboard" becomes "Inbox" (PL "Skrzynka"), with the same position and the
   same role as the landing screen after the first-run welcome.
2. The queue is built from the two lists the API already serves (`GET /runs`, `GET /approvals`):
   *Waiting for you* (pending approvals), *Stopped* (runs with status `failed` or `interrupted`) and
   *Running* (runs with status `running`), in that order, newest first inside a group. A running
   run that waits for a listed approval appears once, as the approval. Succeeded and cancelled
   runs are not queued.
3. Filters All / Approvals / Stopped / Running are flat toggle buttons with their counts; a filter
   that leaves nothing shows a sentence, not an empty pane.
4. Each queue row shows a status shape (diamond, cross, pause, spinner) and its name in words, the
   graph ID, a mono sub-line (node and short run ID, or the run status and short run ID) and the age
   since the run started. An approval has no timestamp of its own and is dated by its run.
5. The header shows the localised date and the newest 14 runs as a strip (one bar per run; the bar
   shape and colour depend on the status) with a sentence "N of M recent runs succeeded" and an
   accessible description of the strip.
6. The detail pane reads the selected run's event stream (`useRunStream`, the same reducer as the
   run inspector) and shows:
   - approval: the prompt as the headline; *What changed* and *Evidence* from the F2.10 approval
     context (`approvalContext`: the direct dependencies of the human node, the check and the
     Git-observed files of each one's last attempt, at most 10 files each with the rest counted;
     unobserved files are not shown as "0"); then the context items of the request;
   - failed: the node it stopped at, its attempts with each check reason and outcome, and the last
     failure (check reason and the last 24 lines of its evidence output, or of the node log);
   - interrupted: the accepted nodes ("kept in the event log"), the nodes that stopped and their
     attempt, the last durable event sequence, and that resume is not available;
   - running: every graph node in graph order with its status, recorded or elapsed time, the
     attempt while retrying and the upstream nodes it waits for.
7. Decision bar of an approval: an optional reason (max 2048 characters), Reject (danger) and
   Approve (primary). The decision is shown as applied only when `approval_decided` arrives on the
   stream; a `409` counts as already decided (as in F2.10). Both buttons are disabled while the stream
   is lost or the run cannot be read (not found, or written by a newer engine), with the reason shown.
   After a decision taken on this screen the item stays selected and open with its decision and offers
   Next, even when the list drops it first. Once its events record `approval_decided` it also stays in
   the queue, dimmed, with that decision and counted in its group, until the screen is left; a dropped
   approval whose decision has not arrived is not queued, so it never looks pending (a decision
   event that arrives before the request answers is kept). Limit: if the person opens another item
   before the decision event arrives, nothing observes it and the row leaves the queue once the list
   drops it. While a held row is queued, the same run can also have a row of its own: a rejected run
   appears under Stopped, an approved one that continues under Running. A decision taken elsewhere
   (CLI, Approvals screen) is shown in the detail but not held in
   the queue. Next goes to the first item in view not decided here and is absent when none is left.
   The detail never swaps under the person: the item shown stays shown until they pick another or it
   leaves the queue. A failed run stopped by a rejected human gate shows that decision and its
   comment. After the person's own decision, the recorded decision is announced in an always-mounted
   `role="status"` region and focus moves to Next; after Next the new item's headline takes focus once.
   Opening an item decided earlier moves focus nowhere and announces nothing. While the lists cannot be
   read, the selection does not move. Other items
   offer Copy summary (kind, headline, sentence, graph and run ID to the clipboard) and Open run.
8. New run lives in the Sidebar. With an empty queue the detail pane says that nothing needs the
   person and offers New run, Open graph and All runs; when only the filter leaves nothing, it says so
   instead.
9. Loading and engine-unreachable states replace the queue, as on every screen that reads lists.
10. Layout: full-bleed under a single 44px page header (page title left, connection right, a hairline
    below; shared by every screen); two columns (queue 320-400px, hairline between); below 900px the
    queue stacks above the detail. Buttons follow the canvas: flat, 8px radius, one silver primary. Text
    stays EN/PL localised; machine values (IDs, node names, check IDs, outcomes, paths) are shown as
    received.

11. **Sidebar** follows the canvas's Sidebar component: one `inset` panel at full height with a
    hairline on the right; a 44px strip with the name "Tarmind" right-aligned (no logo; on macOS the
    traffic lights sit in its free left corner and the strip is draggable); **New run** as a
    full-width button under it; Inbox, Runs, Approvals (pending count as plain mono text) and Editor
    as 30px entries with outline icons; **Recent · last 5**: the five newest runs from `GET /runs`
    with a status shape (an approval waiting shows as waiting), the graph ID, the age, and its status
    in words for assistive technology, then **All runs** with the total; a failed read says so;
    **Later**: Projects, Runners, Docs, disabled, without icons, each with "Soon"; a footer with
    Welcome and setup, Settings and the profile row (initials and "Local profile"). The profile
    leaves the global bar, which keeps the connection indicator.

## Data / API contracts affected

None. The screen consumes `GET /runs`, `GET /approvals`, `GET /runs/{id}`, the run event stream and
`POST /runs/{id}/decisions/{node_run_id}` exactly as before.

## Failure behavior

- A failed list read shows the engine error state with Retry, never an empty or stale queue.
- A selected run that cannot be found says so in the detail pane; the queue stays usable.
- A lost stream disables the decision and keeps the last reduced state; the global bar reports it.
- A decision request that fails shows its message next to the buttons and changes nothing.

## Acceptance criteria

IDs as registered in `docs/roadmap/features.yaml` (entry F2.5b); tests carry the tag.

- [x] **F2.5b-AC1** Queue grouping, de-duplication, filters and counts are pure functions tested over
      fixed lists (`desktop/test/inbox.test.ts`).
- [x] **F2.5b-AC2** Detail selectors are tested over recorded runs: a loop that used its attempts, a
      rejected human gate, an interrupted run, a running run (`desktop/test/inbox.test.ts`).
- [x] **F2.5b-AC3** Every state has a story (needs attention, failed, retries used up, interrupted,
      running, filters, decided, decided here, decision error, connection lost, a run that cannot be
      read, staying on the shown item, keyboard focus, empty, no runs, loading, error; Sidebar recent
      runs, unreadable list, no runs). The story smoke renders each in EN and PL, waits for its play
      function and fails on a play error or an axe violation (checked on the state the play reached).
      These stories are the only automated check for a failed decision request, deciding while the
      stream is lost and a run that cannot be read.
- [x] **F2.5b-AC4** Sidebar order, New run button, plain approvals count, Later group and footer
      profile are tested on the rendered markup (`desktop/test/shell.test.tsx`).
- [x] **F2.5b-AC5** The real-Electron e2e (`desktop/e2e/demo.cjs`): the empty Inbox's Open graph lands
      on New run with the file chosen; the pending approval is queued exactly once (not also as a
      running run); it is decided in the Inbox with a reason; the decision appears after
      `approval_decided`; after `GET /approvals` no longer lists it, the row is still queued as a held
      row (`data-held`) with its decision; the run then succeeds with that reason in its decision.
- [x] **F2.5b-AC6** Decision state and selection (decided here vs elsewhere, event before response,
      held while the list drops it, filter over a held item, Next, the shown item staying put) are
      pure functions (`desktop/test/inbox.test.ts`, `src/inboxDecisions.ts`); the rendered behaviour
      (a newer approval arriving keeps the shown one and the typed reason; focus moves to Next only
      after the person's own decision, to the next headline once after Next, and stays on a filter or
      on a row the person opens) is asserted by the `InboxStaysOnShownItem` and `InboxKeyboardFocus`
      stories under the smoke.

## Security / trust considerations

Prompts, context values, check reasons, evidence output and logs are untrusted display text: they
are rendered as text only (no HTML, no links), cut to bounded lengths, and never stored. The
renderer still reaches the engine only through `window.agentplane`.

## Observability

No new events. Everything shown comes from existing events or API lists; a decision is visible as
`approval_decided` in the run's event log.
