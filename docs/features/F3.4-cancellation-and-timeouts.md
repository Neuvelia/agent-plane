# F3.4 - Cancellation and Timeouts

**Status:** draft (spec only; no implementation yet)
**Priority:** P0
**Target phase:** Phase 3 - Local Production Ready
**Depends on:** F1.2 (Codex process ownership), F1.6 (correction loop); F3.2 only
for the criteria marked **D**
**Companion spec:** F3.4a (Windows process-tree termination)
**ADR:** ADR-0028 (proposed): cancel/timeout reason
semantics and the cross-platform process-ownership model

Product name: Tarmind (in code today: agentplane). Identifiers, paths and event
names below keep the code name.

## Problem

Cancellation exists but is uneven, and nothing bounds how long a unit runs.

- A hung Shell or Codex node blocks its run until the user interrupts it. A run
  has no time limit; `context.WithTimeout` is used only for probes and Git
  helpers (`internal/capability`, `internal/gitstate/run.go`,
  `internal/runtime/workspace.go`, Codex `Detect`).
- Process ownership differs per node type. Codex owns a Unix process group
  (TERM, 500 ms, KILL; `internal/agent/codex/process_unix.go`). The Shell
  executor kills only the direct child (`cmd.Process.Kill`), so a grandchild
  survives while the run reports cancelled. The command Gate runs
  `/usr/bin/diff` with a 1 s `WaitDelay` and no group.
- There is no graceful phase: fixed TERM-then-KILL, or an immediate kill.
- Windows has no process-tree termination (F3.4a).
- `cancelled` exists as a terminal state (node and run) but carries no cause.
  An interrupt, a sibling failure and a deadline look the same in the trace.

## Goal

- Per-node and per-graph time limits, opt-in, validated before the run starts.
- One termination contract for every child process the runtime owns (Shell,
  Codex, command Gate, Git helpers): graceful request, bounded grace, forced
  kill of the whole tree, proof that nothing is left.
- `cancelled` and `timeout` carry a typed reason in the trace and CLI result; a
  timeout is never reported as an ordinary failure.
- A timed-out or cancelled unit never invalidates accepted siblings (AGENTS.md
  rule 6) and never causes unbounded retry (rule 7).

## Non-goals

- Resume or recovery of interrupted runs (F3.3), durable replay (F3.2).
- Sandboxing, CPU/memory/disk quotas, network control (F3.9).
- Approval timeouts for Human nodes (F2.10: ends by decision or run cancel).
- Cost/budget limits (F3.10, F5.11), scheduling (F5.2), remote cancel (F4.6).
- Escaped processes (a descendant that deliberately leaves its group or job).
  Unix `setsid` escape stays out of scope, as in ADR-0010.

## Functional requirements

### Limits (graph surface)

- Node field `timeout_seconds` (integer, 1..86400): wall-clock limit of **one
  attempt** of that node, from the moment it enters `running` (queue time
  excluded). For a loop producer it bounds the producer; the embedded Gate has
  its own fixed bound so a slow producer cannot starve its check.
- Graph field `limits.run_timeout_seconds` (integer, 1..86400): wall-clock limit
  of the whole run from `run_started`.
- Both are semantic (part of the graph version, not layout metadata). Both are
  absent by default: no limit unless authored.
- Preflight validation (`E_TIMEOUT_INVALID`, before `run_started`): non-integer,
  out of range, or set on a `human` node.
- The command Gate evidence process has a fixed internal bound of 30 s, not
  authored. Exceeding it is a Gate `timeout` failure, never a `red` verdict: a
  timeout is not evidence about the candidate (AGENTS.md rule 5).
- A CLI flag may shorten the graph run limit, never extend it (Q5).

### Reasons and states

No new terminal status is added (ADR-0028). `cancelled` and `failed` gain a
typed, closed `reason`:

| Cause | Node status | Run status | `reason` | `failure_kind` |
| --- | --- | --- | --- | --- |
| Interrupt (SIGINT/Ctrl+C, SIGTERM, watch-output failure) | `cancelled` | `cancelled` | `interrupt` | none |
| API/desktop cancel request | `cancelled` | `cancelled` | `user_cancel` | none |
| Run deadline | `cancelled` | `cancelled` | `run_timeout` | none |
| Sibling failed, in-flight work abandoned | `cancelled` | `failed` (by the failure) | `sibling_failed` | none |
| Node deadline | `failed` | `failed` unless retried | `node_timeout` | `timeout` |

1. A run deadline is a cancellation with a reason, not a failure: `run_finished`
   status is `cancelled`, reason `run_timeout`, and the CLI exits with a
   dedicated code (Q4).
2. A node deadline is a failed attempt with `failure_kind: timeout`. In a loop
   it consumes one attempt of the existing budget; exhaustion ends the node
   `failed`/`timeout`. Accepted siblings are never rerun. A timed-out attempt
   has no CheckResult, so the next attempt gets no `Feedback` (Q3).
3. Precedence: an unrelated non-cancellation failure keeps precedence over
   cancellation (F0.4, unchanged). Among cancel causes the first recorded wins.
   The reason comes from the `context.Cause` of a typed cause, never from error
   strings or exit codes.
4. Executor errors keep wrapping `context.Canceled`/`DeadlineExceeded`. A node
   deadline uses a derived context with a typed timeout cause. The run context
   is still live then, and today the scheduler would classify the error as a
   plain failure, so classification must read the cause.

### Termination contract (all child processes)

One shared mechanism (location is an implementation choice and must satisfy the
architecture test), used by Shell, Codex, command Gate and Git helpers:

1. **Own the tree.** Unix: process group (`Setpgid`). Windows: Job Object
   (F3.4a).
2. **Request.** Unix: `SIGTERM` to the group. Windows: best effort (F3.4a).
3. **Grace.** Wait up to the grace period (default 5 s, Q2) for the leader to
   exit and the tree to empty. A second interrupt during grace skips the rest.
4. **Force.** Unix `SIGKILL` to the group; Windows `TerminateJobObject`.
5. **Verify.** Reap the leader and confirm an empty tree within a bounded 1 s.
   A surviving descendant yields a typed `shutdown` error with the leaked count;
   never a clean cancel over leaked work.
6. **Idempotent.** Cancelling an exited, never-started or already-terminating
   process is success.
7. **Classify by our own record** (cause and request), not by exit code or OS
   wait status.
8. Output drain stays bounded (existing 1 s `WaitDelay`); a descendant holding a
   pipe cannot hold the run.

Shell adopts 1-8 (today: direct child only). Codex keeps its Unix behavior with
the shared grace default.

### Scheduler and loop

- On cancel or run deadline: schedule nothing new, terminate in-flight trees by
  the contract, wait, mark in-flight and unstarted nodes `cancelled` with the
  reason, finish the run.
- A node deadline terminates only that node's tree; siblings continue and
  accepted output stays immutable.
- The attempt trace records each attempt's own termination; no new attempt
  starts after the run is cancelled.

## Data / API contracts affected

- Graph (additive, optional, schema version unchanged): `nodes.<id>.timeout_seconds`,
  `limits.run_timeout_seconds`; `docs/graph-spec.md`, parser, validator,
  semantic hash. Graph-edit operations for them are a later slice.
- Events: schema 11 -> schema 13 (proposed; next free number confirmed at merge; 12 is F2.8b's `attempt_diff`), additive. `reason` on `node_finished`,
  `node_terminated`, `run_finished`; `failure_kind: timeout`; new
  `cancel_requested` (scope run/node, reason, source) and `process_terminated`
  (method `graceful|forced|already_exited`, grace_ms, elapsed_ms, leaked count;
  no paths, environment or command lines). Readers accept every earlier schema.
- Run result and CLI JSON: `reason` on node and run. Exit 130 stays for
  `interrupt`/`user_cancel`; `run_timeout` gets a dedicated code (Q4).
- `shell.FailureKind` and `agent.ErrorKind`: add timeout; Codex diagnostic
  `codex_timeout`.

## Failure behavior

- Invalid limit: preflight error with node, path and fix; no run identity.
- Tree cannot be emptied: node `failed`, `failure_kind: shutdown`, leaked count
  in the event; not reported as a clean cancel.
- Cancel before a node starts: `node_terminated` `cancelled` with the reason; no
  process started.
- A persistence failure during cancel does not hide the cancel result (existing
  CLI rule).

## Acceptance criteria

Layers: **U** unit, **R** runtime (fake executor, fake clock, explicit
barriers), **P** real child process per OS, **C** built CLI, **D** needs the
durable store.

### Can ship before F3.2 (in-process; schema 13 (proposed) on the current store)

- [ ] U: both limits validate (range, type, human node rejected) with
  `E_TIMEOUT_INVALID` and a path; absent means no limit.
- [ ] U: the limits change the graph version; layout metadata still does not.
- [ ] R: a node deadline ends only that node `failed`/`timeout`; an accepted
  sibling's outputs and AttemptID are unchanged and it is not rerun.
- [ ] R: a loop attempt that times out consumes exactly one attempt; a later
  attempt can still be accepted; exhaustion ends `failed`/`timeout`; never more
  than `max_attempts` attempts.
- [ ] R: a run deadline ends the run `cancelled`/`run_timeout`; in-flight and
  unstarted nodes `cancelled`; every started node has a terminal event;
  sequence is monotonic; exactly one `run_finished`.
- [ ] R: interrupt, API cancel, run deadline and sibling failure give four
  distinct reasons; a racing unrelated failure keeps precedence (F0.4).
- [ ] R: the reason is decided by context cause; a misleading error message or
  exit code cannot change it.
- [ ] R: an executor that ignores its context cannot hold the scheduler past the
  termination bound; the node ends `failed`/`shutdown`.
- [ ] P (Linux, macOS, Windows): a Shell child that spawns a grandchild leaves no
  descendant after cancel and after a node deadline. Red on `main` today.
- [ ] P: a child that exits on the graceful request within grace is recorded
  `graceful`; one that ignores it is `forced` after grace.
- [ ] P: cancelling an exited or never-started process is `cancelled`, no error.
- [ ] P: Codex fake CLI with a descendant gives the same guarantees; the command
  Gate evidence process is bounded at 30 s.
- [ ] P: a leaked descendant returns a typed `shutdown` error with its count.
- [ ] C: SIGINT and (Unix) SIGTERM give `reason: interrupt`, exit 130, no live
  child; a run deadline exits with the dedicated code; `--json` and human
  output show the reason; a second interrupt during grace skips the rest.
- [ ] Events: order is `cancel_requested` < `process_terminated` < node terminal
  < `run_finished` in every scenario above.
- [ ] F3.4a Windows proof W1-W7 passes.
- [ ] `go test -race` passes for runtime, shell, codex and the helper;
  `make check` passes; the architecture baseline does not grow.

### Needs the durable store (F3.2, PR #108)

- [ ] D: `cancel_requested`, `process_terminated` and `reason` are in the
  append-only store and reconstruct node/run state, reason and leaked count with
  no in-memory data.
- [ ] D: a cancel requested while the process side is gone (runner restarted) is
  a durable fact; recovery does not restart a cancelled node.
- [ ] D: a runner crash leaves a record of owned processes (pid plus start time);
  on next start Unix orphans are detected and terminated or reported. (Windows
  crash orphans are already covered by W4.)
- [ ] D: after restart a run deadline uses the recorded `run_started` and the
  policy chosen in Q8; it is not silently reset.
- [ ] D: a `run_timeout` run appears in history and export with its reason
  (F3.7).
- [ ] D: a cancel arriving over the loopback API is persisted before it is acted
  on.

## Required tests

Validation tables; scheduler tests with fake clock and executor and explicit
barriers (no sleeps); process lifecycle tests using a helper built from the test
binary for every OS; built-CLI signal and exit-code tests; schema 13 (proposed) round trip
including reading the previous schema's logs; race runs.

## Security / trust considerations

- Children are untrusted. Termination must never signal a process the runner
  does not own: Unix uses the group created at start and guards against pid
  reuse after reap; Windows uses the job handle, never a PID lookup.
- Events carry counts and enums only.
- Timeouts and Job Objects are lifetime control, not a security boundary and not
  a sandbox (F3.9).

## Observability

Events above. The human CLI renderer prints one line per cancelled or timed-out
node with its reason and, for forced kills, "forced after Ns". Desktop and the
live map must tolerate schema 13 (proposed); showing the reason is a later slice.

## Risks

- Grace defaults can hide slow agent shutdown: record `elapsed_ms`.
- A node limit shorter than the Gate/Git bounds could fail an attempt before
  evidence exists: the Gate bound is independent of the node limit.
- The schema bump requires desktop and store readers to ignore unknown fields.
- Windows risks are in F3.4a.

## Open questions (recommended defaults)

1. Node timeout per attempt or per node total? Default: per attempt.
2. Grace default and knob? Default 5 s; CLI flag `--cancel-grace`; no graph
   override in v1.
3. Typed timeout feedback to the next loop attempt? Default: none for now.
4. Exit code for a run timeout? Default: 124 (GNU `timeout` convention).
5. Run-limit CLI flag that may only shorten? Default: yes (`--run-timeout`).
6. Default node timeout for Agent nodes? Default: none in the engine; the desktop
   suggests one.
7. Keep partial Git-derived evidence after cancel/timeout? Default: no; F3.1
   retained worktrees are the evidence.
8. Run deadline across a future resume: wall clock or time spent running?
   Default: time spent running; decide with F3.2/F3.3.

## Out of scope for this iteration

Resume and orphan recovery (F3.3), sandboxing (F3.9), budgets (F3.10), remote
cancel (F4.6), a dedicated `timed_out` status (rejected in ADR-0028).
