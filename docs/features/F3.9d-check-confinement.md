# F3.9d - Fail-closed confinement for test_command checks

**Status:** draft
**Priority:** P1
**Target phase:** Phase 3 - Local Production Ready (derived from F3.9)
**Registry:** `docs/roadmap/features.yaml` entry F3.9d
**Depends on:** F1.4b; shares the Linux launcher with F3.9
**ADR:** ADR-0049 (proposed; widens F3.9 v0 with read masking of credential locations)
**Issue:** #205

## Problem

A `test_command` Gate (F1.4b) usually runs code that an Agent wrote a moment
ago: a test suite, a build or a linter. It runs with the runner's full
privileges. It can reach the network, write anywhere the user can, and read
`~/.ssh`, `~/.aws`, `~/.kube`, `~/.config/gcloud` and similar locations.
ADR-0042 says this plainly: the check "is not read-only", and sandboxing is
out of scope.

F3.9 v0 will give Shell nodes `network: off` and `paths.write`, but it is not
wired into Gates and it excludes read confinement.

The reference project in the adoption analysis
(`kacwojdev/agent-control-plane`) runs every check in a fail-closed sandbox.
It uses no network (`unshare -rn`), a scrubbed environment and a tmpfs over
credential directories, and treats its selftest as the container
healthcheck. Its security review rests on that property. A user who moves to
AgentPlane today would silently lose it.

## Goal

A `test_command` Gate can declare `confinement: required`. Its command then
runs under one fixed, documented profile, or does not run at all.

## Non-goals

- A configurable profile language. The profile is fixed in v1 and F3.9 owns
  the general policy surface.
- Confinement of Shell producers or Agent nodes. F3.9 does that; this feature
  only reuses its launcher.
- macOS and Windows enforcement. Both report `unenforceable`, which in
  `required` mode is a preflight error.
- Seccomp syscall filtering, resource limits and CPU or memory quotas.
- Hiding arbitrary file contents. Only the fixed list of credential locations
  is masked.

## Functional requirements

1. A `test_command` Gate config accepts `confinement: none | required`.
   `none` is the default. Without the key, behavior and the graph's semantic
   hash are unchanged.
2. **The `required` profile (Linux).** Every element must be in force before
   `exec`:
   - **Network:** a new user and network namespace, so no usable interface
     exists. This is the F3.9 FR14 mechanism.
   - **Writes:** a Landlock ruleset that grants writes to the Gate's `cwd`
     tree (the worktree when `isolation: worktree`) and to a private, per-check
     temporary directory exposed as `TMPDIR`, and nothing else. This is the
     F3.9 FR13 helper.
   - **Credential masking:** a new mount namespace where each existing entry of
     a fixed list under the runner's `HOME` is covered. Directories get an
     empty read-only tmpfs; files get a read-only bind of `/dev/null`. The list
     is `.ssh`, `.gnupg`, `.aws`, `.azure`, `.config/gcloud`, `.kube`,
     `.docker`, `.netrc`, `.npmrc`, `.pypirc`, `.git-credentials`,
     `.config/gh`, `.terraform.d`, `.vault-token`. Changing the list needs an
     ADR amendment.
   - **Environment:** unchanged from F1.4b (explicit only). `HOME` is
     forwarded only if it is in `env_allowlist`. Masking applies either way.
   - `PR_SET_NO_NEW_PRIVS` is set.
3. **Fail closed.** Preflight probes every element of the profile, reusing the
   F3.9 FR7 probe. If any element is `unenforceable` on this machine, the node
   fails before `run_started` with `E_CONFINEMENT_UNAVAILABLE`. The error names
   the missing mechanism and the remedy (kernel version, sysctl
   `kernel.unprivileged_userns_clone`, AppArmor userns restriction). The helper
   also verifies each element after applying it and exits without `exec` on
   any failure. That is an operational error, never a verdict.
4. **Selftest.** `agentplane capabilities` (ADR-0025) gains a
   `check_confinement` row. It reports `prevented` only after a bounded
   selftest succeeds: a child under the profile fails to connect to a loopback
   listener of the parent, fails to write outside its `cwd`, and reads no
   entry of a fixture credential directory. Otherwise the row reports
   `unenforceable` with the reason. The desktop shows the row like the other
   capability rows.
5. The Check Result reason appends the enforced profile, for example
   `command exited 1; declared side_effects: workspace_writes; confinement:
   network, writes, credentials`.
6. A violation inside the check (connection refused, `EACCES` on a write,
   reading an empty masked directory) surfaces as the command's own exit
   status. The runtime does not reinterpret it (as in F3.9 FR17). The Check
   Result's red evidence shows the command's stderr.
7. The baseline and golden runs of F1.4c use the same confinement as the Gate.

## Data / API contracts affected

- **Graph schema:** the `confinement` key on `test_command` Gate config, plus
  its field descriptor.
- **Events:** `gate_check` reason text (no new event type). F3.9's
  `policy_evaluated` is emitted for the Gate once F3.9 exists. Until then, the
  enforced profile is recorded in the reason only. If ADR-0049 decides on a
  structured field, that is a schema bump.
- **Capability report:** the `check_confinement` row (ADR-0025 is additive).
- **Docs:** the security model gets the honest vocabulary (`prevented` /
  `unenforceable`) and a list of what the profile does not cover.

## Failure behavior

| Situation | Result |
| --- | --- |
| `confinement` on a Gate kind other than `test_command`, unknown value | validation error |
| `required` on macOS, Windows, or Linux without user namespaces or Landlock | preflight error `E_CONFINEMENT_UNAVAILABLE`, the command never starts |
| Helper fails to apply or verify an element | operational error, no verdict, no retry |
| `cwd` is a symlink or lies under a masked location | validation error |

## Roadmap criteria

F3.9d is a derived entry with no roadmap criteria of its own. It supplies the
Gate half of F3.9-AC1/AC2 evidence for checks only. It does not mark F3.9
criteria met.

## Acceptance criteria

- [ ] F3.9d-AC1: Under `required` on Linux with user namespaces, a check that connects to a
  loopback listener opened by the test fails; the same check with `none` connects.
- [ ] F3.9d-AC2: Under `required`, a check that writes outside its `cwd` (a fixture path in
  the test's temporary `HOME`) fails, and the file does not exist afterwards. A write to
  `cwd` and to `$TMPDIR` succeeds.
- [ ] F3.9d-AC3: Under `required`, a fixture `HOME/.ssh/id_test` and `HOME/.netrc` are not
  readable by the check (empty directory, empty file). Outside the check both remain
  unchanged.
- [ ] F3.9d-AC4: With a probe that reports user namespaces unavailable, the node fails
  preflight with `E_CONFINEMENT_UNAVAILABLE`, and a marker file the command would
  create does not exist.
- [ ] F3.9d-AC5: The capability report shows `check_confinement` as `prevented` after a
  passing selftest, and `unenforceable` with a reason otherwise.
- [ ] F3.9d-AC6: Graphs without `confinement` keep F1.4b behavior and semantic hashes.

## Required tests

- **Unit:** config validation; profile construction; mask list resolution (only
  existing entries, no symlink following outside `HOME`).
- **Integration (Linux, skipped with a recorded reason where namespaces are
  unavailable in CI):** the AC1–AC4 checks through the real helper.
- **CLI/e2e:** a loop with a confined `test_command` running red, then green.

## Security / trust considerations

- This is containment of **one** process tree for the check. It is not a VM.
  Kernel bugs, readable files outside the mask list (for example the
  workspace, or `~/.config` entries not on the list) and anything the command
  can reach through the workspace remain exposed. Docs must list this
  explicitly and never say "sandboxed" without the qualifier.
- Masking happens in a private mount namespace. The runner's own view and the
  user's files are never modified.
- The helper takes no input from the graph other than the argv the runner
  built (the F3.9 FR13 rule).

## Observability

- The `gate_check` reason carries the enforced profile.
- The capability row reports the selftest outcome.
- `E_CONFINEMENT_UNAVAILABLE` is counted as a preflight failure kind.

## Open questions

1. Which feature owns the shared helper, `internal/confine`, if F3.9d lands
   before F3.9? Recommended: F3.9d creates it with exactly the F3.9 FR13/FR14
   semantics, and F3.9 extends it.
2. Should `confinement: required` become the default for loops whose producer
   is an Agent? Recommended: decide after one release of real use, through a
   new ADR.
3. Is a structured `confinement` field on `gate_check` worth a schema bump
   now, or does it wait for F3.9 `policy_evaluated`? Recommended: wait.

## Out of scope for this iteration

Configurable profiles, macOS (`sandbox-exec` is deprecated) and Windows
(AppContainer, F3.9b), seccomp, resource limits, confinement of Shell
producers and Agent nodes (F3.9).
