# F0.4 - In-memory DAG scheduler

**Status:** implemented
**Priority:** P0
**Target phase:** Phase 0 - Execution Core

## Problem

Validated graph definitions need deterministic execution ordering while still allowing independent nodes to run concurrently.

## Goal

Execute a validated DAG in memory, track node/run state, and schedule ready nodes subject to a configurable concurrency limit.

## Functional requirements

1. Node states: pending, ready, running, succeeded, failed, skipped, cancelled.
2. A node becomes ready only when all required dependencies/inputs are satisfied.
3. Independent ready nodes may execute concurrently.
4. A configurable global concurrency limit is enforced.
5. F0 behavior is fail-fast for unhandled node failure.
6. A run reaches exactly one terminal state.
7. Scheduler execution is independent of future cloud/UI packages.
8. Executor behavior is abstracted enough for tests to use deterministic fakes.

## Acceptance criteria

- [x] Two independent nodes can be proven to overlap in running state using explicit test synchronization.
- [x] A dependent node never starts before all required upstream nodes succeed.
- [x] Concurrency limit 1 serializes otherwise independent nodes.
- [x] Failed upstream work prevents invalid downstream execution.
- [x] Run terminates deterministically on success and failure.
- [x] `make check` passes.

## Scheduler contract

`runtime.Run` validates and compiles the graph and validates supplied graph
inputs before starting a run. A preflight error returns no run result. A started
run moves from running to exactly one of succeeded, failed, or cancelled.

Pending nodes become ready only after every direct producer succeeded and
`BindingPlan.ResolveNodeInputs` supplied their inputs. A failed resolution is a
node failure. Ready nodes are dispatched in sorted node-ID batches capped by
`MaxConcurrency` (zero defaults to one; negative values are invalid). Results
from a batch are committed in sorted node-ID order. This permits independent
nodes to overlap while keeping state transitions and dispatch deterministic.
Newly ready work waits until the current batch finishes.

An unhandled failure stops later batches. Already running batch peers finish;
their accepted outputs remain available in the result. All unstarted pending
and ready nodes become skipped, including independent work. If several nodes
in a batch fail, the lowest node ID is the primary failure. Output contract
errors fail the producing node. Missing bound outputs fail input resolution at
the consumer. Missing graph outputs fail graph output assembly after the nodes
have succeeded.

The executor receives a context and must cooperate with cancellation. If
cancellation causes execution to end, its error must wrap
`context.Canceled` or `context.DeadlineExceeded`, including when a lower-level
operation reports a different error. Only an error with one of those markers
is treated as cancellation after the run context is cancelled; an unrelated
executor failure remains a node failure and takes precedence. The
scheduler launches no further work after cancellation, waits for in-flight
callbacks, and marks remaining nodes cancelled. A non-cancellation failure in
the active batch takes precedence over cancellation. The result contains
sorted node and graph-output summaries plus a sequence-numbered in-memory
transition trace without values or error text. F0.6 will define execution IDs,
timestamps, and serialized events.

## Required tests

- linear graph;
- diamond/parallel graph;
- concurrency limit;
- upstream failure;
- terminal state invariant;
- context cancellation seam if introduced.

## Out of scope for this iteration

- durable recovery;
- retry loops;
- human gates;
- distributed scheduling;
- dynamic graph mutation.
