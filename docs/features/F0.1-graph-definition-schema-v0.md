# F0.1 - Graph Definition Schema v0

**Status:** ready for planning
**Priority:** P0
**Target phase:** Phase 0 - Execution Core

## Problem

The runtime needs a stable, versioned, text-based contract for graph definitions before validation, scheduling, CLI execution, or a visual editor can be implemented safely.

## Goal

Introduce Go types and parsing/serialization contracts for a minimal DAG graph definition that is human-readable, Git-friendly, and explicit about node input/output contracts.

## Non-goals

- No graph execution.
- No cycle validation beyond what is required to parse structure.
- No expression language.
- No agent, gate, human, or cloud semantics.
- No UI layout engine.

## Functional requirements

1. Support YAML as the authoring format.
2. Represent `schema_version`, graph `id`, optional `name`/metadata, inputs, nodes, edges, and outputs.
3. Node definitions have stable IDs, type, declared inputs, type-specific config, and declared outputs.
4. Edge definitions reference a source output and target input explicitly.
5. Graph definitions must not contain a generic raw secret field.
6. Keep semantic fields separable from non-semantic metadata so future layout metadata can be ignored by semantic hashing.
7. The type system is deliberately small and extensible.

## Proposed value types

```text
string
number
boolean
json
artifact_ref
```

The implementer may propose a smaller first slice if it preserves forward compatibility.

## Data / API contracts affected

New package: `internal/graph`.

Expected concepts:

- `Definition`
- `InputDefinition`
- `NodeDefinition`
- `PortDefinition`
- `EdgeDefinition`
- `OutputDefinition`

Names may change during planning if the resulting API is clearer.

## Failure behavior

Parsing malformed YAML must return an error with enough context for later CLI presentation.

Unknown YAML fields should be discussed during planning. The chosen behavior must be tested and documented.

Unsupported schema versions must fail explicitly.

## Acceptance criteria

- [ ] A valid three-node example graph can be parsed into typed Go structures.
- [ ] The parsed graph exposes explicit node input/output declarations and explicit edge endpoints.
- [ ] Unsupported `schema_version` returns a deterministic error.
- [ ] Malformed YAML returns an error instead of partial success.
- [ ] Parse -> serialize -> parse preserves semantic meaning for the example graph.
- [ ] Tests do not depend on map iteration order.
- [ ] `make check` passes.

## Required tests

### Unit

- valid minimal graph;
- valid parallel-branch example;
- unsupported schema version;
- malformed YAML;
- round-trip semantic equality.

### Integration

Not required for F0.1.

## Security / trust considerations

Graph files are untrusted input.

Parsing must not execute templates, commands, environment expansion, or network access.

Do not introduce automatic secret resolution in this feature.

## Observability

No execution events are required yet.

Parsing errors should be structured enough to support F0.2 diagnostics later.

## Open questions for planning

1. Which YAML library should be used and why?
2. Should unknown fields fail in v0 or be tolerated?
3. How should type-specific `config` be represented without forcing all future node types into one union immediately?
4. What is the normalized semantic representation used by round-trip tests?

## Out of scope for this iteration

- semantic graph validation;
- node reference checks;
- type compatibility checks;
- cycles;
- scheduler;
- execution;
- visual metadata behavior beyond keeping a clean separation seam.
