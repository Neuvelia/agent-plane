# F2.4 - Graph Validation UI

**Status:** implemented (E3.1 Go: requirements 1, 2, 10; E3.2 renderer: requirements 3-9, 11-13)
**Priority:** P0
**Target phase:** Phase 2 - Local IDE
**Depends on:** F0.2, F2.1 (canvas and document API)
**ADR:** ADR-0021 (one validation path), accepted
**Plan:** `docs/superpowers/plans/2026-11-14-graph-editor.md` (slice E3, delivered right after F2.1)

## Problem

The validator's findings are available only on the command line and in raw form. In the editor a mistake
is visible only when a run fails to start, and node configuration errors (shell, gate, agent) appear only at
run start because the API validation path does not run them. A person cannot get from a problem to the
element that causes it.

## Goal

Every diagnostic that `agentplane graph validate` can report is visible in the editor, in an issues panel and
as a badge on the element it concerns; selecting an issue takes the person to that element or source line;
Run is disabled only while a blocking error exists.

## Non-goals

- Automatic fixes (P2 in the roadmap).
- New validation rules or new diagnostic codes beyond the single wrapper code below.
- Translating engine messages (they are shown as received).
- A history of past validation results.
- Policy promotion of warnings to errors.

## Functional requirements

1. **One validation path (Go).** `agentplane graph validate`, `serve`'s validation and the document API run
   the same function: `graph.Validate` followed by each executor's side-effect-free `ValidateNodeConfig` for
   shell, gate and agent nodes (human nodes are checked by `graph.Validate`). A config error becomes a
   diagnostic with the new code `E_NODE_CONFIG_INVALID`, `node_id`, `path` `nodes.ID.config` (or a deeper path
   when the executor reports one), the executor's message and, when it has one, a suggestion. The CLI prints
   and returns the same diagnostics and exit code as the API reports.
2. **Source line.** The document API adds `line` (1-based, when resolvable) to each diagnostic, computed from
   the YAML tree and the diagnostic's `path`, `node_id`, `edge_index` or `graph_input_binding_index`. It is an
   API field only; `graph.Diagnostic` and the CLI JSON are unchanged. A parse error carries its line, and its column
   where the YAML library lets the engine locate it (see the notes on E3.1).
3. **Issues panel.** A card in the editor listing diagnostics with: severity pill (Error, Warning, localised),
   the machine code in mono, the message as received, the suggestion, the element label (node id, `edge
   from -> to`, binding, or graph), and the line. Order is errors first, then warnings, then by element and
   code, stable between refreshes.
4. **Filter.** A segmented control All / Errors / Warnings with counts; the choice is not persisted.
5. **Focus.** Selecting an issue (click or Enter) selects and reveals the node, edge, port or binding on the
   canvas and in the inspector, scrolls the YAML view to `line` when that view is shown, and moves keyboard
   focus to the selected element's heading. An issue with no element (graph level) focuses the graph header.
6. **Badges.** A node shows an error or warning badge with counts (word and glyph, not colour alone); an edge
   shows a badge when a diagnostic names its index; a port shows one when a diagnostic's path ends at that
   port. Badges update with each validation result.
7. **Validation cadence.** Validation runs after every accepted operation (the `edit` response already
   carries diagnostics) and, for text edits, after a 300 ms pause. While a request is pending the panel
   shows a quiet "Validating..." state and keeps the previous list, marked stale.
8. **YAML parse errors.** When the text does not parse, the panel shows one blocking diagnostic with its line
   (and `line N, column M` when the engine reports a column) and no other issues, and the canvas is read-only (F2.1, requirement 12).
9. **Run gating.** Run and "Save and run" are disabled **only** while a diagnostic with severity `error`
   exists or the text does not parse; warnings never disable them. When disabled, the control names the
   reason ("1 error") and offers to focus the first one. A run is never started from unsaved text.
10. **Parity corpus.** A corpus of invalid graphs, one per diagnostic code that `graph.Validate` and the
    node-config validators can produce, is used by tests; the API's diagnostics equal the CLI's JSON for
    every entry. A meta-test lists the codes found in `internal/graph` and the executors and fails if a code
    has no corpus entry.
11. **Accessibility and localisation.** The panel is a labelled region with a list of real buttons; counts
    changes are announced politely; severity labels, filter labels and states are PL and EN; the diagnostic
    text is shown as received. Focus is visible and reduced motion is honoured.
12. **States.** Loading, "No issues", stale, parse-error and connection-lost states use the shared state
    component.
13. **Stories** (EN and PL, axe clean): no issues, only warnings, errors and warnings, filtered, parse error,
    stale/validating, a node with badges, a focused edge issue.

## Data / API contracts affected

The `open`, `edit` and `validate` responses gain `line` on diagnostics (additive); `graph validate` and the API
report `E_NODE_CONFIG_INVALID` for configuration errors that previously appeared only at run start. Event
schema, run store, graph schema and the CLI JSON shape are unchanged. Behaviour change to announce: a graph
that validated cleanly may now report a configuration error it would have hit at run start.

## Failure behavior

- A validation request that fails (sidecar down) shows the connection-lost state and keeps the last list,
  marked stale; Run is disabled until the next successful validation.
- A diagnostic whose element no longer exists (race with an edit) is shown at graph level and does not crash
  focus handling.
- An executor that reports an unstructured error still produces a diagnostic (node level, message as given).

## Acceptance criteria

- [ ] **CLI parity:** for every graph in the invalid corpus the API's diagnostics equal `agentplane graph
      validate --json` (codes, severities, locations, messages, order), including `E_NODE_CONFIG_INVALID`.
- [ ] **No code is missing from the corpus:** the meta-test fails if a code from `internal/graph` or the
      executors has no corpus entry.
- [ ] Config errors are reported before any run: a graph with a shell node without `command` shows an error in
      the panel and CLI validation, and Run is disabled (e2e).
- [ ] Selecting an error focuses its node, edge, port or binding and, in the YAML view, scrolls to the reported
      line; an issue at graph level focuses the header (e2e).
- [ ] Badges on nodes, edges and ports match the diagnostics of the last result exactly (unit over fixtures).
- [ ] Run is enabled with warnings only and disabled with one error; the disabled control names the reason and
      its action focuses the first error (e2e).
- [ ] A YAML parse error shows one diagnostic with its line (and column where available) within 500 ms of the last keystroke and
      leaves the previous canvas read-only; fixing the text clears it (e2e).
- [ ] The panel never reports an issue for a state older than the latest edit: after an edit, a stale list is
      marked stale until the new result arrives (unit).
- [ ] Keyboard only: filter, move through issues, focus one and reach its inspector without a pointer (e2e).
- [ ] Stories exist for every state in requirement 13, EN and PL, zero axe violations, no external requests;
      `npm run check`, `make check`, `make desktop-e2e` pass.

## Required tests

- **Go:** the shared validation function (graph plus config), the wrapper code, line resolution from paths
  (nodes, edges, bindings, ports, parse errors), the parity corpus and its meta-test, CLI exit codes.
- **Renderer unit:** ordering, filtering, badge derivation, stale handling, Run gating rules.
- **e2e:** config error before run, focus from issue, gating, parse error, keyboard path.
- **Stories:** as above.

## Security / trust considerations

Diagnostic text can contain graph content (node ids, config values). It is rendered as text only. Line
resolution reads the in-memory tree, not the file system. Nothing leaves the machine.

## Observability

Validation emits no run events. The panel is derived from the last server result and carries no authority over
run state.

## Open questions

- Whether `E_NODE_CONFIG_INVALID` should be one code or keep a code per executor error. This spec proposes one
  wrapper code with the executor message, because the executors return plain errors today.

## Out of scope for this iteration

Quick fixes, severity overrides, validation history, translating engine messages, exporting diagnostics.

Notes on E3.1: the YAML library reports a line for a parse error but no column, so the API adds `parse_line`.
Issue #57 adds an optional `parse_column` (1-based, in characters) without a second parser: for the decoding
errors that name their node (unknown field; a value of the wrong kind or type) the engine finds the one node on
the reported line that matches the message in the same YAML tree and reads its `Column`. It is omitted, never
guessed, for syntax errors (yaml.v3 exposes only a line), for duplicate-key errors, and when more than one node
on the line fits. Tests: `TestParseErrorColumnComesFromTheFailingNodeNotFromTheMessage` (Go),
`TestParseErrorColumnIsReportedOnlyWhereTheLibraryLocatesIt` (API), `editor-issues-panel.test.tsx` (renderer).
A diagnostic whose element is missing resolves to the nearest part of the path that
exists (for example the `nodes` block), and a graph-level diagnostic has no `line`.

Lead decisions on the parse-error position (2026-11-18, issue #106, delegated by the product owner; the team may revisit):

1. The criterion "a YAML parse error shows one diagnostic with line and column" is weakened to "with its line (and column
   where available)": yaml.v3 reports a column for no error. An own syntax scanner was rejected as out of proportion.
2. The column lookup depends on yaml.v3 message wording. The pinning tests are the guard, and the dependency policy in
   `AGENTS.md` requires a YAML library upgrade to run the `ParseErrorColumn` tests deliberately.
3. For an alias (`id: &x g`, then `inputs: *x`) the library reports the anchor's line and column, so that is the position
   shown. This is library behaviour and is accepted.
4. The library cuts long scalars at a byte count and can split a multi-byte character. `parse_error` is sanitized to valid
   UTF-8 (invalid bytes become U+FFFD) where the API builds it; line and column lookups still use the raw message.
   Test: `TestParseErrorMessageIsValidUTF8`.
5. `desktop/test/fixtures/graph-validate-parse-column.json` is pinned to engine output by
   `TestParseColumnFixtureMatchesEngineOutput`.
