# F2.3 - Edge / Data Mapping Editor (with recorded run values)

**Status:** accepted for implementation (decisions 2026-11-17). Section B, engine slice E6, is implemented opt-in (`F2.3-E6-recorded-run-values.md`); slices E5a.1 (graph data operations, Go engine), E5a.2 (Bindings panel), E5b.1 (values reducer, run picker) and E5b.2 (edge inspector) are implemented; only E5a.3 is specified here and not started. The former open questions are recorded as decisions below.
**Priority:** P0
**Target phase:** Phase 2 - Local IDE
**Depends on:** F2.1, F2.2, F2.4, F0.3 (bindings), F1.7 (accepted values and provenance), F2.5 (run stream), F2.9 (run store)
**ADR:** ADR-0020 (operations), ADR-0023 (recorded run values), both accepted; ADR-0023 recording is opt-in, off by default (owner, 2026-11-15). No new ADR is needed: the new operations are additive to the versioned vocabulary (ADR-0020 decision 2), no route, event or schema changes. Decisions 5 and 6 were taken as the lightweight option (inferred "recording off", full-stream replay), so no ADR is needed; one would become necessary only if either is reversed (a `recording` flag on `run_started`, or a server-side event type filter).
**Plan:** `docs/superpowers/plans/2026-11-14-graph-editor.md` (slices E5a, E6, E5b)

## Problem

Data dependencies are the contract of a graph (AGENTS.md rule 4), but they are hard to see and change: an edge
is two strings in YAML, graph inputs and outputs are separate lists, and nothing shows what actually flowed
along an edge during a run. The roadmap criterion for this feature is that a user can point to the concrete
value that passed through an edge. Since E6 the engine records those values (opt-in); no screen shows them.

## Goal

A person can see, add, replace and remove every data binding of a graph (edges, graph inputs and their
bindings, graph outputs) in one place, with types visible and incompatible choices explained, and, for a run
that recorded values, select an edge and see the value that crossed it.

## Non-goals

- Ordering-only edges or any control dependency (schema v0 has none, and AGENTS.md rule 4 forbids them).
- Transformations on an edge, expressions, or a visual ETL (complex transformation belongs in a code node).
- Showing values for runs that did not record them, or inventing a value (unknown is unknown).
- Recording values of rejected attempts, of failed or skipped nodes, or the contents of artifacts.
- Editing node configuration (F2.2) or creating nodes (F2.1).
- Any graph rule in TypeScript: the renderer asks the engine (F2.1 requirement 5, F2.2 decision).

## Current state (verified on `main`, 2026-11-17)

| Area | Exists | Missing for F2.3 |
| --- | --- | --- |
| Edit engine (`internal/adapter/yamlgraph/edit`) | `add_edge`, `remove_edge`, `can_connect` (node output to node input only), port operations that also clean references | Every graph input, graph input binding and graph output operation; `can_connect` for a graph input source; a bulk connection query |
| API (`internal/api`) | `definition` DTO already carries `inputs`, `edges`, `graph_input_bindings`, `outputs`; diagnostics carry `edge_index` and `graph_input_binding_index` and `line` | Nothing new is needed beyond the operations |
| Desktop canvas (`desktop/src/editor`) | Drag-connect and a keyboard connect list for node ports, edge selection with Remove, per-port badges, input "sources" as text in the inspector | A list of all bindings, graph inputs and outputs anywhere; replace; suggestions; selection shared outside `GraphCanvas` (it is local state there) |
| Run values | Engine records `value_recorded` (schema 10+), run summaries in the store carry `graph_version`, Settings switch and sidecar flags, reducer deliberately ignores values (`desktop/test/schema10.test.ts`) | Renderer `RunSummary` type has no `graph_version`; no values reducer, run picker or edge inspector |

Two facts shape the design. First, a run's `graph_version` and the document API's `version` both come from the
yamlgraph semantic version, so they are comparable; layout and name edits do not change it. Second, in schema v0
`UnitID` equals `NodeID` and the graph is a DAG in which one output may feed several inputs, but nothing runs a
node more than once dynamically, so every node runs once per run: an edge has exactly one source node run, which
makes requirement 19 a defensive rule, not a feature.

## Functional requirements

### A. Static mapping editor (slices E5a.1-E5a.3)

1. **Operations added by this spec** (`ops_version: 1`, additive; `add_edge`, `remove_edge`, `can_connect` are F2.1).
   A graph input or output name travels in `id` (as a node id does in `add_node`; `name` stays `set_name`'s, the
   reasoning F2.2 used for `port`).

   | `op` | Fields | Effect |
   | --- | --- | --- |
   | `add_graph_input` | `id`, `type`, `required` | Declares a graph input; refuses an existing name or invalid type |
   | `update_graph_input` | `id`, optional `new_id`, `type`, `required` | Renames (updating its bindings), retypes or toggles required; refuses a retype that would create `E_BINDING_TYPE_MISMATCH` |
   | `remove_graph_input` | `id` | Removes the input and every binding from it (a required target input becomes unbound; the engine reports it, the UI previews it) |
   | `add_graph_input_binding` | `from` (`inputs.NAME`), `to` (`NODE.inputs.PORT`) | Appends the binding; refused as `can_connect` would |
   | `remove_graph_input_binding` | `from`, `to` | Removes that binding |
   | `set_graph_output` | `id`, `from` (`NODE.outputs.PORT`) | Declares the output or changes its source; the source must exist |
   | `remove_graph_output` | `id` | Removes the output |
   | `can_connect` (extended) | `from` may also be `inputs.NAME` | Same answer shape and rules as for an edge |
   | `list_connections` (query) | exactly one of `from` (an output or `inputs.NAME`) or `to` (an input) | `options`: every counterpart port as `{ref, type, required, ok, code?, message?}`, sorted by node id then port (graph inputs first), computed with the validator's own rules |

   Replacing a provider needs no operation of its own: one atomic batch `[remove_edge | remove_graph_input_binding,
   add_edge | add_graph_input_binding]` removes the old provider and adds the new one, and the whole batch is
   refused if the new connection is. Emptying `inputs`, `edges` or `outputs` leaves `{}` or `[]`, never removes a
   key the schema requires.
2. **Connection options (Go).** `list_connections` replaces the draft's per-diagnostic suggestion lists in every
   `open`/`edit` response. It is on demand, so responses do not grow, and it avoids the 500-operation batch cap
   (a 200-node graph can have more than 500 inputs). For `W_DECLARED_OUTPUT_UNUSED` the UI asks with `from`;
   for `E_REQUIRED_INPUT_UNBOUND` it asks with `to`. The renderer filters on `ok` and groups by `required`; it
   never compares types.
3. **Bindings panel.** A card listing every edge as `source node . output -> target node . input` with the
   declared type, status badges from the diagnostics (F2.4) and Remove. Selecting a row selects the edge on the
   canvas and the reverse. Rows are ordered by target node then input, stable. Graph input bindings are rows of
   the same list with source `inputs.NAME`.
4. **Add and replace.** "Add binding" opens an inline form: choose a source (output or graph input), then the
   targets are listed from `list_connections`; refused targets stay in the list, marked and with the engine's
   reason as visible text (type mismatch, already provided, would create a cycle, same node). Choosing a
   target that already has a provider offers "Replace" and says what is removed. The same form is the keyboard
   path for connecting and replaces the connect strip's limit to node outputs.
5. **Graph inputs.** A card listing graph inputs (name, type, required) with add, edit and remove, and for each
   its bindings to node inputs, with the same compatibility rules and reasons. Removing an input that has
   bindings previews them first.
6. **Graph outputs.** A card listing graph outputs (name to `NODE.outputs.PORT`) with add, change source and
   remove, offering only existing outputs that are required (decision 8); an optional output is not offered as a
   graph output. An existing graph output that names an optional port stays valid and is shown unchanged; adding
   one is done by hand in YAML.
7. **Hints.** A "needs a connection" part of the Bindings panel lists `W_DECLARED_OUTPUT_UNUSED` and
   `E_REQUIRED_INPUT_UNBOUND` diagnostics. "Options" shows the engine's ok candidates as one-click bindings
   (first 20, then "show all"); for an unbound required input there is also "Add graph input" (one batch:
   `add_graph_input` named after the port, a numeric suffix if taken, plus its binding; decision 7).
   Nothing is applied without a click. The v0 contract cannot express an empty binding, so there is no "empty
   binding" hint; the independence list of F2.2 is the parallelism information.
8. **Types are visible.** Ports on the canvas and rows in every list show their type; edges on the canvas are
   labelled with it on selection.

### B. Recorded run values (engine, slice E6, implemented)

These requirements implement ADR-0023 and are specified in `F2.3-E6-recorded-run-values.md`. Summary: event
`value_recorded` (9); at most 16 KiB per event and 1 MiB per run, `artifact_ref` as reference only (10);
redaction by the configured list, `serve --redact-env` (11); opt-in `--record-values` and the Settings switch (12);
store and replay (13); `graph_version` on run summaries (14).

### C. Edge values in the editor (slices E5b.1-E5b.2)

15. **Reducer.** A pure reducer in the renderer derives, from the events of one run, the recorded value of each
    key `(node, port)`; a graph input has key `inputs.NAME`. An edge's value is the value of its source key.
    It is separate from the run view reducer, whose output stays unchanged (`schema10.test.ts`). It keeps only
    value events and what the state machine needs (schema version, node status), de-duplicated by sequence so a
    reconnect replay is idempotent. Nothing is stored in components.
16. **Run picker.** In the editor, "Show values from run" lists runs whose `graph_id` equals the open graph's id,
    newest first, marking those whose `graph_version` equals the open document's `version`. A run of another
    version, or one with no `graph_version` (older store), is tagged "different version" and its values appear
    only after an explicit, inline confirmation, labelled as from another version. The newest matching run is
    chosen by default; an explicit choice lasts until the document closes.
17. **Edge inspector.** Selecting an edge or a graph input binding shows the source, the target, the declared
    type and, for the chosen run, one of these distinct states, in this order of precedence:
    - **no run**: no run of this graph exists yet;
    - **run unavailable**: the chosen run could not be read (not found, store error);
    - **different version**: values withheld until confirmed (requirement 16);
    - **node not finished**: the source node has no accepted value yet (pending, running, waiting for a human);
    - **node failed or skipped**: no accepted value exists (failed, skipped, cancelled);
    - **older run**: the run's events are schema 1-9, which cannot carry values;
    - **not recorded**: the run is schema 10 or later but has no value event at all (recording was off for it);
    - **no value for this port**: the run has value events, but none for this key (an optional output or input
      that had no value, which E6 requirement 2 records as nothing);
    - **value not carried**: the event exists without `value` (run budget reached, text that is not UTF-8, or a
      JSON value that spelled a secret): size, hash, `truncated` and `redacted` marks, and no text;
    - **value**: the text, its size, and the `truncated` and `redacted` marks, with a Copy button (decision 4).
      A string is text, a number or boolean as recorded, `json` pretty-printed by default with a "raw" toggle that
      shows the text exactly as recorded, `artifact_ref` as the reference string, never opened or linked. An
      empty string or `null` is shown as an empty value, never as "not recorded". A truncated value says "first
      N of M bytes".

    The editor adds one line about the current session ("this session records values" or "off; enable in
    Settings, applies at next start", from `recordingSettings()`), as a hint, not as the cause of a state.
18. **Live runs.** While the chosen run is going, values appear as their events arrive; the connection-lost
    banner and stale handling of F2.5 apply, and values already received stay visible and marked possibly
    incomplete.
19. **Static units.** Unit IDs equal node IDs and each node runs once per run, so an edge never has two source
    node runs. If a stream nevertheless holds two value events for one key with different node run IDs, the
    inspector says "ambiguous" with both sequence numbers and shows neither value. A Go test pins the invariant.
20. **Localisation, accessibility and stories** as in F2.1: PL and EN, keyboard operable (the bindings list
    and the edge inspector are reachable without a pointer), stories (EN and PL, axe clean) for each state in
    requirement 17.

### E5a.1 Graph data operations (Go)

- **Behaviour:** none visible; the operations of requirement 1 and `list_connections` exist behind `POST
  /graphs/edit`, with F2.1's error shape. New codes: `E_EDIT_GRAPH_INPUT_EXISTS`, `E_EDIT_GRAPH_INPUT_NOT_FOUND`,
  `E_EDIT_GRAPH_INPUT_TYPE_CONFLICT`, `E_EDIT_BINDING_NOT_FOUND`, `E_EDIT_GRAPH_OUTPUT_INVALID`.
- **API / operations:** all new, typed prediction on `graph.Definition` plus tree edit, and the existing safety net
  (ADR-0020 decisions 4 and 5). A graph input reference is rewritten by `rename_node`'s existing paths and by
  `update_graph_input`; no second list of reference sites (`refs.go` stays the one list).
- **Contracts affected:** operation vocabulary only (additive, `ops_version` stays 1); `QueryResult` gains
  `options`. No route, DTO, graph schema, event or store change.
- **Security:** names and references are untrusted text constrained by the identifier and reference grammar;
  nothing touches paths or secrets; the batch cap (500) and body limits are unchanged.
- **Acceptance (Go):**
  - [ ] Table tests per operation (success, each failure code, no-op idempotence), in `internal/adapter/yamlgraph/edit`.
  - [ ] Tree and typed implementations give equal semantic versions after every operation, on the corpus
        (`.agents/graphs/*.yaml`, `testdata/*`, including `phase0-cli.yaml` and `hostile.yaml`, which have bindings).
  - [ ] Comments, key order and unrelated lines are preserved; golden diffs name exactly the expected lines;
        a bindings-free file gains `graph_input_bindings` and keeps its other lines.
  - [ ] After any random sequence of the new operations on the corpus, `graph.Validate` reports no dangling
        reference (property test, 50 seeds, as F2.2's).
  - [ ] **Parity:** for every pair (source, target) of the corpus graphs, `can_connect` and every
        `list_connections` entry agree with `graph.Validate` (ok means adding produces no new error; refusal code
        equals the validator's), including a graph input source.
  - [ ] `list_connections` is deterministic (equal input, equal list) and answers on a generated 200-node,
        400-edge graph in under 500 ms (skipped under `-race`, as the F2.1 timing test).
  - [ ] Emptying `inputs`, `edges`, `outputs` leaves valid YAML that `graph.Parse` accepts.
  - [ ] API test: the new operations round trip through `POST /graphs/edit` with `base_hash` handling unchanged.
- **Out of scope:** UI; ordering of `graph_input_bindings` beyond append; renaming a graph output (remove and set).
- **Risks:** `list_connections` costs one validation per candidate pair; the 500 ms budget is a measured claim
  and the design falls back to one baseline validation plus incremental checks if the benchmark fails. A graph
  output source that is optional contradicts the spec sentence "producible on every successful terminal
  path"; the validator does not check it today, so the editor simply does not offer optional outputs (decision 8).

### E5a.2 Bindings panel

- **Behaviour:** requirements 3, 4 and 8. Selection (node, edge, binding) moves to one owner shared by canvas,
  node list, Bindings panel and inspectors; Issues focus (F2.4) targets the new rows.
- **API / operations:** `can_connect`, `list_connections`, `add_edge`, `remove_edge`, `add_graph_input_binding`,
  `remove_graph_input_binding`. Replace is one batch sent through `applyOps` (one undo step). The refusal text is
  the engine's, shown as received. The existing connect strip switches from N `can_connect` operations to
  `list_connections`, which reduces it to one query. The batch-cap chunking helper (`connect.ts`) is removed with it.
- **Contracts affected:** none (renderer only; `Op` and `QueryResult` types in `editor/types.ts`).
- **Security:** names and engine messages are rendered as text only. No path, grant or token is shown.
- **Accessibility and i18n:** a real `<table>` with caption; the row's first cell is a button (`aria-pressed`);
  refused targets stay in the list, `aria-disabled`, with the reason as visible text referenced by
  `aria-describedby` (not only a tooltip); status words and glyphs, never colour alone; add and remove are
  announced politely; focus moves to the next row, or the panel heading, after a removal; the form is inline, no
  focus trap, Escape cancels. PL and EN keys `editor.bindings.*`; engine messages unchanged.
- **Acceptance:**
  - [x] (Renderer unit, `desktop/test/bindings-model.test.ts`; markup in `desktop/test/bindings-panel.test.tsx`) row order, edge and graph-input-binding rows,
        badge mapping from diagnostic indexes, replace builds the two-operation batch from the definition, and
        no port-type or cycle logic exists (the `no-graph-rules.test.ts` scan covers the new files).
  - [x] (Renderer unit) a refused `list_connections` entry is never sendable and shows its message.
  - [x] (Stories, EN and PL, axe clean) panel with rows and badges, empty, add form with disabled reasons,
        replace confirmation, read-only canvas (anchors), conflict banner.
  - [x] (e2e, `desktop/e2e/demo.cjs`) keyboard only: add a binding, replace a provider and remove an edge with no
        pointer use; a refused target shows the engine's reason.
  - [x] (e2e) selecting a row selects the edge on the canvas and the reverse.
- **Out of scope:** drag onto an occupied input (stays refused with its reason, decision 2); drawing graph
  inputs on the canvas (decision 1); node-level connect from the inspector.
- **Risks:** lifting selection touches `GraphCanvas.tsx` (609 lines); keep it a mechanical change in its own
  commit. `list_connections` on a large graph relies on the E5a.1 budget.

### E5b.1 Values model and run picker

- **Behaviour:** requirements 15, 16 and 19. The editor has "Show values from run" with the picker rules; the
  chosen run's events are read through the existing `subscribe(runId)`; no new bridge call.
- **API / operations:** existing `GET /runs` (poll via `usePoll`) and the run event stream. The renderer
  `RunSummary` type gains `graph_version?` (the Go field exists, `omitempty`). Per decision 6 the renderer
  replays the full stream and keeps only what the reducer needs; there is no server-side type filter. Revisit
  only if a measured run exceeds the budget (below).
- **Contracts affected:** renderer types only. Go gains tests, no code: the summary of a run started from a
  grant carries a `graph_version` equal to the document API's `version` for the same bytes, and a run holds at
  most one value event per `(node, port)`.
- **Security:** values are user data. They live in renderer memory only, for one run at a time, at most 1 MiB of
  text plus event overhead (E6's bound), and are dropped when the run changes, the document closes or the editor
  unmounts. Never written to `localStorage`, `sessionStorage`, IPC or the console; never sent to the edit API
  or put in an error message. The renderer never sees paths or secrets; redaction stays the engine's.
- **Delivered in:** `desktop/src/values.ts` (reducer, `desktop/test/edge-values.test.ts`), `desktop/src/valuePicker.ts` (picker model), `desktop/src/useRunValues.ts` (hook), `desktop/src/ValuePicker.tsx` (view, `desktop/test/edge-values-view.test.tsx`); Go: `TestValueRecordingEmitsAtMostOneEventPerKey` (`internal/runtime`) and `TestServeRunSummaryVersionEqualsTheDocumentVersionForTheSameBytes` (`cmd/agentplane`, where the real starter lives). Decisions taken where the text left room: "newest matching run" is the newest run of the *same version* (with none, nothing is chosen for the person and the others stay available behind the confirmation); runs the store lists with `error` are not offered; a second event of the same node run for one key is the same accepted value and the first is kept, only a different node run is ambiguous; the renderer also bounds distinct keys (4096) and counts UTF-8 bytes against the 1 MiB. The picker is not mounted in `EditorScreen` yet: the inspector slot is E5b.2's, and the editor sources are owned by the E5a work.
- **Acceptance:**
  - [x] (Renderer unit, `desktop/test/edge-values.test.ts`) reducer: one key per `(node, port)` and `inputs.NAME`;
        duplicate sequences ignored; two node runs for one key yield "ambiguous"; other runs' events ignored;
        retained size bounded (a 5 MiB synthetic stream keeps at most the 1 MiB of values).
  - [x] (Renderer unit) replay equals live: reducing the fixture `demo-approve-values.json` in one pass equals
        reducing it split at every position with a reconnect replay.
  - [x] (Renderer unit) picker: filters by `graph_id`, newest first, marks version equality, tags a missing
        `graph_version` as different, defaults to the newest matching run, never shows a different-version
        run's values without confirmation.
  - [x] (Renderer unit) privacy: after viewing values, storage objects are empty and no console method was
        called with a value.
  - [x] (Go) summary `graph_version` parity and one value event per key (`internal/api`, `internal/runtime`).
- **Out of scope:** comparing values between runs or attempts (F2.8); a values-only API; a retention tool (F3.2).
- **Risks:** `graph_id` is a file-internal id, so two files or a template copy with the same id share runs
  (decision 3: matched by `graph_id`; the "different version" label and confirmation limit the confusion);
  full-stream replay of a very long stored run costs time and IPC (decision 6). Add a measurement on the
  longest stored run in the e2e fixtures; if replay to first value exceeds 2 s, reopen decision 6.

### E5b.2 Edge inspector

- **Behaviour:** requirements 17, 18 and 20. The inspector slot shows the edge inspector when an edge or a graph
  input binding is selected (the node inspector for a node). Reached from the canvas, the Bindings panel and
  the keyboard.
- **API / operations:** none new. States come from the reducer (E5b.1) and the existing run view node status.
- **Contracts affected:** none. Copy is localised; engine data is shown as received.
- **Security:** values rendered as text, never as HTML or links; control characters other than newline and tab,
  and Unicode bidirectional controls, are shown as visible `\uXXXX` marks so a value cannot reorder the screen; a
  long value scrolls inside a bounded, focusable region; the formatted JSON view is offered only when the text
  parses completely and no number literal changes (a 20-digit integer keeps its digits), otherwise the raw text
  is the only view (pretty-printed is the default only when it is offered). `artifact_ref` is a plain string
  with no open or link action. Copy writes the displayed text (decision 4) to the clipboard on an explicit
  click only, never automatically, and its result is announced politely.
- **Accessibility and i18n:** the value is in a labelled region (`role="region"`, `tabindex="0"`) so a keyboard
  user can scroll it; the state message is a `role="status"` line; each state has its own heading text, not just
  a colour; "different version" is a word tag plus an inline confirm button; the picker is a native labelled
  select. PL and EN keys `editor.edgeValue.*`.
- **Acceptance:**
  - [x] (Renderer unit) every state of requirement 17 is reachable and distinct, with the stated precedence; an
        empty string and `null` render as empty values; a truncated value says "first N of M bytes".
  - [x] (Renderer unit) bidi and control characters are escaped; a 20-digit integer and a `1e999` literal keep
        their text in the formatted view or the view is withheld.
  - [x] (Renderer unit) `json` values open pretty-printed and the raw toggle shows the recorded text byte for
        byte; a value that fails the formatting rule opens raw with no toggle; Copy writes exactly the displayed
        text and is absent for states without a value.
  - [x] (Stories, EN and PL, axe clean, no external request) one story per state of requirement 17, plus truncated,
        redacted, long, json formatted, and connection lost.
  - [x] (e2e, recording on; the test seeds `recording.json` in its temporary user-data dir) after running
        `demo-vertical.yaml`, selecting `fast.stdout -> approve.summary` shows `fast branch done` and
        `flaky.json -> approve.evidence` shows its JSON; a run with recording off shows "not recorded" for both.
  - [x] (e2e) restart the app, reopen the editor: the same values appear from the store (replay equals live).
  - [x] (e2e) a run of another graph version shows "different version" and no value until confirmed.
  - [x] (e2e) keyboard only: reach an edge row, open its inspector, scroll the value region.
  - [x] `npm run check`, `make check`, `make desktop-e2e`, `make desktop-stories` pass.

  Decisions taken where the text left room (none changes a contract):
  - Beside the ten states there are two the spec lists no row for: **loading** (the run list or the first events have not arrived; shown as a loading line, never as "no run") and **ambiguous** (requirement 19: two node runs for one key, with both sequence numbers and no value). A run list that cannot be read and a run whose log holds no event are **run unavailable**; runs of another version only (none of this version, none chosen) are **different version** with the text "no run of this version yet".
  - **Precedence.** The states that depend on the source node (not finished, failed or skipped) apply only when the key has no recorded value; a recorded value is shown whatever the node's status says. A graph input has no source node, so those two states do not apply to it.
  - **Copy writes the displayed text**, which includes the `\uXXXX` marks, so a pasted copy cannot carry a hidden or bidirectional control. It is omitted for an empty value (nothing to copy). JSON `null` and an empty string show their text (`null` or nothing) under an "Empty value" line.
  - **Formatting** copies every number and string literal from the recorded text (a token re-indenter run only after the platform parser accepted the whole text), so no number literal can change; key order and duplicate keys are kept. It is not offered when the text does not parse completely, when it is truncated, when nesting exceeds 32 levels, or when indenting would change nothing (no toggle then).
  - **Lost connection (requirement 18).** The picker gains the F2.5 "Reconnect" button next to its alert; a reconnect keeps the values already received and the replay is ignored up to the last sequence applied. Values and states shown while the connection is lost carry a "possibly incomplete" mark.
  - The value region is also the only place a value is rendered; "different version" values carry the tag beside their heading.
- **Out of scope:** value diff, search, artifact content, target-side values, rejected-attempt values.
- **Risks:** "not recorded" and "no value for this port" are inferred, not announced by the engine (decision 5;
  the only ambiguity is an optional port with no value); the e2e needs an Electron restart, which `demo.cjs`

## Data / API contracts affected

New operations and one query in the ADR-0020 vocabulary (E5a.1), `options` in `QueryResult`, and a renderer type
field `graph_version` (E5b.1). Unchanged: graph schema v0, event schema (10 added `value_recorded`; 11 is current),
store format, routes, preload bridge, the forwarding allowlist. E6's contracts (`--record-values`,
`--redact-env`, Settings entry) are as implemented.

## Failure behavior

- A refused operation changes nothing and explains itself (F2.1 error shape); a refused replace keeps the old
  provider because the batch is atomic.
- A value event without `value` (E6 requirements 4-6) is shown as "value not carried" with size and hash; the
  engine cannot supply a hex dump of text it declined to record, so none is invented.
- A store write failure while recording stops the run as ADR-0019 already does; no value is forwarded that is
  not on disk.
- A run from schema 1-9, or recorded with the switch off, shows its own state, never an empty value.
- If redaction cannot be configured (`--redact-env` names a missing variable), recording stays off for the session
  and Settings shows it (E6 requirement 12).

## Security / trust considerations

Recorded values are user, repository and model data and may contain secrets the redactor does not know. That is
why recording is opt-in, bounded and explained next to its switch. Events stay in the 0600 files of the 0700 run
directory; there is no retention or deletion tool (F3.2), which the Settings text says. In the editor, values are
text only, held in memory for one run, never persisted by the renderer and never leaving the machine. Graph, port
and input names are untrusted text. The renderer never receives paths, grants' paths or tokens, and E5a adds no
route, so ADR-0021's allowlist is unchanged.

## Observability

Recording a value is an observable fact in the event stream (AGENTS.md rule 8). Editing emits no run events.

## Decisions

These were open questions in the previous draft. Each is decided below with a one-line rationale. Decided
2026-11-17 (lead, delegated by the product owner); the team may revisit.

1. **Canvas:** graph inputs and outputs are not drawn on the canvas; cards in the inspector only (E5a.3). The
   layout contract (ADR-0022) covers nodes only.
2. **Replace:** dropping an edge on an occupied input is refused with the engine's message. A provider is replaced
   only through the Bindings form, as one atomic remove-and-add batch, so the action is explicit, previewed and
   undoable.
3. **Which runs:** the edge inspector matches runs by `graph_id` (the run store does not know a file). Runs of
   another graph version are shown only after an explicit confirmation and are labelled "different version", so
   a value is never silently attributed to the wrong definition.
4. **Value actions:** a Copy button is included, and `json` values are pretty-printed by default with a raw toggle.
   Rationale: users paste values into bug reports, and the raw text stays one click away for exactness.
5. **"Recording off":** inferred from the stream (no value events on a schema 10+ run); no `recording` field on
   `run_started`, no ADR. The only ambiguity is an optional port with no value, which has its own state.
6. **Reading values:** the renderer replays the full event stream and keeps values only; no server-side type
   filter now (ADR-0023 decision 6: no second read path). Revisit if a measured run exceeds the budget (E5b.1 risks).
7. **"Add graph input" hint:** yes, one click, labelled and undoable (one batch).
8. **Optional outputs as graph outputs:** not offered; only required outputs can be chosen as graph outputs, which
   keeps the spec rule "producible on every successful path" true for what the editor writes. Optional outputs
   can still be added by hand in YAML.
9. **After "Save and run":** unchanged from the existing E2.3 behaviour; this feature does not alter it. The
   editor's picker preselects the newest matching run on return (requirement 16).
10. **Caps:** keep the ADR-0023 caps, 16 KiB per value and 1 MiB per run (`events.MaxValueBytes`,
    `events.MaxRunValueBytes`); the e2e on the demo and a real agent run remains the evidence.

## Out of scope for this iteration

Ordering edges, expressions and transformations, value diff between runs or attempts (F2.8), artifact content
viewing, retention and deletion of recorded values (F3.2), Hosted sync of values, graph inputs on the canvas
(decision 1), a values-only API (decision 6).
