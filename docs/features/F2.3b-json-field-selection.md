# F2.3b - JSON field selection in bindings

**Status:** draft (ADR-0040 proposed; not implemented; needs owner decision between a selector and a future Code node)
**Priority:** P0 as a remaining part of roadmap F2.3 scope ("selecting a field from a JSON object")
**Target phase:** Phase 2 - Local IDE (tail)
**Depends on:** F0.3 (bindings), F2.3 (Bindings panel), F2.4 (validation UI), ADR-0003, ADR-0020, ADR-0023
**ADR:** ADR-0040 (proposed)
**Closes:** issue #185

## Problem

An edge moves one whole value. To use one field of a `json` output a user must add a Shell node with `jq`.
Roadmap F2.3 lists field selection as part of the editor scope; the spec excluded it without a named home.

## Goal

An edge or graph-input binding can pick one field of a `json` value by JSON Pointer, statically checked for
grammar and type pairing, with run-time failures typed and attributable.

## Non-goals

- Expressions, filters, maps, joins, JSONPath, jq, CEL (a Code node, if ever).
- Coercion between types.
- Selecting from non-`json` sources or into `artifact_ref`.
- Control dependencies or ordering edges.

## Functional requirements

1. Optional `select` on `edges[]` and `graph_input_bindings[]`: an RFC 6901 JSON Pointer string.
2. Schema version 1 is required when any `select` is present; version 0 graphs are unchanged. The reader accepts 0 and 1.
3. Validation: source port is `json`; target is `string|number|boolean|json`; pointer grammar valid; pointer
   escaping (`~0`, `~1`) per RFC. Errors name the edge and field.
4. Run time: resolve the pointer on the accepted source value; on missing path or exact-type mismatch fail the
   consumer before it executes with a typed binding error naming edge, pointer and observed JSON type.
5. The semantic hash covers `select`; v0 graphs hash as before.
6. Engine operation `set_edge_select` (and graph-input binding equivalent), additive to the ADR-0020 vocabulary,
   with `can_connect`-style preview; the Bindings panel shows a selector field only for `json` sources and no
   pointer logic lives in TypeScript.
7. Recorded run values (ADR-0023) store the selected value; the edge inspector shows the pointer beside it.

## Data / API contracts affected

Graph schema v1 (additive field), hash normalization, edit operations, one binding error reason. No event
schema number is allocated by this spec; coordinate with the owner of the next schema bump.

## Failure behavior

Invalid pointer: validation error, nothing runs. Missing or wrongly typed selected value: consumer fails with the
binding error; no null is substituted.

## Acceptance criteria

- [ ] A v0 graph without `select` has an identical semantic hash, events and CLI output to before.
- [ ] A graph using `select` with `schema_version: 0` fails validation naming the field and the required version.
- [ ] A valid pointer from a `json` output into a `number` input runs and delivers the selected number.
- [ ] Source not `json`, or target `artifact_ref`, fails validation naming the edge.
- [ ] Pointer to a missing path fails the consumer before it starts (marker-file test) with edge and pointer in the error.
- [ ] Selected JSON type differing from the target type fails with observed and expected types; no coercion.
- [ ] `~0` and `~1` escapes select the right keys (table test).
- [ ] Changing `select` changes the semantic hash.
- [ ] `set_edge_select` previewed through `can_connect`-style call refuses invalid choices; renderer contains no pointer parsing (architecture test).
- [ ] Recorded values show the selected value with the pointer.
- [ ] `go test -race` passes for every package touched.

## Required tests

- Unit: pointer grammar and resolution, type pairing, hash.
- Integration: run a graph that selects a nested field; failure paths.
- Renderer: selector field visibility.

## Security / trust considerations

Selection reads only the accepted value already bound; it adds no filesystem or process access. Pointer length
and depth bounded (limits set in implementation).

## Observability

The binding error is a typed failure on the consumer node; edge values keep their existing events.

## Open questions

- Owner decision: ADR-0040 option B (selector) or A (future Code node). If A is chosen, close #185 as deferred to
  a named Code node feature instead of implementing this spec.
- Whether graph outputs (`outputs.*.from`) also accept `select` (recommended: later, not v1).

## Out of scope for this iteration

Graph outputs selection, expressions, Code node.
