# F2.1 - Graph Canvas (document API, operations engine and editable canvas)

**Status:** implemented (slices E1, E2.1, E2.2, E2.3)
**Priority:** P0
**Target phase:** Phase 2 - Local IDE
**Depends on:** F0.1, F0.2, F0.6, F2.5 (desktop shell), F2.5a (design system, i18n, Storybook)
**ADR:** ADR-0020 (edit operations), ADR-0021 (document API and write trust), ADR-0022 (layout), all accepted
**Plan:** `docs/superpowers/plans/2026-11-14-graph-editor.md` (slices E1 and E2)

## Problem

Graphs are authored in a text editor and run from the terminal. The desktop can only display a graph that
already exists. There is no way to create or change a graph from the app, and the engine has no API that
reads, edits and writes a graph file without rewriting it (`graph.Marshal` drops comments and reorders
nodes).

## Goal

A person can open or create a graph file in the desktop app, see it as a canvas and as YAML, add, move,
connect, rename and delete nodes, and save, with the file changing only where the edit requires, and run the
saved graph. The Go sidecar owns every graph rule; the renderer sends operations and renders results.

## Non-goals

- Node configuration forms and port editing (F2.2), the edge/binding editor, graph inputs and outputs (F2.3),
  the issues panel and Run gating beyond the minimum below (F2.4).
- New node types, new schema fields, or any change to schema v0 semantics.
- Templates (F2.12), groups, auto-layout beyond the deterministic fallback and the explicit "Arrange".
- A graph library, projects or workspaces; version history; collaboration; Hosted editing.
- Editing files that contain YAML anchors, aliases or merge keys on the canvas (they open read-only there).
- A second YAML parser or graph validator in TypeScript.

## Functional requirements

### A. Graph document API and operations engine (Go, slice E1)

1. **Endpoints** exactly as ADR-0021: `POST /graphs/grants` (main only), `POST /graphs/open`,
   `POST /graphs/stat`, `POST /graphs/edit`, `POST /graphs/validate` (text, grant or legacy path),
   `PUT /graphs/save`. Bearer token, Host check, no CORS, loopback only, bodies capped (1 MiB for graph
   documents, 64 KiB otherwise), unknown JSON fields rejected.
2. **`open`** returns: `text`, `hash` (sha256 of the bytes), `version` (semantic version), `definition` (a
   typed DTO with JSON tags, separate from runtime types), `diagnostics`, `readonly_canvas` (bool) with
   `readonly_reason` (`anchor`, `alias`, `merge_key`, `parse_error`), `line_ending`, and `label` (file name).
3. **`edit`** takes `{grant, base_hash, text?, ops, ops_version}` where `base_hash` identifies the text the client
   holds: the text the server keeps for the grant (a client with stale text gets 409 `stale_base` and re-opens), or
   `text` the client sends after typing in the YAML view (then `base_hash` is that text's hash). It
   applies ADR-0020 operations to a working copy, runs the safety net, and returns `text`, `hash`,
   `version`, `definition`, `diagnostics` and one `results` entry per operation. It never writes the file.
4. **Operations defined by this spec** (`ops_version: 1`; F2.2 and F2.3 add the rest):

   | `op` | Fields | Effect |
   | --- | --- | --- |
   | `add_node` | `id`, `type` (`shell`, `agent`, `gate`, `human`), optional `layout` `{x, y}` | Adds `nodes.ID` with the type's starter shape (below) and, if given, its layout entry |
   | `remove_node` | `id` | Removes the node, every edge touching it, graph input bindings that target it, graph outputs that read it, its `units` entry and its layout entry |
   | `rename_node` | `id`, `new_id` | Renames the key and every reference (edges, graph input bindings, graph outputs, `units`, layout); refuses an invalid or existing id |
   | `set_name` | `name` | Sets or clears the top-level `name` (presentation: version unchanged) |
   | `set_layout` | `nodes` `{id: {x, y}}`, or `clear: true` | Sets positions in `metadata.layout` (ADR-0022); presentation: version unchanged |
   | `add_edge` | `from` (`NODE.outputs.PORT`), `to` (`NODE.inputs.PORT`) | Appends the edge; refuses if `can_connect` would |
   | `remove_edge` | `from`, `to` | Removes that edge |
   | `can_connect` (query) | `from`, `to` | Changes nothing; result `{ok}` or `{ok: false, code, message}` using the validator's own rules |

   Node ids follow the graph identifier grammar. The starter shape of each type is valid YAML and may be
   semantically incomplete (diagnostics say so): `shell` gets `config: {command: ""}`, `agent` gets
   `config: {adapter: "", workspace: "", task: ""}`, `gate` gets `config: {check_id: "", kind: json_predicate}`,
   `human` gets the required `outputs: {decision: {type: string, required: true}}` and an empty prompt.
5. **`can_connect`** is true only when both ports exist, their declared types are equal, the target input
   has no other provider, source and target nodes differ, and the edge would not create a cycle. It
   reuses the validator's rules (codes `E_BINDING_TYPE_MISMATCH`, `E_INPUT_MULTIPLE_PROVIDERS`,
   `E_GRAPH_CYCLE`, `E_EDGE_*_NOT_FOUND`); no second implementation exists.
6. **Atomic batches, structured errors, safety net, guarantees and refusals** as ADR-0020. Every operation
   has a tree and a typed implementation whose semantic versions agree.
7. **Save** as ADR-0021: grant required, `.yaml`/`.yml`, regular file or absent file in an existing directory,
   no symlink final component, atomic temp-file-and-rename, `base_hash` required to overwrite (`null` creates
   if absent), 409 with the current hash on conflict, file mode preserved, new files 0644.
8. **Run from a grant.** `POST /runs` additionally accepts `graph_grant` in place of `graph_path`, reading the
   saved bytes of the granted file. `graph_path` keeps working unchanged (ADR-0021, decision 9). The run uses
   the saved file, never the editor's unsaved text.
9. **Forwarding.** Main forwards only the exact routes of ADR-0021; `/graphs/grants` is never forwarded.

### B. Desktop editor (slice E2)

10. **Open and new.** Preload `openGraph()` and `newGraph()` (native dialogs in main). A recent-graphs list
    (labels only) is kept by main in user data; picking one makes main issue a new grant. The renderer never
    sees a path. `newGraph` creates an unsaved draft (minimal valid graph with `schema_version: 0`, an id
    derived from the chosen name, empty `inputs`, `nodes`, `edges`, `outputs`); the first save creates the file.
11. **Views.** An editor screen with a segmented control Visual / YAML / Split. YAML is a CodeMirror 6 editor
    (a renderer-only dependency, justified in the PR per the dependency policy) with YAML highlighting, line
    numbers, an accessible name and no focus trap (a documented key leaves it). Split shows both.
12. **One document.** The renderer holds `draftText`, `savedHash`, `dirty`, and the last server `result`
    (definition, version, diagnostics). A canvas action sends operations to `/graphs/edit` and replaces the
    draft with the returned text. A YAML edit is debounced (300 ms) into `/graphs/validate`; on success the
    canvas shows the new definition. While the text does not parse, the canvas keeps the last good definition
    **read-only** with a banner that names the parse error, and operations are disabled until it parses.
13. **Canvas.** `@xyflow/react` with zoom and pan, one node per definition node showing its id, type and
    status of its diagnostics (counts, not text), and **one handle per declared port** with its name. Node
    objects are static; selection and diagnostics reach them through context (the R3 lesson). Dragging a node
    sends `set_layout` on drop. A node without a layout entry uses the deterministic dagre position; an
    "Arrange" button writes all positions.
14. **Toolbar.** `+ Shell`, `+ Agent`, `+ Gate`, `+ Human` (add at the viewport centre or a free spot), Delete,
    Rename, Validate, Undo, Redo, Save, Save and run, Arrange. Every toolbar action is a real button.
15. **Connecting.** Dragging from an output handle to an input handle sends `add_edge` only if `can_connect`
    is ok (checked while hovering, shown on the target handle). A rejected target shows the engine's reason.
    The keyboard path: select a node, choose "Connect from output...", pick a port, then a compatible target
    from a list that disables incompatible ports with the reason (this list is the one F2.3 extends).
16. **Delete and rename** use `remove_node` and `rename_node`; Delete asks only when the node has edges, and
    states how many edges and bindings go with it.
17. **Undo and redo** are an app-level stack of document texts (at most 200), shared by canvas, forms and the
    YAML view (CodeMirror's own history is off, so there is one history). A new edit clears the redo stack.
18. **Dirty, conflict, close.** A dirty indicator in the title row; Save is Ctrl/Cmd+S. On window focus the
    renderer calls `stat`; a clean draft reloads silently, a dirty draft shows a banner with "Keep mine" and
    "Reload". A save refused with 409 shows the same banner. Closing or opening another graph with a dirty
    draft asks to save, discard or cancel.
19. **Read-only canvas** for files with anchors, aliases or merge keys (and for files `graph.Parse` rejects):
    the YAML view stays editable, the canvas and toolbar operations are disabled, and a notice states the
    reason and what remains possible.
20. **Save and run.** If the draft is dirty it is saved first; the run starts from the grant and the app
    shows the new run in the inspector. Run is available whenever the saved file has no blocking diagnostic
    (F2.4 refines the gating).
21. **Localisation and accessibility.** PL and EN strings for every label; diagnostics and engine messages are
    shown as received. Every operation is reachable without a pointer (toolbar buttons, the connect list, the
    node list). Focus is visible, controls are native, state is never colour-only. Reduced motion is honoured.
22. **Stories.** Stories (EN and PL, axe clean) for: empty new graph, a graph with nodes and edges, a node
    with diagnostics, YAML error state, read-only (anchor) state, conflict banner, dirty state, loading and
    error states, over fixtures recorded from the Go API.

## Data / API contracts affected

New local API routes and DTOs (ADR-0021), the operation vocabulary (ADR-0020), `metadata.layout`
(ADR-0022; `docs/graph-spec.md`, Metadata section, is updated in this feature), an additive `graph_grant`
field on `POST /runs`, new preload methods, and a tightened forwarding allowlist in `main.cjs`. Graph schema
v0, the event schema and the run store are unchanged. `desktop/README.md` and F2.5's preload rules are
updated.

## Failure behavior

- A refused batch changes nothing and returns `code`, `message`, `op_index` and the node, edge or path
  involved, with a suggestion.
- Unknown grant, stale `base_hash`, a file that vanished, a directory that changed, a read-only target and a
  full disk give distinct errors; the previous file is always intact (atomic replace).
- The sidecar dying shows the connection-lost state; the draft stays in memory and can be copied or saved
  once the engine is back.
- A file the engine rejects opens as text with a read-only canvas, never as an empty graph.
- A request over a limit (size, number of operations) is rejected with the limit named.

## Acceptance criteria

- [ ] **Round trip:** a graph created from scratch in the UI is saved and `agentplane run` executes it without
      modification, and `agentplane graph validate` accepts it (e2e).
- [ ] **No-op save is byte-identical** for the three example graphs and the CRLF and BOM fixtures (Go test).
- [ ] **Edits are minimal:** on `demo-vertical.yaml`, each operation of this spec changes exactly the expected
      lines (golden diff), preserves all comments and key order, and the typed and tree implementations give
      equal semantic versions.
- [ ] **Layout is not semantics:** moving a node leaves `graph.SemanticVersion` unchanged and adds only
      `metadata.layout` lines; the run's `graph_version` is identical before and after (Go and e2e).
- [ ] **Safety net:** a batch that would change a second node through a YAML anchor is refused and nothing is
      returned for saving; files with anchors, aliases or merge keys open with `readonly_canvas: true`.
- [ ] `can_connect` agrees with `graph.Validate` for every pair of ports of the corpus graphs: whenever it says
      ok, adding the edge produces no new error; whenever it says no, the code equals the validator's.
- [ ] **Delete and rename keep the graph consistent:** after `remove_node` and `rename_node` on the corpus
      graphs, `graph.Validate` reports no dangling reference and the layout has no stale entry.
- [ ] **Write trust:** save refuses an unknown grant, a non-YAML name, a directory, a symlink final component,
      an oversize body, invalid UTF-8, a stale `base_hash` (409) and a create over an existing file (409);
      the old file is byte-identical after each; `/graphs/grants` is unreachable from the renderer; routes
      outside the allowlist return 400.
- [ ] **Run uses saved bytes:** running from a grant with unsaved edits runs the saved file (Go and e2e).
- [ ] **Conflict:** changing the file on disk while the draft is dirty shows the conflict banner within one
      window focus; "Keep mine" saves only after a fresh `base_hash`, "Reload" discards the draft (e2e).
- [ ] **Keyboard only:** an e2e that never uses the pointer adds two nodes, connects them through the connect
      list, renames one, saves and reopens the file with the same content.
- [ ] **Undo/redo** restores the exact previous text for canvas, YAML and layout edits; 200 states cap (unit).
- [ ] **YAML errors:** typing invalid YAML shows the parse error and read-only canvas within 500 ms of the last
      keystroke; fixing it restores the canvas with the last typed text unchanged (e2e).
- [ ] A generated graph of 200 nodes and 400 edges opens and applies an operation in under 250 ms in the Go test.
- [ ] No graph rule is implemented in TypeScript: a test greps `desktop/src` for the validator's codes and for
      type-compatibility logic and finds none outside fixtures and display mapping.
- [ ] `npm run check`, `make check`, `make desktop-e2e` and the story run pass; stories exist for every state in
      requirement 22, EN and PL, zero axe violations, no external requests.

## Required tests

- **Go, operations:** table tests per operation (success, each documented failure, idempotence where stated);
  tree/typed agreement; presentation operations leave the version unchanged; the fidelity corpus of the E0
  spike as golden tests with comment-position checks; anchor/merge refusal; safety-net refusal.
- **Go, API:** endpoint tests (auth, Host, limits, unknown fields), save security cases above, atomicity under
  a simulated failure, `graph_grant` run start, the forwarding allowlist.
- **Renderer unit:** history stack, dirty/conflict state machine, debounced validate, operation builders; no
  graph rules.
- **e2e (real Electron and sidecar):** create, save, run from the CLI; move and diff; conflict; keyboard-only
  path; YAML error; read-only anchor file; recent graphs.
- **Stories:** per requirement 22, with axe in both languages.

## Security / trust considerations

Graph text, node ids, config values and file names are untrusted input. They are rendered as text, never as
HTML. The renderer addresses files only by grant; the sidecar enforces extension, symlink, size and atomicity;
the token and grants never reach the DOM or logs. No graph content leaves the machine. The run-start exposure
of a renderer-supplied `graph_path` (ADR-0021, decision 9) is unchanged and out of scope.

## Observability

Editing is not an execution transition, so it emits no run events. The API logs nothing about document
content. Errors are structured. A save that fails is visible to the person at once.

## Open questions

- Id suggestion for `add_node` (`shell_1`, `shell_2`, ...) is deterministic by type and the lowest free number;
  confirm before implementation that this is the wanted default.
- Whether "Arrange" should preserve manually placed nodes when only some are unplaced (this spec writes all).

## Out of scope for this iteration

Config forms, ports, loops and units editing (F2.2); edge list, graph inputs and outputs, run values (F2.3);
issues panel and Run gating details (F2.4); templates, groups, projects, history, sync, Hosted.
