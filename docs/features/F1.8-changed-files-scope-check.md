# F1.8 - Changed-files Scope Check

**Status:** implemented (ADR-0016)  
**Priority:** P1  
**Target phase:** Phase 1 - Agent Loop

## Problem

Agent nodes can receive an intended file scope, but without a deterministic post-execution check the runtime cannot verify that the agent stayed inside that scope.

A coding agent may be asked to modify only:

```text
internal/runtime/**
tests/runtime/**
```

but accidentally also change:

```text
cmd/agentplane/main.go
```

Relying on the model or provider to self-report its changed files is insufficient for enforcement. The runtime needs an independent, deterministic source of truth and must return structured evidence that can be consumed by Gate, CheckResult, correction loops and the future Run Inspector.

## Goal

Introduce a deterministic changed-files scope check based on Git-observed repository changes and compare those changes against the node's declared allowed paths.

After this feature is complete:

- the runtime can determine the files changed relative to an explicit baseline;
- changed files are compared against an explicit allowed scope;
- `warn` mode records a scope violation without blocking execution;
- `deny` mode returns a blocking/red check result;
- structured evidence lists files outside scope;
- scope violations can flow through the existing CheckResult / Return Envelope path;
- provider-reported changed-file metadata is not trusted as the enforcement source;
- existing agent/gate/retry semantics remain unchanged.

## Non-goals

- Preventing writes before they happen.
- Filesystem sandboxing.
- Git worktree isolation.
- Automatic rollback.
- AST-based blast-radius analysis.
- Semantic dependency analysis.
- LLM-based scope assessment.
- Automatic expansion of allowed scope.
- Permission policy engine.
- Secret management.
- UI / Run Inspector implementation.
- Cloud policy enforcement.

## Functional requirements

1. Scope checking is deterministic.
2. Git-observed repository state is the authoritative source for enforcement.
3. Provider/adapter-reported `changed_files` may be retained as metadata but must not be trusted for enforcement.
4. The check compares changed paths against explicit `allowed_paths`.
5. The implementation supports at least two modes:
   - `warn`;
   - `deny`.
6. `warn` mode must expose the violation in structured output without blocking the graph.
7. `deny` mode must produce a blocking/red result.
8. A violation must expose structured evidence identifying files outside scope.
9. File lists in results/evidence must be deterministically ordered.
10. Untracked/new files must not silently bypass scope checking.
11. Deleted files must be considered.
12. Renames must be handled explicitly and conservatively.
13. Path matching must not confuse similar prefixes such as:

```text
internal/runtime/**
internal/runtime2/file.go
```

14. The check must not silently pass in `deny` mode when the Git state cannot be determined.
15. Existing Gate / CheckResult / Return Envelope contracts must be reused rather than replaced.
16. Existing Shell Node and Agent Adapter behavior must remain backward compatible.

## Scope-check model

Conceptually:

```text
workspace before execution
        |
        v
     baseline
        |
        | agent modifies repository
        v
workspace after execution
        |
        v
Git-observed changed paths
        |
        v
compare to allowed_paths
        |
        +-- all allowed ------> green
        |
        +-- violations -------+--> warn mode: observable, non-blocking
                              |
                              +--> deny mode: red/blocking
```

The exact Go representation should follow the existing check/gate abstractions rather than introduce a parallel result system.

## Source of truth

### Git-observed changes

Enforcement must use Git-observed changes from the local repository.

The implementation may use Git plumbing/porcelain commands or an existing repository helper, but it must detect the relevant change classes rather than relying on a single naive command that omits untracked files.

At minimum the design must account for:

- modified tracked files;
- staged files;
- newly created/untracked files;
- deleted files;
- renamed files.

### Provider-reported changed files

`AgentExecutionOutput.changed_files` is useful metadata, but it is not an enforcement authority.

Conceptually:

```text
adapter reported files  -> metadata / observability
Git observed files      -> scope enforcement
```

A provider must not be able to hide a violation by omitting a path from its own output.

## Baseline semantics

The scope checker must compare the post-execution repository state against a clearly defined pre-execution baseline.

A baseline must be captured before the unit of work begins.

The approved implementation may use one of the following, depending on the current runtime architecture:

- base commit/tree identity;
- explicit Git revision;
- repository snapshot/reference suitable for diffing;
- another deterministic baseline already present in the runtime.

The implementation must document what the baseline means.

### Pre-existing changes

The scope checker should avoid attributing unrelated pre-existing user changes to the current agent attempt.

If the current pre-Phase-3 runtime cannot perfectly distinguish pre-existing dirty state from agent-created changes, the implementation must:

- choose the safest practical semantics;
- make the limitation explicit;
- avoid silently claiming stronger isolation guarantees than the runtime actually provides.

F1.8 does not implement worktree isolation. That belongs to F3.1.

## Allowed-path contract

Reuse the existing `allowed_paths` / scope representation introduced by the Agent Adapter Contract and Return Envelope where practical.

The matcher should remain intentionally small and predictable.

Supported forms should be limited to the patterns approved during planning, for example:

- exact relative file path;
- directory subtree / glob if the project already supports it.

Do not introduce a new custom path-expression language.

Conceptually:

```text
allowed_paths:
  - internal/runtime/**
  - tests/runtime/**
```

The exact matching implementation must be documented and covered by tests.

## Path normalization

All repository paths must be normalized before matching.

At minimum the implementation should define behavior for:

- repository-relative paths;
- `./` prefixes;
- platform path separators;
- redundant separators;
- `..` traversal attempts;
- repository-root anchoring.

A normalized path must not escape the repository root.

Prefix matching must not be used as a substitute for proper path matching.

Example:

```text
allowed: internal/runtime/**

internal/runtime/a.go       -> allowed
internal/runtime/sub/b.go   -> allowed
internal/runtime2/c.go      -> denied
```

Symlink-specific enforcement is not required unless the current repository/path abstraction already provides it cleanly. Do not claim sandbox-level guarantees.

## Check modes

### Warn

`warn` mode records a scope violation but does not block the graph.

Conceptually:

```text
verdict: green (ADR-0016; superseded "warning / non-blocking")
reason: changed_files_outside_scope
```

Use the current CheckResult/Gate semantics. Do not invent a separate verdict model if the runtime already represents warnings differently.

### Deny

`deny` mode produces a blocking/red result.

Conceptually:

```text
verdict: red
reason: changed_files_outside_scope
```

Downstream execution follows the existing Gate/CheckResult semantics.

## CheckResult integration

Reuse the existing Check Result Contract.

A scope violation should carry enough structured information for CLI, correction loop and future UI consumption.

Conceptually:

```text
CheckResult
  verdict
  reason: changed_files_outside_scope
  evidence[]
  scope[]
  check_id
  duration
```

Do not duplicate CheckResult with a scope-specific result type unless a lightweight typed detail payload is already part of the existing contract.

## Evidence contract

Violation evidence must identify the files outside scope.

At minimum preserve:

- offending paths;
- allowed scope;
- check mode;
- check identifier/reason.

Optionally include the full observed changed-file list if that remains small and useful.

Do not embed full Git diffs into the CheckResult. Large diff content belongs in later artifact handling.

Conceptual evidence:

```text
reason: changed_files_outside_scope

outside_scope:
  - cmd/agentplane/main.go

allowed_scope:
  - internal/runtime/**
  - tests/runtime/**
```

File paths in evidence must be sorted deterministically.

## Rename semantics

Renames must not allow a scope bypass.

The implementation plan must explicitly define the behavior for at least:

- allowed -> allowed;
- allowed -> disallowed;
- disallowed -> allowed;
- disallowed -> disallowed.

A conservative interpretation is preferred.

For example, a rename from an allowed path to a disallowed path must be treated as a violation.

If both old and new names are available from Git, preserve enough information to explain the violation.

## Deleted files

Deleting a file is a modification and must participate in scope enforcement.

Deleting a path outside `allowed_paths` must produce a violation in `deny` mode.

## Untracked files

New untracked files must be included in the observed changed-file set.

A newly created path outside scope must not bypass enforcement simply because `git diff` does not list untracked files by default.

## Git failures

The implementation must have explicit behavior when Git inspection cannot complete.

Examples:

- Git executable unavailable;
- workspace is not a Git repository;
- invalid baseline;
- Git command failure;
- malformed Git output if parsing is required.

### Fail-open / fail-closed

In `deny` mode, inability to determine the changed-file set must not silently become green.

Use the existing check failure/error conventions to represent an indeterminate enforcement result.

For `warn` mode, the approved plan may choose a non-blocking diagnostic if that matches existing CheckResult semantics, but the uncertainty must remain observable.

## Interaction with correction loop

F1.8 does not introduce new retry behavior.

A red scope result should flow through the existing contracts:

```text
scope check red
     |
     v
CheckResult
     |
     v
Return Envelope
     |
     v
correction attempt
```

The correction attempt should receive concrete evidence such as:

```text
Files outside allowed scope:
- cmd/agentplane/main.go

Allowed scope:
- internal/runtime/**
```

The runtime must not automatically enlarge `allowed_paths` to include the violating files.

## Relationship to Gate Node

F1.8 is a deterministic check that should plug into the existing gate/check architecture.

Do not create a separate execution path for scope validation.

The check must remain usable independently of any coding-agent provider.

## Relationship to Agent Adapter Contract

The Agent Adapter Contract may already carry:

```text
allowed_paths[]
changed_files[]
```

F1.8 gives deterministic meaning to `allowed_paths` for enforcement.

It does not change the rule that adapter/provider-reported changed files are only metadata.

## Security / trust considerations

Changed-files scope checking is a detection/control mechanism, not a sandbox.

It can answer:

```text
Did the workspace change outside the declared scope?
```

It does not guarantee:

```text
The agent was physically unable to write outside the scope.
```

Write prevention belongs to later workspace isolation / execution policy features.

Do not market or document F1.8 as filesystem isolation.

## Determinism

For the same:

- repository state;
- baseline;
- allowed paths;
- check mode;

the result should be the same.

Deterministic behavior requires at least:

- stable path normalization;
- stable matcher semantics;
- sorted observed/offending path lists;
- no dependence on Go map iteration order;
- no LLM involvement.

## Data / API contracts affected

Potentially affected contracts:

- check/gate interface;
- `CheckResult`;
- allowed-path scope representation;
- repository/Git helper package;
- correction-loop / Return Envelope integration;
- Agent execution metadata where baseline identity must be carried.

Changes should be additive where practical.

Existing Shell graphs and agent workflows that do not enable the check must continue to work.

## Proposed API shape

The exact public API is decided during PLAN ONLY and should follow the repository's existing check abstraction.

Conceptually, the operation is equivalent to:

```text
checkChangedFiles(
  repository,
  baseline,
  allowedPaths,
  mode,
) -> CheckResult
```

Do not introduce this exact function signature if the current Gate/Check API already has a better integration point.

Avoid a standalone generic policy framework.

## Git command execution

Git inspection must use safe deterministic process execution.

Requirements:

- explicit executable and argv;
- no unnecessary `sh -c` / shell interpolation;
- explicit repository working directory;
- command failures are preserved as structured errors/check failures.

Reuse existing process/Shell/Git helpers where sensible without routing repository inspection through an Agent node.

## Failure behavior

The following outcomes must be distinguishable where practical:

- all changed files are allowed;
- out-of-scope files found;
- warning-only violation;
- blocking violation;
- Git unavailable;
- not a Git repository;
- invalid baseline;
- path normalization/matching error.

Reuse existing CheckResult/error conventions rather than creating a new error hierarchy.

## Observability

The check result must be serializable/traceable through existing run events/check metadata so future Run Inspector views can answer:

- what scope was allowed?
- what files actually changed?
- which files violated scope?
- was the check in warn or deny mode?
- why did the gate block?

Do not implement the Run Inspector itself in F1.8.

## Required tests

### Unit

- no changed files -> green;
- one allowed changed file -> green;
- multiple allowed changed files -> green;
- one forbidden changed file -> red in deny mode;
- one forbidden changed file -> warning/non-blocking in warn mode;
- mixed allowed and forbidden files;
- nested allowed path;
- similar-prefix path is not incorrectly allowed;
- deterministic sorted evidence;
- `./` path normalization;
- `..` / repository escape is rejected or normalized safely according to the approved design;
- duplicate allowed-path rules do not change semantics;
- empty allowed scope behavior is explicit;
- Git failure behavior for warn mode;
- Git failure behavior for deny mode.

### Git behavior

- modified tracked file;
- staged modification;
- newly created/untracked file;
- deleted file;
- rename allowed -> allowed;
- rename allowed -> forbidden;
- rename forbidden -> allowed;
- invalid baseline;
- non-Git workspace.

### Contract / integration

- temporary repository with baseline commit;
- modify one allowed file and one forbidden file;
- execute scope check;
- verify red CheckResult in deny mode;
- verify offending path appears in structured evidence;
- verify allowed path does not appear as a violation;
- provider-reported changed-file list omits forbidden path but Git-observed check still rejects;
- CheckResult can be consumed by existing Return Envelope/correction path without provider-specific special cases;
- existing Shell Node behavior remains unchanged;
- existing Agent Adapter execution remains unchanged when F1.8 is not configured.

## Temporary repository test strategy

Integration tests should create isolated temporary Git repositories rather than mutate the developer's working tree.

A representative test should:

1. create a temporary directory;
2. initialize a Git repository;
3. create files;
4. create a baseline commit;
5. record the baseline identity;
6. modify an allowed file;
7. modify/create a forbidden file;
8. run the scope checker;
9. assert the structured result/evidence;
10. clean up through the test framework.

Tests must not change the process-global current working directory if avoidable.

## Documentation requirements

Document at least:

- what `allowed_paths` means;
- supported path matching syntax;
- how the baseline is determined;
- what file states are included;
- warn vs deny semantics;
- the fact that Git observation is authoritative for enforcement;
- limitations before F3.1 worktree isolation;
- the fact that F1.8 detects scope violations but does not prevent writes.

## Open questions

Resolved during planning; decisions are recorded in ADR-0016. Kept for traceability:

- What baseline representation best fits the current runtime: commit SHA, tree SHA or another snapshot abstraction?
- How does the runtime currently represent the pre-execution repository state, if at all?
- Which exact path/glob syntax already exists and can be reused safely?
- How should warning results map onto the current CheckResult verdict model?
- What is the smallest Git command set that correctly captures tracked, untracked, deleted and renamed paths?
- Should rename evidence preserve both old and new paths?
- Where should repository inspection live: an existing Git helper package or a new small internal package?
- Does baseline identity need to be carried on attempt metadata now, or can it remain internal to the scope check integration?
