# F2.6 - Run Inspector: Overview (remaining gap)

**Status:** accepted for implementation (decisions 2026-11-17). Gap spec: most of the roadmap item is already delivered; see "Already delivered".
**Priority:** P0
**Target phase:** Phase 2 - Local IDE
**Depends on:** F0.6 (events), F1.5 (check results), F2.5 (live map, API, reducer), F2.5a (KPIs, timeline,
event log), F2.9 (run store). Roadmap lists F0.6 and F1.5 only; the Phase 2 specs above are the real base.
**ADR:** none expected (renderer-only, no event, API, persistence or trust-boundary change); decision 9
**Companion:** `F2.7-run-inspector-node-detail.md` (both touch `desktop/src/reducer.ts`; they can land in
either order)

## Problem

The roadmap asks the overview to answer four questions: what happened, where the system waited, what failed
and what it cost in time. The desktop already answers the first and the time question for the common case
(status, wall clock, node time, saved time, retries, per-second timeline, event log). It does not answer
"where did the run wait" (scheduler queue versus a human), "what failed" (the person must click through nodes),
"which chain of nodes decided the wall clock" (critical path), and it cannot narrow the view to failed,
retried, human or slow nodes. "Agent time" from the roadmap is shown only as an undifferentiated "node time".

## Goal

The Run Inspector overview shows, for a live or stored run and from recorded events only: the time spent
waiting (queued by the scheduler, waiting for a human), the agent time, a basic critical path, a short "what
failed" outcome summary, attempt-aware timeline rows that open the node, and node filters
(failed, retried, human, slow). Every value is derived by a pure function over the reduced run and the graph
summary; unknown stays unknown.

## Non-goals

- Advanced critical path (resource-aware, what-if) - roadmap says P1.
- Any engine, event, API or bridge change: everything is derived from existing events and `graph_summary`.
- Node detail content (inputs, outputs, activity, changed files): F2.7.
- Cancel, rerun, export, token or cost figures, blast radius.
- Cross-run comparison, a runs list with filters or search (F2.9 index, later).
- The UI owning run status or scheduling decisions.

## Functional requirements

1. **Reducer facts.** The reducer additionally keeps, per node, `readyAt` (timestamp of `node_ready`) and the
   timestamps of `approval_requested` and `approval_decided`, and per run `graphVersion` and `runId`. Nothing
   else in the reduction changes. Replayed sequence numbers are ignored as today.
2. **Waiting.** Pure selectors compute, per node, `queuedMs` = `node_started` minus `node_ready` and `humanWaitMs`
   = `approval_decided` minus `approval_requested`. A missing timestamp gives unknown, never 0. For a node still
   waiting in a run that is still going, the value is labelled "so far" and measured to the newest event, never
   to the clock. The summary adds "Queued" and "Human wait" totals and a "Waited longest" line naming the
   node and the kind of wait (queue or human), at most three nodes.
3. **Agent time.** The summary adds "Agent time": the sum of `durationMs` of finished nodes whose graph type is
   `agent`. It is "not applicable" for a graph with no agent node, and unknown while no agent node has
   finished (decision 2). "Node time" and "Saved" keep their F2.5a definitions; their help text says that human
   wait is part of node time, and "Human wait" is shown as its own figure (decision 3).
4. **Critical path (basic).** A selector returns the longest path by node duration over the graph's
   data-dependency edges, restricted to nodes that started: weight is `durationMs` for a finished node and
   the time from start to the newest event for an unfinished node of a running run (the result is then labelled
   "so far"). Nodes that never started (skipped, cancelled before start) weigh nothing and are not on the path.
   Ties are broken by node ID in ascending order so the result is deterministic. The result is the ordered
   node IDs, the total, and, when the wall clock is known, the total as a share of it. It is unknown when no
   node has a duration. The overview lists the path as text; each path node carries a text badge "Critical"
   on the map and in the timeline (not colour alone). Queue time is not part of the path (decision 4), so the
   wall clock can exceed the path total.
5. **Outcome summary.** For a run whose status is `failed`, `cancelled` or `interrupted`, the overview shows
   "What failed": each failed node with its `failure_kind`, diagnostic codes and the reason of its last red
   check (when one exists), the count of skipped and cancelled nodes, and for a rejected human node the
   decision and comment. Each entry opens that node. A succeeded or running run shows no such card (a running
   run with a failed node shows the failed entries labelled "so far"). Reason text is shown as received.
6. **Attempt-aware timeline.** `timeline()` additionally returns, per row, ordered segments: `queued`,
   `attempt` (with attempt number and outcome), `human` and `running`, each with start and end second
   offsets from run start and clipped to the column cap and bucket size already in force (the existing dot
   grid stays, with per-attempt segments added; decision 7). A retry attempt is
   drawn in a distinct tone from the first attempt, a queued interval as hollow dots and a human wait in
   the human tone. Each row is a native button that selects the node (keyboard: Enter and Space) and is
   named in text with node ID, attempt count, start offset, duration and outcome. A visually hidden table lists
   the same segments, so the chart has a text alternative. Column cap and bucketing (600 columns) are unchanged.
7. **Node filters.** A segmented control above the timeline filters nodes by All, Failed, Retried, Human and
   Slow, with the count of matching nodes on each option. Predicates: Failed = node status `failed`; Retried =
   more than one attempt; Human = graph type `human`; Slow = duration at least `max(1 s, 2 x median)` of the
   run's finished node durations, defined only when at least three nodes have finished, otherwise the Slow
   option is disabled with that reason (decision 1). Non-matching nodes are dimmed (and labelled) on the map
   and hidden from the timeline; the selected node is never hidden. The filter is view state only and resets
   with the run. Filters apply to nodes only; the event log keeps its own, unchanged filters (decision 5).
8. **Run identity.** The header shows the full run ID as selectable text, the start time (locale formatted)
   and the first 12 characters of the graph version; each is unknown when absent. No filesystem path is shown.
9. **States.** While the stream is lost, every new value is labelled as of the last event and none is
   extrapolated; an interrupted run's unfinished segments end at its last event and say so.

## Data / API contracts affected

None on the wire. `GET /runs/{id}` and the event stream are unchanged. Renderer-internal: `NodeView` and
`RunView` gain the fields of requirement 1; `insight.ts` gains the selectors of requirements 2-7;
`GraphSummary` (already carrying node type and edges) is only read. New i18n keys in `en` and `pl`.

## Failure behavior

- A node with a missing `node_ready`, `node_started` or approval timestamp has unknown waits; totals skip
  unknown values and the card says how many nodes were skipped.
- A stored stream with no terminal event (interrupted run): waits and the critical path end at the last
  event and are labelled; the status stays `interrupted`.
- `GraphSummary` unavailable (graph still loading, or the run's graph did not parse): agent time shows
  unknown, critical path and Human/Slow filters are disabled with the reason; nothing else breaks.
- Timestamps out of order (clock steps): a negative interval is unknown, never negative.
- Unknown event types and the schema-11 workspace events are ignored by the new selectors.

## Acceptance criteria

Fixtures: `desktop/test/fixtures/demo-approve.json`, `demo-reject.json`, `exhausted.json`,
`agent-scope-retry.json`, plus synthetic event sequences built in the test file (as `insight.test.ts` does).

- [ ] Human wait of a synthetic run whose `approval_requested` is at +1 s and `approval_decided` at +61 s is
      60000 ms; for the recorded `demo-approve` human node (decided by flag, sub-millisecond) it equals the
      timestamp difference of its two events (independent reference calculation). The recorded fixtures are
      too fast to prove non-trivial waits, so synthetic sequences carry those checks.
- [ ] For a synthetic run where `node_ready` precedes `node_started` by 2000 ms, `queuedMs` is 2000; with the
      `node_ready` event removed it is unknown (not 0).
- [ ] A run stopped at `approval_requested` reports human wait "so far" up to the newest event, and the value
      does not change when the test clock moves.
- [ ] "Agent time" equals the sum of the agent nodes' `node_finished.duration_ms` in `agent-scope-retry.json`;
      for `demo-approve.json` (no agent node) it is "not applicable"; before any agent node finishes it is unknown.
- [ ] Critical path of a synthetic diamond (a -> b, a -> c, b -> d, c -> d) with durations 1, 5, 2, 1 is
      a, b, d with total 7; with equal b and c durations the tie goes to the lower node ID; every consecutive
      pair on the path is a graph edge; skipped nodes are absent; with no durations it is unknown.
- [ ] A 500-node chain yields a 500-entry path (no recursion limit, linear in nodes plus edges).
- [ ] "What failed" for `exhausted.json` lists the failed node with its `failure_kind` and a reason equal to the
      `reason` of its last red `gate_check`; for `demo-reject.json` it lists the rejected human node with the
      decision and the number of skipped dependents; a succeeded run has no card.
- [ ] Node filters on recorded runs: Retried marks exactly `flaky` in `demo-approve`; Failed marks exactly the
      failed node in `exhausted`; Human marks exactly the human node; Slow follows the chosen rule on a
      synthetic duration set; option counts equal the marked counts; All restores everything; the selected
      node stays visible under every filter.
- [ ] Timeline segments for the `flaky` node of `demo-approve` are two attempt segments (attempt 1 outcome
      `rejected`, attempt 2 outcome `accepted`) whose offsets equal the attempt events' timestamps; no segment
      overlaps another of the same row.
- [ ] A timeline row is a `button`; Enter and Space select the node; the node panel opens in the same view and
      the run summary, timeline and event log remain rendered (component test and e2e).
- [ ] Each timeline row's accessible name and the hidden table contain node ID, attempt count and outcome;
      axe reports zero violations on the new stories.
- [ ] Run header shows run ID, start time and a 12-character graph version for a recorded run, and unknown
      for a synthetic stream without them.
- [ ] Live, replayed, batched and duplicated delivery of the same events give equal waits, critical path,
      outcome summary, timeline segments and filter counts (extends the live-and-replay test).
- [ ] For a synthetic 10,000-event run the timeline keeps at most 600 columns and at most
      `3 x attempts + 2` segments per row, and the event tail keeps 200 rows.
- [ ] `en` and `pl` catalogues have identical keys and parameter names, including Polish plural cases 1, 2-4,
      5+, 12-14 and 22 for any new count message.
- [ ] No file under `internal/`, `cmd/` or `desktop/electron/` changes (diff stat), the preload method set is
      unchanged, and `npm run check`, `make desktop-e2e` and `make desktop-stories` pass.

## Security / trust considerations

- Node IDs, failure kinds, reasons, diagnostic codes, approval comments and run IDs are untrusted text and are
  rendered as text, never HTML. No `dangerouslySetInnerHTML`.
- No local path, token, port or environment value is shown or derived; the renderer gains no bridge method
  and the CSP and route allowlist do not change. Run ID and graph version are not secrets.
- Derived figures are labelled as computed from events and carry no authority over run state.

## Observability

No new events. Every number is a pure function of recorded events and the graph summary, so a stored run and
a live run give the same overview.

## Decisions

These were open questions in the previous draft. Each is decided below with a one-line rationale. Decided
2026-11-17 (lead, delegated by the product owner); the team may revisit.

1. **"Slow":** duration >= `max(1 s, 2 x median)` of the finished nodes' durations, only with at least three
   finished nodes. Rationale: relative to the run, so it needs no setting and no fixed threshold that suits no graph.
2. **"Agent time":** the sum of Agent-node durations, shown next to "Node time" (not a rename). Rationale: keeps
   the F2.5a figure intact and adds the roadmap's missing one.
3. **Human wait:** stays inside "Node time" and "Saved" (F2.5a FR13 unchanged) and is shown as its own figure.
   Rationale: no change to an already delivered definition; the help text states it.
4. **Critical path:** longest duration path over data edges; queue wait excluded and shown separately.
   Rationale: the advanced, scheduler-aware path is P1 in the roadmap.
5. **Filter scope:** filters apply to nodes (map, timeline) only; the event log keeps its own filters. Rationale:
   two different things (nodes, events) should not share one control.
6. **Tokens and "Model calls":** stay "unknown" until F3.10 provides usage. Rationale: a proxy count would read as
   a measurement (deterministic evidence over inference).
7. **Timeline shape:** keep the dot grid and add per-attempt segments by tone and text. Rationale: no new design
   system work and the existing stories and cap keep applying.
8. **Runs list filters:** none in this feature. Rationale: better built on the F2.9 index.
9. **ADR:** none. Rationale: renderer-only, no durable contract changes; revisit if another client (hosted web)
   needs the critical-path and "slow" definitions to be binding.
