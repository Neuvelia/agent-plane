# F1.1 - Agent Adapter Contract

**Status:** ready for implementation (contract decisions in ADR-0009; code pending)
**Priority:** P0
**Target phase:** Phase 1 - Agent Loop

## Problem

The execution core can run deterministic Shell nodes, but it has no provider-neutral contract for executing coding agents. Adding Codex, Claude Code or another agent directly to the runtime would couple execution-core to provider-specific CLI behavior and make future adapters difficult to add or replace.

## Goal

Introduce a small, provider-neutral Agent Adapter Contract that allows the runtime to execute an Agent node without knowing which coding-agent provider is behind it.

After this feature is complete:

- execution-core can invoke an agent through a generic adapter contract;
- adapters declare their capabilities instead of the runtime assuming them;
- agent input and output have normalized contracts;
- a deterministic MockAdapter proves the contract through reusable contract tests;
- no real coding-agent provider is implemented yet.

## Non-goals

- Implementing Codex CLI, Claude Code, Gemini CLI or any other real provider.
- Normalizing every provider-specific feature.
- Implementing Unified Streaming from F1.3.
- Implementing Gate Node, Check Result, retries or correction loops.
- Enforcing changed-files scope.
- Implementing Git worktrees, sandboxing, secrets management or permissions policy.
- Building a plugin SDK, marketplace or dynamic adapter loading system.

## Functional requirements

1. Define the minimal provider-neutral `AgentAdapter` contract in ADR-0009:
   identity, capability detection and context-cancellable execution.
2. An adapter has a stable logical identity.
3. The adapter can report whether it is available and expose a small capability report.
4. The contract supports execution of an agent task in an explicit workspace.
5. Execution input supports at least:
   - task;
   - workspace;
   - allowed paths / intended scope;
   - explicit context references;
   - explicit environment references.
6. Execution output supports at least:
   - summary;
   - changed files;
   - artifact references or lightweight artifact metadata;
   - raw provider metadata;
   - optional usage metadata.
7. Missing usage data remains unknown and must not be normalized to zero.
8. Provider-specific data may be retained as raw metadata, but execution-core must not interpret it.
9. Cancellation must integrate with the runtime's existing context/cancellation semantics.
10. The runtime must be able to dispatch an Agent node through the generic contract without provider-specific branching.
11. Existing Shell node behavior and Phase 0 CLI behavior must remain unchanged.
12. A deterministic MockAdapter must be available for tests only.
13. A reusable contract/conformance test suite must verify the public adapter semantics.
14. An Agent node uses the schema-v0 configuration and declared output ports
    specified in `docs/graph-spec.md`; invalid Agent config fails before
    adapter execution.
15. The adapter receives scheduler-owned run/node correlation. Attempt ID is
    empty until F1.6 creates actual attempts.

## Capability contract

The capability model remains intentionally small and represents at least:

- adapter availability;
- adapter/provider version when known;
- cancellation support;
- streaming support declaration;
- usage reporting support;
- workspace execution support.

Unknown capability information must remain distinguishable from an explicit `false` when that distinction matters.

Do not create a broad provider feature matrix in this iteration.

## Execution input contract

The normalized input should represent the minimum context required by a coding agent without introducing hidden global state.

Conceptually:

```text
AgentExecutionInput
  task
  workspace
  allowed_paths[]
  context_refs[]
  environment_refs[]
  run/node/attempt correlation
```

### Task

The bounded unit of work the agent should perform.

### Workspace

An explicit absolute local path compatible with the existing runtime. F1.1
checks the path shape, but does not create worktrees, isolate writes, or prove
that a real provider can use the directory.

### Allowed paths

The intended modification scope. In F1.1 this is contract data only. Deterministic enforcement belongs to F1.8.

### Context references

Explicit references to additional context such as files, text or artifacts. This iteration must not implement retrieval, vector memory, RAG or automatic context discovery.

### Environment references

Explicit references to environment/configuration values required by the adapter. The contract must not automatically expose the complete parent process environment and must not implement secret resolution.

## Execution output contract

Conceptually:

```text
AgentExecutionOutput
  summary
  changed_files[]
  artifacts[]
  raw_metadata
  usage
```

### Summary

Short normalized description of the result when available.

### Changed files

Files associated with the execution result. F1.1 defines the field only; F1.2 may populate it using Git independently of provider claims.

### Artifacts

References or lightweight metadata only. Large artifact storage belongs to F3.5.

### Raw metadata

Serializable provider-specific metadata that the core runtime stores/passes through but does not interpret. Raw metadata must not intentionally contain secrets.

### Usage metadata

Optional provider-reported usage information. Unknown values remain unknown. F1.1 does not implement pricing or cost aggregation.

## Data / API contracts affected

Potentially affected contracts:

- execution/runtime interface used by F0.4;
- Agent node representation in graph schema if adapter selection is not already represented;
- event/correlation types from F0.6;
- normalized execution result types;
- adapter lookup/registration used by runtime.

Changes should be additive where possible. Existing Shell graphs must remain valid.

## Runtime integration

The intended dependency direction is:

```text
execution-core
    |
    v
AgentAdapter
    |
    +-- MockAdapter      F1.1 tests
    +-- CodexAdapter     F1.2
    +-- other adapters   later
```

The runtime must not contain logic such as:

```text
if adapter == "codex" ...
if adapter == "claude" ...
```

If adapter lookup is required, use the smallest explicit registry/lookup mechanism necessary for local execution. Do not implement plugin discovery.

## Event / streaming boundary

F0.6 remains the runtime event foundation. F1.1 keeps its lifecycle event
schema and IDs; normalized Agent outputs are available through accepted graph
ports and the in-memory run result, not from event-only replay. Do not place
task text, raw provider metadata, environment values or full output in
lifecycle event payloads. F1.2 defines trace evidence for changed files;
F1.3 defines provider-neutral progress, retention and backpressure.

F1.1 may expose the minimum event/sink seam required by the adapter contract, but it must not implement the provider-neutral event vocabulary planned for F1.3.

Provider-specific event shapes must not leak into execution-core.

## Cancellation

Cancellation uses the runtime's existing `context.Context` semantics. F1.1
does not add an explicit `Cancel` method. F1.2 must demonstrate termination of
its real process/session and document any justified optional interface before
changing this public contract.

## Failure behavior

The public contract must make the following failure categories distinguishable where practical:

- adapter unavailable;
- capability detection failure;
- invalid execution input;
- execution start failure;
- execution failure;
- cancellation;
- unsupported capability.

Reuse existing runtime error/result conventions where possible. Do not build a large generic error framework.

## Mock adapter / contract tests

Implement a deterministic MockAdapter for tests only.

Tests must be able to control at least:

- capability report;
- successful output;
- execution error;
- cancellation behavior;
- raw metadata;
- usage metadata;
- emitted events if events are part of the approved F1.1 contract.

The reusable contract suite should test the public semantics rather than MockAdapter internals.

## Acceptance criteria

- [ ] A provider-neutral Agent Adapter Contract exists.
- [ ] A MockAdapter passes reusable contract/conformance tests.
- [ ] Runtime can execute an Agent node through a generic adapter path using the mock.
- [ ] Execution-core contains no provider-specific Codex/Claude/Gemini branches.
- [ ] Capability detection has explicit available/unavailable behavior.
- [ ] Task, workspace, allowed paths, context refs and environment refs propagate through the contract.
- [ ] Normalized output supports summary, changed files, artifact references, raw metadata and optional usage.
- [ ] Unknown usage is not represented as zero.
- [ ] Cancellation behavior is covered by tests.
- [ ] Agent config rejects unknown adapter, missing/both task sources, wrong
      types and unsupported output ports before adapter execution.
- [ ] Adapter correlation matches the run/node IDs in lifecycle events;
      attempt ID remains empty.
- [ ] No provider output or raw metadata is added to lifecycle payloads.
- [ ] Existing Shell node tests and CLI tests still pass.
- [ ] `go test -race ./...` passes.
- [ ] `make check` passes.

## Required tests

### Unit

- adapter identity;
- available capability detection;
- unavailable adapter detection;
- task propagation;
- workspace propagation;
- allowed paths propagation;
- context reference propagation;
- environment reference propagation;
- normalized successful output;
- summary;
- changed files;
- artifact references/metadata if implemented;
- raw metadata round-trip;
- known usage metadata;
- unknown usage metadata;
- adapter execution error;
- cancellation;
- unsupported capability where applicable.

### Contract / conformance

- MockAdapter satisfies the public adapter contract;
- contract suite can be reused by later real adapters where appropriate.

### Integration

- runtime dispatches Agent node through generic adapter lookup;
- no provider-specific runtime branch is required;
- Shell Node behavior remains unchanged;
- existing Phase 0 CLI behavior remains unchanged.

## Security / trust considerations

Agent adapters execute untrusted or semi-trusted tooling against a workspace.

For F1.1:

- do not automatically pass the full process environment;
- do not resolve or store secrets;
- do not expose unrelated repository content through hidden context;
- make workspace, scope and context explicit;
- raw metadata must not intentionally include secrets;
- allowed paths are advisory until deterministic enforcement is added later.

F1.1 does not claim sandboxing or least-privilege enforcement.

## Observability

The contract must retain F0.6 run/node/attempt correlation so future traces can associate adapter execution with the correct graph execution.

The implementation should expose enough structured metadata to support later Run Inspector views without requiring the UI to parse provider-specific prose.

Full normalized agent streaming is deferred to F1.3.

## Open questions

None blocking F1.1. ADR-0009 resolves the minimal interface, capability
detection method, preparation/collection within `Execute`, context
cancellation, opaque JSON metadata, schema-v0 Agent config, correlation and
event boundary. F1.2/F1.3 own real CLI process and streaming questions.

- Codex CLI integration (F1.2).
- Claude Code / Gemini adapters.
- Provider authentication/session management.
- Unified Streaming event normalization (F1.3).
- Gate Node (F1.4).
- Check Result Contract (F1.5).
- Correction Loop / maxAttempts (F1.6).
- Return Envelope / scoped retry (F1.7).
- Changed-files Scope Check enforcement (F1.8).
- Git worktrees / workspace isolation.
- Secret store and secret resolution.
- Execution permission policy.
- UI / Run Inspector.
- Cloud execution/control plane.
- Plugin/Adapter SDK and dynamic loading.
