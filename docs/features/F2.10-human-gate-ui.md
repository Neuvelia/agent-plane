# F2.10 - Human Gate UI

**Status:** draft (spec review pending; implementation not started)
**Priority:** P0
**Target phase:** Phase 2 - Local IDE

Contract decisions live in
[ADR-0019](../adr/0019-local-human-gate-contract.md). This spec states the
observable behavior and acceptance criteria. Visual targets for the approval UI
require owner approval (deadline: 2026-11-10 evening) before UI coding.

## Problem

`type: human` is recognized by the graph safe-view projection but has no
runtime semantics: a graph cannot pause for a person, and the desktop app
cannot show evidence, record an approve/reject decision or continue the run.
AGENTS.md requires human gates to be driven by consequence, not model
confidence, and trace to be part of correctness.

## Goal

A local graph run can contain a Human node that pauses only its own unit,
presents bounded evidence in the desktop app, accepts exactly one durable
decision, and continues or fails deterministically. The decision is a trace
fact visible in run history.

## Non-goals

- Remote/web approval, accounts, RBAC, multiple approvers (F4.8).
- Timeouts, escalation, notifications.
- Resuming a waiting run after sidecar/app death (Phase 3 durable execution).
- Explicit reject-to-node transitions or replanning (only run-ending reject in
  this iteration; see Open questions).
- LLM-assessed or confidence-driven auto-approval.

## Functional requirements

1. Graph schema: `type: human` with `config.prompt` (static text, bounded),
   `config.blast_radius` (`L1|L2|L3`, declared consequence class, default `L3`),
   typed `inputs` shown as evidence, and an output `decision` of enum
   `approved|rejected`. Config validation follows the existing strict-unknown-key
   policy. No secrets in `prompt`.
2. Runtime: when dependencies are satisfied the Human node enters `waiting`
   (a new non-terminal node state), starts no process and holds no scheduler
   slot. Independent branches keep running. Dependents do not start.
3. A decision request is addressed by `(run_id, node_run_id, request_id)`.
   Submitting `approved` marks the node succeeded with `decision=approved`.
   Submitting `rejected` marks the node failed with reason `human_rejected` and
   follows the normal failure path (no accepted sibling is rerun).
4. The decision is committed durably before the node transitions and before
   dependents start. Re-submitting the same decision with the same
   idempotency key returns the original outcome without a second event.
   A different decision for an already decided request fails with
   `decision_conflict`.
5. Cancelling the run while waiting ends the node as cancelled; a late decision
   is rejected with `request_not_pending`.
6. Desktop UI: waiting Human nodes are visible on the live map and run overview;
   an approval view shows prompt, blast radius, and bounded safe-view evidence
   from bound inputs; approve/reject with optional comment; after submit the
   UI reflects the committed outcome, not an optimistic one.
7. Run history shows the request, decision, time and comment. A run that is
   `waiting` when the sidecar dies is shown as `interrupted`, never as
   resumed or approved.
8. Duplicate clicks, UI reload and two windows resolve to a single decision.

## Data / API contracts affected

- Graph schema: `human` node config (backward compatible for graphs without
  Human nodes; existing safe-view `human` case becomes meaningful).
- Events: event schema bump (current 8 -> 9) adding `human.requested` and
  `human.decided`; node state `waiting`.
- Desktop service protocol: typed methods for listing pending requests and
  submitting a decision, plus a projection of both events in replay/history.
- SQLite history projection (ADR-0018): request/decision rows. No change to
  existing completed-run rows.
- CLI: `agentplane run` on a graph with a Human node must have a
  deterministic non-interactive behavior (see Failure behavior).

## Failure behavior

- Invalid Human config or unbound evidence input fails validation with node id
  and source location before any node starts.
- Decision for an unknown/already-resolved/cancelled request returns a typed
  error; no state or event change.
- Comment over the length bound, or containing a configured secret, is
  rejected or redacted; it is never stored raw.
- Durable commit failure leaves the node `waiting` and returns an error; the
  node never continues on an uncommitted decision.
- CLI without a decision channel: the node fails with reason
  `human_required_no_channel` rather than blocking forever (until the CLI
  decision command exists, see Open questions).

## Acceptance criteria

- [ ] A graph with two independent branches, one containing a Human node, runs:
      the other branch completes while the Human node is `waiting`.
- [ ] Approve continues dependents exactly once; reject fails the node with
      `human_rejected` and does not rerun accepted siblings.
- [ ] Same-key resubmission yields identical outcome and exactly one
      `human.decided` event; conflicting resubmission returns
      `decision_conflict` with no new event.
- [ ] Event stream for a Human run is reconstructable: `human.requested`
      precedes `human.decided`, which precedes dependent `node.started`
      (verified by sequence numbers).
- [ ] Killing the sidecar while waiting yields history status `interrupted`.
- [ ] Cancel while waiting yields cancelled node and `request_not_pending` for
      a late decision.
- [ ] No raw secret/comment overflow appears in events, SQLite DB/WAL or files
      (redaction test).
- [ ] Desktop e2e: approve and reject paths driven through the UI with fake
      adapters only; no paid/production agent is run.
- [ ] `make check` green; native Windows/Linux/macOS runs reported separately.

## Required tests

- Unit: Human config validation, state machine transitions, idempotency key
  handling, comment bounds/redaction.
- Integration: scheduler overlap proof with explicit barriers (waiting node does
  not block sibling branch), durable-commit-before-continue ordering with
  injected commit failure, cancel/late-decision.
- CLI/e2e: `human_required_no_channel` behavior; packaged-app approve/reject
  flow; history replay of a decided and an interrupted run.

## Security / trust considerations

Prompt, comment, evidence and decision requests are untrusted input. Evidence is
rendered only through safe-view projections. Decision submission is a typed
sidecar method callable only through the authenticated local protocol; no new
network listener. The UI must not reveal model reasoning or raw secrets.

## Observability

`human.requested` (node run id, request id, blast radius, evidence refs) and
`human.decided` (request id, decision, idempotency key, comment hash/redacted
text, committed-at). Waiting is derivable from events alone.

## Open questions

1. CLI channel: ship `agentplane decide ...` now, or keep
   `human_required_no_channel` until Phase 3? (Owner decision.)
2. Reject: run-ending only now (proposed), or explicit transition edge now?
   Roadmap schedule lists it as "end of run or explicit transition" (Thu 12.11).
3. Is `blast_radius` only declared metadata for display now, or does it already
   gate behavior (e.g. L1 may auto-open when deterministic checks pass)?
   Proposed: display-only; no auto-open in this iteration.
4. Visual variants for the approval view await owner approval.

## Out of scope for this iteration

Web approval, multi-approver, timeouts, resumable waiting runs, auto-open by
blast radius, replanning transitions.
