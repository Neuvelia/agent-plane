# F3.3 - Resume / Recovery

**Status:** draft
**Priority:** P0
**Target phase:** Phase 3 - Local Production Ready
**Registry:** `docs/roadmap/features.yaml` entry F3.3
**Depends on:** F3.1, F3.2, F2.10
**ADR:** ADR-0051 (proposed)
**Issue:** #207

## Problem

F3.2 made the JSONL event log the durable state of a run and can tell a
`running` run from an `interrupted` one (ADR-0027). Nothing can continue an
interrupted run:

- **A crash, reboot or closed laptop** loses all remaining work. A rerun
  re-executes nodes that already succeeded, including Agent attempts that
  cost money and changed files.
- **A waiting `human` node does not survive process death** (ADR-0017). An
  approval that comes hours later has no run left to approve.

In the reference project of the adoption analysis
(`kacwojdev/agent-control-plane`), `graph approve` followed by `graph resume`
is part of daily use for L2/L3 gates. AgentPlane cannot express that flow.

## Goal

An interrupted run continues under the same run ID. Succeeded work is never
redone. Work whose side effects are uncertain is never replayed without an
operator decision. Pending human decisions can be given at resume time.

## Non-goals

- Exactly-once side effects (roadmap F3.3 out of scope).
- Automatic resume on start, a daemon or a supervisor.
- Resuming a `cancelled`, `failed` or `succeeded` run ("rerun from node" is a
  different feature).
- Resuming with a changed graph.
- Desktop resume controls (a follow-up; the API seam is listed below).

## Functional requirements

1. **Command:**

   ```text
   agentplane runs resume RUN_ID [--store-dir DIR] [--approve NODE]... [--reject NODE]... [--retry NODE]... [--json | --watch]
   ```

   Same exit codes as `agentplane run`.
2. **Preconditions.** All are checked before anything is appended. A failure
   leaves the log byte-identical.
   - The run exists in the store and its derived state is `interrupted`. A
     `running` run (lock held) gives `E_RESUME_LOCKED`. A terminal run gives
     `E_RESUME_TERMINAL`.
   - The graph file recorded for the run is re-read and its semantic
     `graph_version` equals the recorded one. Otherwise `E_RESUME_GRAPH_CHANGED`
     names both hashes.
   - Every accepted output needed by a pending node can be rehydrated (FR4).
     Otherwise `E_RESUME_VALUES_MISSING` names the node and port.
   - Run-scoped resources still exist: the F3.1 integration ref for isolated
     runs, and the workspace path. Otherwise `E_RESUME_WORKSPACE_MISSING`.
3. **Node classification**, derived only from the log:
   - **kept:** a terminal `succeeded` (accepted) node. It is never executed
     again. F3.3-AC1.
   - **pending:** no `node_started`. It runs normally once its dependencies
     are satisfied.
   - **uncertain:** `node_started` (or an attempt started) without a terminal
     node event. It is not replayed. It becomes `needs_intervention` with
     reason `uncertain_side_effect`, and its dependents stay pending, unless
     the operator passes `--retry NODE`. Then it runs again from attempt 1
     with a new node-run ID linked to the old one. F3.3-AC2.
   - **waiting human:** a `human` node with an approval request and no
     decision. It returns to waiting. `--approve` / `--reject` decide it
     immediately with the semantics of ADR-0017.
   - **failed or skipped** before the interruption: unchanged. Resume does not
     turn failures into retries.
4. **Value persistence.** A run is resumable only if its accepted outputs were
   persisted. When enabled (FR5), the runtime writes each accepted output once
   to `values/SHA256.json` in the run directory (mode 0600, content-addressed),
   and the existing acceptance event records the hash. Values are never placed
   in events. The F2.3-E6 recorded values stay bounded and redacted for
   display and are not used for rehydration.
5. **Enablement.** `agentplane run --resumable` (and the desktop sidecar
   setting) persists values. Without it, `runs resume` is refused with
   `E_RESUME_VALUES_MISSING` unless no kept node has a pending dependent. ADR-0051
   records the alternative of persisting always.
6. **Isolated Agent units** (F3.1): kept units are already integrated on the
   run-scoped ref. An uncertain node's linked worktree is discarded, never
   integrated, before `--retry` creates a fresh one.
7. **Events.** A new `run_resumed` event is appended first. It holds the new
   process's runtime version and the lists of kept, pending, uncertain,
   retried and waiting nodes. Sequence numbers continue the same log. A
   resumed run can be interrupted and resumed again.
8. **Store and API.** `runs list/show` show resumed runs with the resume count.
   The loopback API gains `POST /runs/{id}/resume` with the same parameters
   and refusals. The desktop button is a follow-up.

## Data / API contracts affected

- **CLI:** `runs resume`; `run --resumable`.
- **Events (schema bump):** `run_resumed`; an acceptance event field
  `value_ref` (sha256), present only for resumable runs; the
  `needs_intervention` reason `uncertain_side_effect`.
- **Store:** the `values/` directory in run directories. `runs prune`
  deletes it with the run.
- **API:** `POST /runs/{id}/resume`.

## Failure behavior

Every refusal in FR2 is typed and leaves the log unchanged. A crash during
resume leaves the run `interrupted` again, and resume can be retried; FR3 is
computed from the log each time. A value file whose hash does not match is
`E_RESUME_VALUE_CORRUPT`; it is never silently re-computed.

## Roadmap criteria

| Criterion | Roadmap text | Treatment |
| --- | --- | --- |
| F3.3-AC1 | Po restarcie run z trzema zakończonymi node'ami nie wykonuje ich drugi raz. | covered by acceptance criterion 1 |
| F3.3-AC2 | Niepewny command z side effect nie jest automatycznie replayowany. | covered by acceptance criterion 2 |

## Acceptance criteria

- [ ] A run with three succeeded nodes, killed with SIGKILL while a fourth runs, resumes
  without executing the three again (per-node counter files unchanged). The fourth is
  uncertain. Proves F3.3-AC1; test tagged `// roadmap: F3.3-AC1`.
- [ ] An uncertain Shell node with a side effect (an append to a file) is not replayed:
  the run ends `needs_intervention` with `uncertain_side_effect` and the file has one
  line. With `--retry NODE` it runs again. Proves F3.3-AC2; test tagged
  `// roadmap: F3.3-AC2`.
- [ ] A run killed while a human node waits resumes with `--approve NODE` and completes.
  Downstream receives `decision: approved`.
- [ ] `E_RESUME_GRAPH_CHANGED`, `E_RESUME_TERMINAL`, `E_RESUME_LOCKED` and
  `E_RESUME_VALUES_MISSING` each leave the log byte-identical.
- [ ] A resumed run's log replays to the same derived state as the live process reported
  (F3.2 reducer), including after a second interruption and resume.
- [ ] No value content appears in `run_resumed` or acceptance events; value files are
  mode 0600.

## Required tests

- **Unit:** the classification reducer over synthetic logs; precondition
  checks; value store read/write and hash verification.
- **Integration:** a real subprocess runner killed at barriers (no sleeps) and
  then resumed; the isolated-worktree variant.
- **CLI/e2e:** `runs resume` exit codes and `--json` output; the API endpoint.

## Security / trust considerations

- **Value files** may hold sensitive outputs. They are 0600, stay in the store
  directory and are never sent anywhere. Redaction does not apply to them, so
  they are excluded from any export and diagnostics bundle (F3.7, F3.11).
- **Resume re-reads the graph file from disk** and refuses on any hash change,
  so a modified graph cannot inherit approvals.
- **Approvals given at resume** are recorded as ordinary approval events with
  the same validation as live approvals.

## Observability

- `run_resumed` with node lists.
- Resume count per run in `runs list`.
- `uncertain_side_effect` is countable across runs: the metric for how often
  crashes hit in-flight work.

## Open questions

1. Value persistence opt-in (`--resumable`, recommended) or always on for runs
   with a store? Always-on costs disk space and keeps sensitive values on disk
   for every run.
2. May an author declare `recovery: replay` on a Shell node known to be
   idempotent, so it is replayed without `--retry`? Recommended: not in v1.
3. Should resume with a changed graph be possible when only nodes that were not
   yet started changed? Recommended: no (a later feature, with an ADR).

## Out of scope for this iteration

Automatic resume, desktop controls, rerun of terminal runs, graph changes on
resume, exactly-once guarantees, resume of a run started by an older event
schema without value files.
